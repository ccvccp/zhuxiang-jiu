# 竹创·全周期智能 Agent 融合设计

- 日期：2026-11-28
- 目标仓库：`ccvccp/zhuxiang-jiu`
- 基线：`master` 合并提交 `1997d689cc44c5a4bb2b223ed17d6c1212958e25`
- 方案：统一主 Agent＋共享运行档案＋全周期活文档
- 状态：总体架构、数据流、部署与验收四部分已获用户逐项批准，等待书面规格复核

## 1. 背景与现有能力

仓库已有两类互补但尚未形成统一生命周期的 Agent 能力。

### 1.1 受控协同开发团队

`docs/agent-team/` 定义 Kimi Work 主 Agent 按需组织需求、架构、前端、后端、测试、独立审查和交付子 Agent。GitHub Issue、分支、PR 和 CI 是正式记录，PR 合并与生产部署均需用户分别确认。

### 1.2 竹创创新规划与 Word 流水线

`zhuxiang-jiu/agent-infra/zhuchuang/` 已提供证据采集、外部模型适配、规划、设计、部署、验收、确定性审查、失败恢复和合并 Word 生成能力。四章通过稳定编号和结构化数据保持一致，无真实证据时验收保持 `pending`。

当前缺口不是再增加一组角色，而是让开发过程与四章文档共享同一运行、同一证据链和同一版本状态，避免“代码已经变化、文档仍描述旧方案”或“模型文本被误当成执行事实”。

## 2. 目标与成功闭环

用户只向一个主 Agent 提出一次需求，系统按需完成：

`需求 → 四章初版 → Issue／开发 → 测试／审查 → PR → 合并确认 → 部署确认 → 真实验收 → 四章正式版`

首版目标如下：

1. 一个需求只建立一个统一 `run_id`，Issue、分支、PR、测试、四章和 Word 均可追踪到该运行。
2. 四章是全周期活文档：规划阶段形成初版，开发、测试、PR、部署和验收证据持续回流。
3. 代码、GitHub、测试和部署事实只来自真实工具结果；外部模型只生成候选方案与文档内容。
4. 任一影响规划、设计、代码范围或证据的变化都会使旧文档审查许可失效。
5. 中断恢复不重复创建 Issue、分支或 PR，不重复执行生产命令。
6. 功能交付与生产验收分开表述；未部署或未执行验收时不得写成 `passed`。
7. 最终 Word 只从当前审查通过的四章源稿生成，并能重新打开解析和回读验证。

## 3. 约束与非目标

1. 沿用 Kimi Work 主 Agent 和仓库内轻量 CLI，不引入常驻调度服务、任务数据库、分布式队列或管理后台。
2. 复用现有 `llm_client.py`、竹创模型适配器、项目事实注册表、团队角色规程和 GitHub 模板。
3. 外部模型只接收当前阶段所需的最小脱敏证据，不接收密钥、生产配置、用户数据或完整仓库。
4. 外部模型不能直接创建 Issue、修改代码、合并 PR、操作生产环境或宣布验收通过。
5. PR 合并必须获得用户明确批准；生产部署必须针对当次运行另行明确批准。
6. 首版不实现自动合并、自动生产部署、管理界面或常驻部署服务。
7. 不修改用户原始 `D:\网站架构设计`；开发从 GitHub `master` 的干净基线开始。
8. 不提交 `.env`、凭据、本地缓存、运行输出或其他敏感文件。

## 4. 方案比较与决策

| 方案 | 优点 | 缺点 | 决策 |
| --- | --- | --- | --- |
| 统一主 Agent＋共享运行档案＋活文档 | 融合紧密，复用现有能力，证据与版本一致，无需常驻服务 | 需要统一状态契约、同步与失效规则 | 采用 |
| 全部收进竹创 CLI | 命令统一，便于批处理 | 重复建设 Kimi Work 调度，权限与交互复杂，改造最大 | 不采用 |
| 两套系统顺序衔接 | 改动少，落地快 | 仍是拼接，中间状态不回流，文档易漂移 | 不采用 |

## 5. 总体架构

### 5.1 三层结构

| 层级 | 组成 | 职责 |
| --- | --- | --- |
| 统一控制层 | Kimi Work 主 Agent、统一运行档案、人工确认门 | 接收需求，控制生命周期、依赖、恢复、授权和最终汇报 |
| 专业能力层 | 协同开发团队与竹创规划、设计、部署、验收、审查能力 | 按阶段完成开发或文档工作，以结构化契约交接 |
| 证据与交付层 | 项目事实包、Issue／PR、测试记录、四章源稿、Word | 保存可核验证据，保证代码、文档和执行结果同版 |

### 5.2 角色融合

| 融合角色 | 主要职责 | 权限边界 |
| --- | --- | --- |
| 主 Agent／统一协调者 | 需求接收、运行建立、任务拆分、状态提交、证据集成、恢复与汇报 | 不自动合并或部署，不绕过审查 |
| 需求 Agent＋规划 Agent | 目标、范围、非目标、优先级、创新规划和验收口径 | 不修改业务代码，不虚构项目事实 |
| 架构 Agent＋设计 Agent | 组件、接口、数据、安全、依赖和跨章追踪 | 重大架构变化需用户确认 |
| 前端／后端 Agent | 在分配范围内实现代码和测试 | 不直接改写规划或验收结论 |
| 测试 Agent＋验收 Agent | 共用验收用例，执行测试并映射真实证据 | 不删除或放宽测试，不无证据判定通过 |
| 部署 Agent | 部署前提、步骤、确认门、验证、执行记录与回滚 | 未获当次授权不得执行生产部署 |
| 代码审查 Agent＋竹创独立审查 | 分别检查代码质量与文档事实、追踪、一致性、真实性 | 任一硬门禁失败均阻止正式交付 |
| 交付 Agent＋Word 渲染器 | 汇总 Issue／PR 和证据，渲染当前审查通过版 Word | 不渲染过期或阻断源稿 |

### 5.3 单一控制中心

竹创原编排器作为统一主 Agent 调用的文档能力引擎，不再形成第二个全周期控制中心。现有 CLI 保留用于独立调试、文档恢复和证据导入，但开发任务的 Issue、分支、PR 与授权决策由统一主 Agent 协调。

主 Agent 是运行档案的唯一写入协调者。专业角色返回结构化结果，不直接并发修改共享清单或四章。

## 6. 全周期数据流

### 6.1 生命周期

```text
需求进入
  ↓
固定仓库基线，采集项目事实，建立唯一 run_id
  ↓
生成四章初版：规划／设计完整，部署为方案，验收为 pending
  ↓
初版审查通过 → 创建或关联 Issue → 拆分开发任务
  ↓
编码、测试、独立代码审查、PR
  ↓                 ↓
  └──── 里程碑证据持续回流四章 ────┘
  ↓
用户确认合并 → 记录真实合并提交
  ↓
用户另行确认部署 → 执行部署并采集验证证据
  ↓
导入真实验收证据 → 重新审查 → 更新同一份正式 Word
```

未获得合并或部署确认时，流程停在对应人工门，不自动前进，也不把后续内容写成已完成。

### 6.2 里程碑

| 里程碑 | 必要记录 | 对四章的影响 |
| --- | --- | --- |
| 项目证据建立 | 仓库提交、脏工作区状态、事实包哈希 | 填充现状事实与证据索引 |
| 初版审查通过 | 四章源稿哈希、审查报告 | 允许创建开发任务和初版 Word |
| 开发任务建立 | Issue、分支、责任和依赖 | 更新任务追踪，不写成开发完成 |
| 代码与测试完成 | 提交、测试命令、退出状态、结果摘要 | 更新实现状态与验收证据映射 |
| PR 审查完成 | PR 链接、独立审查、CI 状态 | 更新交付状态，等待合并确认 |
| 合并完成 | 真实合并提交 | 更新基线，不代表部署完成 |
| 部署执行完成 | 环境、命令、时间、退出状态、健康检查 | 更新部署事实，不自动等于验收通过 |
| 验收结论记录 | 每个用例的真实证据和结论 | 形成 `pending`、`passed` 或 `failed` |

## 7. 共享运行档案与接口契约

### 7.1 存储位置

沿用 `zhuxiang-jiu/output/zhuchuang/<run-id>/`，不新增数据库。运行产物继续不默认进入 Git。

现有文件继续保留：

- `manifest.json`：统一运行状态和交付索引；
- `evidence.json`：项目事实和真实证据；
- `chapters.json`：当前四章结构化源稿；
- `review.json`：当前审查许可、阻断和警告；
- `document.md`：当前合并源稿；
- `创新规划设计部署验收.docx`：当前最新审查通过版 Word。

### 7.2 清单扩展

在不删除现有字段的前提下，`manifest.json` 增加以下逻辑信息：

| 字段组 | 内容 |
| --- | --- |
| `lifecycle` | 当前阶段、状态、阻塞原因、等待的确认类型 |
| `development` | Issue、分支、PR、提交、合并提交及其真实链接 |
| `document` | 当前递增版本、状态、源稿哈希、证据哈希、Word 路径 |
| `milestones` | 已完成里程碑、对应证据和原子提交时间 |
| `authorization` | 合并与部署授权的当次运行关联及确认范围；不保存秘密 |

文档状态限定为：

- `draft`：已生成但尚未通过当前审查；
- `reviewed`：当前源稿审查通过，可以渲染或已经渲染；
- `delivered`：当前 Word 与源稿、证据哈希一致并已通过回读；
- `stale`：输入已变化，旧审查和旧正式交付状态失效。

### 7.3 写入与并发

1. 主 Agent 串行提交共享状态和四章更新；并行开发角色只返回各自结果。
2. 清单、源稿和审查文件使用原子写入，不能只更新其中一部分后宣称里程碑完成。
3. 同一运行不得并发执行两个会修改共享状态的生命周期提交。
4. 每次里程碑提交先核对当前版本，发现基线变化时停止并重新集成，不覆盖他人结果。
5. 角色交接至少包含 `run_id`、目标、允许范围、输入版本、证据引用、禁止事项和预期输出。

## 8. 活文档版本与失效规则

### 8.1 同一最新文档

运行目录根部的合并 Word 只表示当前最新审查通过版。每次正式更新分配递增版本号，并关联对应 Issue、PR、合并提交或验收证据。

### 8.2 历史快照

每次正式更新前，将上一版清单摘要、四章、审查报告、Markdown 和 Word 保存在 `revisions/R<序号>/`。历史快照只读，用于审计和比较，不作为当前交付入口。

### 8.3 变更即失效

以下变化必须使当前文档进入 `stale`：

- 规划目标、范围、非目标或验收口径变化；
- 架构、组件、接口、数据或安全设计变化；
- 与文档相关的代码范围、PR 或合并提交变化；
- 测试、部署或验收证据新增、替换或失效；
- 源稿哈希或证据哈希与当前审查记录不一致。

失效时，旧版移入历史快照，当前正式 Word 入口不再指向旧版。只有重新审查和渲染成功后，才恢复当前正式 Word 和 `delivered` 状态。不得通过手工修改清单状态绕过重新审查。

### 8.4 事实来源优先级

| 内容 | 可接受来源 |
| --- | --- |
| 项目现状 | 注册表 Markdown、代码和已定位项目资产 |
| Issue、分支、PR、合并 | GitHub 或 Git 实际查询结果 |
| 测试与 CI | 真实命令输出、退出状态和 CI 记录 |
| 部署 | 已批准步骤的真实执行记录和健康检查 |
| 验收 | 覆盖全部用例的有效证据 |
| 未来规划与建议 | 明确标注的模型或人工候选内容 |

模型文本不能覆盖上述事实来源。

## 9. 外部模型与降级

继续支持 `auto`、`external` 和 `rule`：

- `auto`：外部模型不可用时按阶段明示降级，允许记录 `mixed`；
- `external`：严格外部模式，失败或一次纠错后仍不符合契约即停止；
- `rule`：只使用真实证据和确定性模板，不调用模型。

活文档同步不因为“需要更新”就重复调用外部模型。确定性状态、链接、提交、测试和验收事实由同步器直接更新；只有需要重新生成方案文本时才调用模型，并保留实际生成方式和警告。

## 10. 部署设计

### 10.1 部署前检查

1. 确认目标环境、待部署合并提交和实际变更范围。
2. 核对 CI、独立代码审查和当前文档审查状态。
3. 检查配置完整性、健康检查方法和回滚条件；不得打印或上传秘密。
4. 具体命令只能来自目标仓库真实 Docker、脚本或运行手册。

### 10.2 单独授权

部署前向用户展示目标环境、合并提交、执行步骤、影响、验证和回滚方案。只有用户明确确认当次生产部署后才能执行。设计批准、PR 合并批准和其他运行的授权不能复用。

### 10.3 执行与验证

按已批准步骤执行，记录真实命令、环境、时间、退出状态和结果。部署 Agent 只提交执行记录，验收 Agent 根据覆盖用例的证据形成结论。部署成功不等于全部验收通过。

### 10.4 失败与回滚

仅执行用户已批准的安全回滚步骤。没有安全回滚方案时立即停止并报告，不自行扩大生产操作，不紧密循环重试生产命令。回滚同样需要保存真实证据并更新运行状态。

## 11. 安全与异常处理

| 场景 | 处理方式 |
| --- | --- |
| 外部模型失败 | 按生成模式明示降级或停止，不伪装成功 |
| 开发或测试失败 | 保留分支与失败证据，修复后重跑，验收不得通过 |
| 文档同步失败 | 代码结果不受影响，但运行未完成，旧正式 Word 失效 |
| 状态写入冲突 | 停止提交，重新读取当前版本并集成，不覆盖更新 |
| GitHub 状态不确定 | 先查询真实 Issue、分支和 PR，再恢复，避免重复创建 |
| 合并未授权 | 停在 PR 阶段，保持等待确认 |
| 部署未授权 | 只保留部署方案，不执行生产操作 |
| 部署失败 | 保存现场，按已批准方案回滚或停止 |
| 验收证据不足 | 保持 `pending`；真实失败证据形成 `failed` |
| 敏感信息或生产风险 | 停止相关处理，不提交、不输出秘密，不继续生产操作 |

密钥继续只从本地环境配置读取，不进入提示词、运行档案、Word、日志或 Git。

## 12. 测试策略

| 测试层 | 覆盖内容 |
| --- | --- |
| 契约单元测试 | 清单扩展、状态枚举、角色交接、里程碑和证据引用 |
| 生命周期测试 | 合法前进、人工门阻塞、失败、恢复和终态口径 |
| 版本测试 | 文档递增版本、历史快照、失效、重新审查和当前 Word 指向 |
| 并发测试 | 单写入协调、版本冲突和并行任务结果不丢失 |
| GitHub 集成测试 | Issue／PR 关联、真实状态查询和幂等恢复 |
| 模型测试 | 外部、规则、混轨、一次纠错和同步时不重复调用 |
| 真实性测试 | 伪造合并、部署、测试或验收声明被阻断 |
| Word 集成测试 | 当前版本生成、OOXML 校验、重新打开和四章／附录回读 |
| 回归测试 | 竹创既有测试及受影响的协同团队文档校验 |

真实外部模型和真实 GitHub 冒烟是独立验证，不得由模拟测试替代。生产部署与验收只能在用户选择目标环境并明确授权后执行。

## 13. 验收标准

### 13.1 功能交付验收

首版功能交付必须同时满足：

1. 一次真实需求只使用一个 `run_id`，Issue、分支、PR、四章和 Word 可相互追踪。
2. 初版、开发回流、PR 回流和最终交付使用同一运行档案。
3. 代码或证据变化会使旧版失效，旧 Word 不能继续作为当前正式版。
4. 中断恢复不会重复创建 Issue、分支或 PR。
5. 未经确认不能合并或部署；未经证据不能验收通过。
6. 外部模型降级和失败均如实标记，确定性同步不额外调用模型。
7. 既有及新增测试全部通过并记录实际数量；独立审查无未解决 Critical／Important。
8. 最终 Word 通过 OOXML 校验和内容回读，四章、附录、当前版本和验收状态完整。
9. Git 差异、日志、运行档案和 Word 不含密钥或生产敏感配置。

### 13.2 生产验收

生产验收必须在用户批准当次部署后，取得目标环境健康检查及全部业务验收用例的真实证据。有效通过证据才能形成 `passed`，失败证据形成 `failed`，证据不足保持 `pending`。

代码合并只代表代码基线变化，不能替代生产部署或生产验收。

## 14. 首版交付物

1. 更新后的统一协调规程和角色交接约定。
2. 统一生命周期清单、里程碑提交和版本失效机制。
3. 开发／GitHub 结果到四章的确定性同步接口。
4. 历史快照、当前 Word 入口和断点恢复能力。
5. 对应自动化测试、使用文档、部署运行手册和验收说明。
6. 一次真实小需求的端到端示例及实际 Issue／PR／测试证据。
7. 一份与该运行同版的四章合并 Word；未真实部署时验收保持 `pending`。
