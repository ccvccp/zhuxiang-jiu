# Kimi Work 受控多 Agent 协同开发团队设计

- 日期：2026-11-27
- 目标仓库：`ccvccp/zhuxiang-jiu`
- 基线分支：`master`
- 方案：按需启动的受控协同团队
- 状态：设计已获用户批准，等待书面规格复核

## 1. 背景与目标

竹香酒项目包含 FastAPI 后端、静态网站、Taro 小程序、Redis、Docker 和既有 CI。需要在该仓库中建立一套可由 Kimi Work 主 Agent 按需调度的多 Agent 协作机制，使用户提出一次需求后，团队能够完成需求分析、Issue 拆分、编码、测试、独立审查和 PR 创建。

GitHub Issue、分支、PR 和 CI 是正式的协作与审计记录；Kimi Work 对话负责协调和汇报。本方案不引入常驻调度服务，不自动合并 PR，也不自动部署生产环境。

## 2. 成功标准

首版配置完成后，能够从一个真实的小型需求走完以下闭环：

`需求 → 验收标准 → Issue → 独立分支 → 编码 → 测试 → 独立审查 → PR → 等待用户确认`

交付汇报必须提供真实的 Issue／PR 链接、变更摘要、实际执行的测试及结果、未解决事项。没有运行的检查不得写成已通过。

## 3. 约束与边界

1. 用户每批新需求在 Kimi Work 中发起一次，之后由主 Agent 自动组织本批工作。
2. PR 合并必须由用户明确批准；生产部署需要单独、再次明确批准。
3. 开发从 GitHub `master` 的干净副本开始，不直接修改用户 `D:\网站架构设计` 中现有未提交内容。
4. 不提交 `.env`、凭据、浏览器缓存、本地运行产物或无关文件。
5. 不访问或修改生产数据、生产服务，不绕过现有检查和审查。
6. 首版不建设任务数据库、常驻服务、管理后台、自动合并或自动部署能力。
7. 子 Agent 仅在用户已明确请求多 Agent 协同的任务中启动，并遵循主 Agent 分配的范围。

## 4. 团队架构与职责

主 Agent 是唯一协调入口。专业子 Agent 不绕过主 Agent 修改其他任务，也不直接向用户承诺最终结果。

| 角色 | 主要职责 | 权限边界 |
|---|---|---|
| 主 Agent／协调者 | 需求接收、上下文准备、任务拆分、依赖管理、进度统筹、结果集成与汇报 | 不自动合并 PR、不部署生产 |
| 需求 Agent | 用户故事、验收标准、边界场景、Issue 内容建议 | 不修改业务代码 |
| 架构 Agent | 技术方案、模块影响、依赖顺序、数据与接口约定 | 重大架构变更需用户确认 |
| 前端 Agent | 静态网站、Taro 小程序及对应测试 | 只修改分配范围内的文件 |
| 后端 Agent | FastAPI、Redis、数据库及对应测试 | 不直接操作生产数据或服务 |
| 测试 Agent | 测试计划、自动化用例、回归验证、失败复现 | 不删除或放宽测试制造通过 |
| 审查 Agent | 独立代码审查、安全检查、验收标准核对 | 可退回修改，不可自行合并 |
| 交付 Agent | 分支整理、提交、PR 描述、Issue 关联、交付清单 | 创建 PR 后停止并等待用户决定 |

### 4.1 调度原则

- 一个开发 Issue 对应一个独立分支和明确责任 Agent。
- 无共享状态、无依赖的任务才可并行；存在依赖或可能修改同一文件的任务串行执行。
- 主 Agent 在分派前提供真实路径、已有结论、验收标准和禁止事项，避免子 Agent 重复探索或越界。
- 需要理解关键文件或行号时，主 Agent 先定位再分派；不能把理解核心问题的责任完全转交给子 Agent。
- 审查 Agent 不应是同一变更的唯一实现者，确保至少有一次独立复核。

## 5. 端到端工作流程

### 5.1 需求进入

用户在 Kimi Work 描述需求。主 Agent 检查仓库、现有文档和近期变更。信息足够时继续；关键信息缺失时集中说明假设和阻塞项，不虚构事实。

### 5.2 需求与架构分析

需求 Agent 形成可验证的验收标准；架构 Agent 判断影响范围、依赖顺序、测试策略和回退方式。小需求可合并这两个环节，避免不必要的手续。

重大架构变化、数据迁移、权限扩大或生产行为变化必须单独提示用户，不能藏在普通开发任务中。

### 5.3 Issue 拆分

主 Agent 创建描述总体目标的父 Issue，并按可独立交付的工作拆分相关 Issue。每个开发 Issue 必须包含：

- 目标与验收标准；
- 修改范围及明确不做的内容；
- 前后置依赖；
- 测试要求；
- 风险与回退方式。

Issue 是任务状态的正式记录。重复执行前必须搜索现有 Issue 和分支，避免重复创建。

### 5.4 隔离开发

开发分支命名为 `agent/<Issue编号>-<简短英文名称>`。每个任务只包含所属 Issue 的变更，提交遵循仓库既有 Conventional Commits 风格。

本设计文档先在 `docs/agent-team-design` 分支提交；实施阶段从该分支创建带真实 Issue 编号的正式任务分支，设计文档随首版配置一起进入 PR。

### 5.5 测试与独立审查

测试 Agent 提供真实命令、退出状态和关键结果。既有失败与本次引入的失败必须区分；没有证据时不得归因。

审查 Agent 核对代码差异、验收标准、安全风险、测试证据和回归影响。未通过时退回责任 Agent 修复，不能将未通过项描述为可合并。

### 5.6 PR 交付

交付 Agent 创建 PR 并关联对应 Issue。PR 必须写清：

- 变更摘要；
- 验收标准完成情况；
- 实际测试命令和结果；
- 影响范围与风险；
- 遗留事项；
- 回退方法。

CI 通过且独立审查完成后，PR 才进入“等待用户确认”的状态。

### 5.7 人工决策

只有用户明确同意才可合并 PR。生产部署是独立决策，不因合并而自动触发。部署前必须另行提供目标环境、变更范围、验证和回退方案。

## 6. 异常处理与恢复

| 场景 | 处理方式 |
|---|---|
| 测试失败 | 先复现并分类，由责任 Agent 修复后重跑；不得删除、跳过或放宽测试制造通过 |
| 代码冲突 | 主 Agent 调整任务顺序或文件边界；业务语义冲突不强行自动解决 |
| 需求阻塞 | 在 Issue 记录缺失信息和影响，暂停该任务，继续无依赖任务 |
| 连续修复失败 | 同一问题两轮修复仍未通过则停止循环，向用户提供失败证据和建议 |
| 工具或网络异常 | 保留分支和修改，记录最后成功步骤；传输错误按工具可靠性规则有限重试，不重复创建 Issue／PR |
| 范围扩大 | 主 Agent 重新评估拆分与风险；重大变化需用户确认 |
| 敏感信息或生产风险 | 立即停止相关操作，不提交、不输出秘密，向用户说明阻塞原因 |

## 7. 首版交付物

### 7.1 团队规范与角色提示词

在 `docs/agent-team/` 中提供：

- 使用入口和端到端操作规程；
- 主 Agent 调度规则；
- 需求、架构、前端、后端、测试、审查、交付角色的提示词；
- 任务交接所需的最小上下文模板。

这些文件是主 Agent 分派时显式读取和引用的仓库内规范，不宣称会被 Kimi Work 自动加载。

### 7.2 GitHub 模板

- `.github/ISSUE_TEMPLATE/agent-task.md`：目标、范围、验收标准、依赖、测试和回退要求。
- `.github/PULL_REQUEST_TEMPLATE.md`：变更摘要、Issue 关联、测试证据、风险、遗留事项和回退说明。

模板应简洁，小任务可以填写“无”并说明理由，避免形式化负担。

### 7.3 首个受控开发任务

以“配置 Kimi Work 多 Agent 协同团队”为首个任务：

1. 设计文档复核后编写实施计划。
2. 创建真实 Issue，使用正式 `agent/<Issue编号>-...` 分支。
3. 添加团队规范、角色提示词和 GitHub 模板。
4. 校验 Markdown 链接、模板字段、路径和 Git 差异。
5. 进行独立审查，修复发现的问题。
6. 创建 PR 并等待用户确认，不自动合并或部署。

## 8. 测试与验收策略

首版主要变更应为文档和 GitHub 模板，不修改业务代码，因此无需运行与变更无关的完整业务测试套件。必须执行与变更相匹配的验证：

1. 检查所有新增文件位于预期路径，没有敏感文件或本地产物混入。
2. 校验内部 Markdown 链接指向真实文件。
3. 校验角色提示词均包含职责、输入、输出和权限边界。
4. 校验 Issue／PR 模板覆盖本设计要求的必填信息。
5. 检查 Git 差异仅包含首版约定内容。
6. 由独立审查 Agent 复核可执行性、一致性和权限边界。
7. 在 PR 中如实列出所执行的文档校验；未运行业务测试时明确说明原因和范围。

若实施过程中需要修改脚本或业务代码，必须补充对应自动化测试，不能沿用“仅文档变更”的验证策略。

## 9. 使用方式

配置合并后，用户在 Kimi Work 中提出需求并指定该仓库。主 Agent 读取 `docs/agent-team/` 的规程，完成需求和架构分析，创建或复用 Issue，按依赖调度子 Agent，并在测试与独立审查通过后交付 PR。

示例：

> 在 zhuxiang-jiu 仓库中修复购物车优惠计算问题。按受控多 Agent 团队流程完成分析、Issue、开发、测试、审查和 PR；不要合并或部署。

## 10. 非目标与后续扩展

首版不包含 GitHub Issue 自动巡查、定时触发、自动合并、自动部署、常驻调度服务或管理界面。如果后续需要 Issue 标签驱动或定时开发，应在独立设计中补充任务锁、防重复领取、失败恢复、配额和通知机制。
