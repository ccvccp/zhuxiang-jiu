## 一、背景与问题

### 1.1 问题发现

对 `main.py` 的三个端点做并发数据竞争风险评估时发现:

| 端点 | 操作 | 风险 |
|---|---|---|
| `POST /api/inventory/deduct` | `stock -= q`(check-then-act + RMW) | 🔴 **超卖**(库存变负) |
| `POST /api/inventory/restock` | `stock += q`(RMW) | 🟠 回补量丢失 |
| `POST /api/agent/upgrade` | `wallet += pay`(RMW) | 🟠 **钱包充值丢失**(资损) |

### 1.2 根因

- 三个端点都是 `async def`,但函数体内 **0 个 `await`** — 单进程单事件循环下隐式原子
- 这是一种**隐式、脆弱**的并发安全:
  - 一旦引入 `await db.fetchone()` 立即在 RMW 中间产生让出点
  - 改为同步 `def` 后 FastAPI 用线程池,GIL 不保护复合操作
  - 多 worker 部署更严重(进程独立内存)
- 与前端 `inventory-service.js` 的 lost-update Bug **同构**,前端已用 FIFO Mutex 修复,后端未对齐

### 1.3 边界测试发现的安全漏洞

生成边界测试时发现 `AgentUpgradeRequest.payAmount` 缺 `ge=0` 约束:

```python
# 修复前:负数可绕过,钱包被恶意扣减
payAmount: float = Field(0, description="支付金额")
# 修复后:ge=0 拦截负数
payAmount: float = Field(0, ge=0, description="支付金额")
```

根因:`agent["wallet"] = agent.get("wallet", 0) + req.payAmount` — payAmount 无下界,负值扣减钱包。

## 二、asyncio.Lock 实现

### 2.1 锁基础设施

文件:[`zhuxiang-jiu/backend/main.py`](../zhuxiang-jiu/backend/main.py#L72-89)

```python
import asyncio

_locks = {}

def _get_lock(key: str):
    """获取或创建 per-key 锁。单事件循环下无 await,创建竞态安全。"""
    if key not in _locks:
        _locks[key] = asyncio.Lock()
    return _locks[key]
```

### 2.2 三个端点加锁

| 端点 | 锁键 | 保护范围 | 设计要点 |
|---|---|---|---|
| `agent_upgrade` | `agent:{agentId}` | wallet 累积 RMW | per-agent 互斥 |
| `inventory_deduct` | `stock:{productId}` | check-then-act + RMW(防超卖) | check+扣减整体加锁 |
| `inventory_restock` | `stock:{productId}` | stock 累积 RMW | **与 deduct 共享锁键** |

### 2.3 对齐前端 Mutex 模式的 5 个设计点

| 设计点 | 前端 Mutex | 后端 asyncio.Lock |
|---|---|---|
| 锁键格式 | `stock:productId` / `agent:{agentId}` | `stock:{productId}` / `agent:{agentId}` |
| 公平性 | FIFO 队列 | asyncio.Lock 本身 FIFO |
| 释放保证 | try/finally | `async with`(异常也释放) |
| check-then-act 整体加锁 | 锁内检查+扣减 | 锁内检查+扣减 |
| deduct/restock 共享锁键 | 同一 `stock:productId` | 同一 `stock:{productId}` |

## 九、已知限制与后续方向

### 9.1 当前已知限制

| 限制 | 说明 |
|---|---|
| 单进程有效 | `asyncio.Lock` 是进程内锁,多 worker(`uvicorn --workers N`)不共享 |
| `_mock_store` 内存存储 | 测试用内存存储,生产需替换为真实 DB |
| 无 await 下锁是防御性 | 当前隐式原子已足够,锁为未来引入 await / 改 sync / 多 worker 提供显式保护 |

### 9.2 后续演进方向

| 场景 | 方案 | 何时考虑 |
|---|---|---|
| 引入 `await db.fetchone()` | 当前 asyncio.Lock 直接生效 | 加 DB 层时 |
| 改为同步 `def` 端点 | 当前 asyncio.Lock 仍有效(async with 在 async 函数内) | 如需阻塞 IO |
| 多 worker 部署 | Redis 分布式锁 或 真实 DB 行锁 | 上生产时 |
| 跨服务并发 | 分布式锁(Redis Redlock) | 微服务化时 |
