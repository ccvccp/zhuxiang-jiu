## 一、背景与问题

### 问题 1: 扫码赚钱模块生产全链路瘫痪(严重)

生产环境所有读参数端点(领码/统计/团队/奖励/活动酒池/admin)返回 500:

```
{"error":"Invalid input of type: 'bool'. Convert to a bytes, string, int or float first."}
```

**根因**: `promotion_repository._serialize_settings` 只 JSON 化 `dict/list`,
而 `DEFAULT_SETTINGS` 含 `enabled: True`(bool)——redis-py 拒绝 bool 直传 hset。
生产 settings 键不存在, 每次 GET 触发初始化路径 `hset(enabled=True)` 即炸。

**盲区**: 本地测试 45/45 全绿(内存模式无此约束)——双模式序列化
缺陷在内存模式下不可见。pocket/flashsale 均已正确处理 bool,
promotion 是漏网之鱼。

### 问题 2: boundCount Redis 反序列化为字符串

`get_code` 读出的 `boundCount` 为字符串 `"0"`——truthy 导致前端
`c.boundCount || 0` 失效且类型不诚实。

### 问题 3: 钱包总资产漏奖励余额(口径缺口)

用户口径要求: 奖励类收入(扫码/顺手等)存入**专用购物账户**(与存现隔离,
不可提现), 但钱包总资产显示**总和**。

核查结论: 账户隔离设计本就正确(8 个奖励类模块全部经 `deposit_reward`
入 `rewardBalance`, `withdraw` 仅操作 `balance`); 但 `get_info` 的
`totalAssets = balance + 定期 + 待结` **漏了 rewardBalance**, 且前端
钱包页完全未展示奖励余额——与「显示总和」要求不符。

## 三、收入隔离机制(终态口径, 核查确认)

| 资金类型 | 入账路径 | 账户 | 可提现 | 可购物 |
|---|---|---|---|---|
| 扫码赚钱(一级¥20/轮·二级¥15/轮) | `deposit_reward` | `rewardBalance` | ✗ | ✓ |
| 顺手赚钱(打卡¥2/存续奖¥20-30) | `deposit_reward` | `rewardBalance` | ✗ | ✓ |
| 其他奖励(信值结算/引流/同盟/角色等 8 模块) | `deposit_reward` | `rewardBalance` | ✗ | ✓ |
| 存现充值(≥¥100) | `deposit` | `balance` | ✓ | ✓ |

隔离由代码结构保证: `withdraw` 只读 `balance` 余额, `rewardBalance`
不可提现不可转赠, 仅 `pay_with_reward` 购物核销。
总资产显示总和: `balance + rewardBalance + 定期 + 待结`。

## 六、经验沉淀(可复用)

1. **Redis 双模式序列化盲区**: 模块 settings 含 bool/None 字段时,
   序列化必须 JSON 化——本地内存模式测试全过不代表 Redis 模式可用。
   排查方式: 生产公网直调 + 看容器日志; 对照 pocket/flashsale 的
   正确实现
2. **Redis 数值字段还原**: hgetall 读出的数值字段一律按类型还原
   (boundCount/int), 前端 VO 用 Number 强转兜底
3. **SSH 自定义头验证坑**: PS 单引号经 ssh 到 bash 时内部双引号会
   丢失(`curl -H "X-Role: admin"` 实变空值头, 返回误导性 401/403)——
   须写 python 脚本 scp 上去执行(urllib 正常)
4. **口径核查方法论**: 用户提出资金口径诉求时, 先核查数据流
   (哪些模块→哪个账户→哪个操作可动), 再补显示层——本次隔离机制
   本就正确, 缺口仅在总资产公式与前端展示
