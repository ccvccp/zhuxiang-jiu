## 〇、与代码回滚手册的关键差异(先读)

| 维度 | 代码类回滚(如 62号中文化) | 本例(数据清理回滚) |
|---|---|---|
| git revert | 可逆 | **不存在**——零代码改动 |
| 部署物 | scp+容器重建 | **无**——数据层操作 |
| 恢复方式 | revert 反向提交 | **重造数据**(重跑红队/API 重登记/Redis 直写) |
| 可逆性 | 完全可逆 | **近似可逆**——原 createdAt 元数据不可精确恢复(DEL 无快照) |

**红队基准源的本质**(考据 [nexus74_p5_service.py](file:///d:/网站架构设计/zhuxiang-jiu/backend/services/nexus74_p5_service.py#L444-L458)):
基准源由 P5 红队攻击运行时经 `_rt_source()` → `create_source()` **自动登记**——
每跑一轮红队自动创建 3 源, 生产残留的 12 条 = 4 轮验证 × 3 基准源。
**红队能力本体(规则/红线/运行档案/免疫态)未被清理, 零影响。**

## 一、回滚决策矩阵

| 触发场景 | 恢复路径 | 耗时 | 精度 |
|---|---|---|---|
| 需复跑红队验证(基准源是红队运行副产物) | **路径A: 重跑红队**(权威) | ~1 分钟 | 功能等效(新 id 16+) |
| 只要基准源素材, 不要红队运行记录 | **路径B: API 手工重登记** | ~3 分钟 | 内容精确/新 id |
| 须恢复原 id 2-14(对接旧记录) | **路径C: Redis 直写** | ~5 分钟 | 原 id+内容(时间戳近似) |

> 三路径共同点: **seq 发号器(source:seq=15)永不回退**——新登记续号 16+,
> 路径 C 直写旧 id(2-14 < 15)不与发号器冲突, 防未来 id 复用错乱。

## 五、路径C: Redis 直写(精确原 id)

适用: 须恢复原 id 2-14(如对接历史记录)。**编码红线**: 写入值须与
仓储序列化形态一致(五清单: int/bool/JSON 字段); 经本地文件走
`docker cp`/`redis-cli -x` 避免 PowerShell 引号与编码陷阱。

```bash
# ① 本地构造恢复 JSON(以 source 2 为例, 字段按清理前实测形态):

#   createdAt 用原值(有记录的)或登记时近似值。

# ② 写入(逐键 SET, 在生产 redis-cli 交互内执行最稳):
ssh root@47.236.61.117
docker exec -it zhuxiang-redis-1 redis-cli
> SET zhuxiang:nexus74:sources:2 '{"sourceId": 2, "title": "红队RT01 果酒好喝姐妹们冲", "body": "红队基准正文(违规话术)", "intent": "seeding", "intentLabel": "种草", "keywords": "[]", "hasImage": 0, "hasVideo": 0, "createdAt": "2026-09-13T10:53:23.908918+00:00"}'
```
