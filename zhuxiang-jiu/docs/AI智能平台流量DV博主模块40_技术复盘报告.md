## 二、节奏复盘：为什么一天能跑完六期

### 2.1 分期策略是第一生产力

P2 原设计是一个大阶段，实施前主动拆成 **P2a（防污染）/ P2b（进化）** 两批。事后看这个拆分是全程最重要的决策：

- P2a 先堵数据污染，P2b 的学习才有干净样本——**依赖排序正确**
- 若两批合并交付，质量门 bug 与进化 bug 会纠缠在同一批测试里，排查成本翻倍
- 每批 45 项专项独立验证，失败定位半径极小

> **可复用结论**：任何含"学习/数据回流"的模块，防污染层永远单独成批、先行交付。

### 2.2 复用决策的执行尺度

全程恪守"复用不合并"：36号通道、11号归因、37号存证、35号中枢、全局 ai_learning——只调用不搬代码。两处典型取舍：

- **层1 因子权重直接挂既有 Hedge 引擎**（第21档案），自建代码量≈0；引擎加 `reward` 字段时用"缺省回退 ±1"保住既有 21 个档案零影响——**改公共组件的纪律是向后兼容优先**
- **层2 博主权重没上学习器**：个体样本量撑不起在线学习，用可解释规则步进（±0.05 有界步长）——**样本量决定工程选型，不追技术先进性**

### 2.3 实机验收的时机

两次实机验收（P0 后一次、P2 后一次）而不是只在最后：第一次抓到"全局异常处理器错误格式与验收脚本预期不符"这类**只有真实容器才暴露的集成问题**，第二次时脚本口径已对齐，一次全绿。

## 三、踩坑记录（按教训价值排序）

### 坑 1：验收脚本把"端点不存在"误判为"数据为空" ⭐ 教训最深

**现象**：P2 实机验收中 `GET /api/blogger/follows/{id}` 返回 null，排查一小时。
**根因**：路由只定义了列表端点，FastAPI 把 `/follows/2` 匹配到列表路由吞掉了路径参数，返回的其实是列表结构——脚本 `.get("status")` 取到 None。
**教训**：
- 测试脚本断言失败时，**先验证请求到达了预期端点**（查响应结构/日志），再怀疑数据
- "设计文档没定义的端点"与"端点存在但行为异常"是两类问题，验收脚本应对 4xx/结构异常显式报错而非静默取空值

### 坑 2：文件编辑"成功"但未落盘

**现象**：批量修改测试类 `def run` → `async def run`，工具提示成功，重跑仍报 `TypeError: NoneType can't be used in 'await'`。
**根因**：与同终端沙箱写 `.pyc` 被拒的故障时间点重叠，部分编辑未持久化；`grep` 显示的是修改前内容，一度误导判断。
**教训**：**编辑工具的成功回执 ≠ 磁盘事实**，关键修改后应重新 grep 确认；跨多个工具/沙箱作业时，以文件系统为准。

### 坑 3：表名与存储初始化清单不一致（KeyError('accounts')）

**现象**：P3c 专项 7 个用例集体 KeyError。
**根因**：新表 `TABLE_ACCOUNTS = "accounts"`，但 `_ensure_store()` 初始化清单里写的是 `"blogger_accounts"`——通用 CRUD 直接 `store[table]` 取键，两边对不上。
**教训**：数据层新增表时，**表名常量与 `_ensure_store` 清单必须同一处 PR 内改**；更根本的改法是让 `_ensure_store` 直接遍历所有 `TABLE_*` 类属性（本模块未做，记为改进项）。

### 坑 4：三审闸门直接复用导致评论场景误判

**现象**：评论区截流回复生成后被判 65 分（缺出处声明），无法自动通过。
**根因**：直接借用了跟随内容的 `compliance_gate`——但评论场景**没有 @原作者/出处语义**，硬套反成误杀。
**教训**：**复用前先过"语义适配"关**：合规检查的每条规则要问"这个场景下该规则成立吗"。后来为评论写了独立 gate（保留酒类广告法硬词，去掉出处检查），问题消解。类似的还有年龄提示词面口径（"未成年人" vs REQUIRED_AGE_TIP 的 "18"）——**校验与模板必须同源同词面**。

### 坑 5：测试自身的三类口径错误（非生产问题但耗时）

- 断言未考虑 clamp 语义（base=1.0 时 +0.05 被 clamp 掩盖，应换低权重博主或按 clamp 后期望断言）
- 测试数据构造与设计行为耦合（探测博主置顶改变了决策顺序、效率调制改变了步长期望）——**设计行为变更后，旧测试的"合理假设"需要重新审视**，这类失败每次都值得确认是"实现错"还是"测试假设过期"
- Mock 时间/槽位依赖（同槽位内单博主作品数不足以构造 3 份连续零引流）——改用直测内部方法绕开高成本链路构造

### 坑 6：环境与工具链摩擦（低价值损耗）

PowerShell 引号/heredoc 限制导致内联 python 脚本两次失败（改落临时脚本文件）、`docker compose` 中文目录名推导项目名失败（需 `-p zhuxiang-jiu`）、重跑验收前必须清理 Redis 残留（三限基于上次发布时间，残留数据会让全新一轮被旧间隔拦截——**这本身验证了三限的正确性，但验收脚本应内置清理步骤**）。

## 五、量化观察

- **测试投入比**：七套专项（356 项）约占交付时间 35%——但三次真实缺陷捕获（雷达 paused 过滤/冻结分支变量/表名不一致）全部来自专项，**ROI 直接可算**：这三个缺陷若逃逸到实机或线上，任一个的排查成本都超过全部测试编写时间
- **实机验收第二次全绿的边际成本极低**：因为第一次（P0 后）就把容器口径差异（错误响应格式/直达地址/清理流程）趟平了
- **每批"专项+回归+提交"的固定节奏**让 14 个 commit 没有一个处于"不可回退"状态——中途任何时刻可安全 ship

## 六、给下个模块的行动清单

**流程类（立即生效）**
1. 数据层新表：表名常量与 `_ensure_store` 同步修改；建议后续统一改为遍历 `TABLE_*` 属性自动初始化（消灭坑 3 这一类）
2. 验收脚本模板化：内置 Redis 前置清理 + "响应结构与预期端点一致"前置断言（消灭坑 1/坑 6 残留）
3. 含学习回流的模块：防污染层单独成批先行（P2a 模式固化为惯例）
4. 关键编辑后重新 grep 验证落盘（工具链纪律）

**设计类（进入设计文档模板）**
5. 公共组件（引擎/仓储/闸门）改动必须"缺省回退旧行为"，在 PR 描述中显式声明兼容口径
6. 合规/校验规则复用时逐条过"场景语义适配"清单（出处/署名/年龄词面等）
7. 进化类变量一律"有界步长 + clamp + 可回滚 + 健康熔断"四件套

**技术债（登记待还）**
8. `BloggerService` 已达 1700+ 行，下个迭代考虑按"编排/进化/健康"拆分（当前不拆的理由：方法间共享状态多，拆分收益低于风险）
9. 跟随内容"单作品仅1条"护栏目前靠全表扫描 `find_comment_by_target`，量大后需加索引键
10. 评论区截流归因尚未回流层2（仅 failStreak），设计已预留

## 七、结语

40号最有价值的产出不是 33 个端点，而是验证了一条可复制的交付路径：

**设计冻结（含分期依赖排序）→ Mock-first 骨架 → 每批"专项+全量回归+实机抽查"→ 真实化只加开关 → 验收脚本沉淀为资产 → 复盘反哺下个模块。**

速度来自不返工，不返工来自每一步都有证据。
