# 并发锁实施规范

> 面向开发人员的 Mutex 锁实操规范。基于 inventory-service / checkout-service / agent-upgrade-service 的落地经验整理。
> 原理详见 [并发控制与事务一致性技术文档](并发控制与事务一致性技术文档.md)，超时/防重入详见 [超时竞争与防重入机制技术设计文档](超时竞争与防重入机制技术设计文档.md)。

---

## 1. 适用范围与目标

### 1.1 适用范围

本规范适用于所有涉及**共享状态读写**的操作，包括但不限于：

- 库存扣减/回补（防超卖）
- 订单号生成（防重复）
- 优惠券核销（防重复使用）
- 积分扣减（防超扣）
- 钱包额度更新（防 lost-update）
- 代理商升级/降级事务（防并发覆盖）
- 任何需要串行化的临界区

### 1.2 目标

- **统一加锁模式**：所有 Mutex 使用一致的模式，降低维护成本
- **防止已知并发 Bug**：lost-update、超卖、死锁、锁不释放
- **可追溯**：每个锁 key 有明确的资源语义，便于排查

## 2. 何时需要加锁（判定准则）

### 2.1 决策树

```
操作是否涉及共享状态读写(DB/内存共享对象)?
├─ 否 → 不需要锁
└─ 是 → 是否多个并发请求可能操作同一资源?
    ├─ 否(单线程/无并发) → 不需要锁
    └─ 是 → 操作是否"读后写"(SELECT 后 UPDATE)?
        ├─ 是 → 必须加锁(lost-update 高风险)
        └─ 否(直接 UPDATE) → 是否同一行被并发更新?
            ├─ 是 → 必须加锁(覆盖风险)
            └─ 否(INSERT 新行) → 不需要锁
```

### 2.2 必须加锁的场景

| 场景 | 风险 | 示例 |
|------|------|------|
| 读后写(SELECT+UPDATE) | 读陈旧快照+覆盖 | 返利重算(阶段6) |
| 同一行并发 UPDATE | last-write-wins | agents 表并发升级 |
| 计数器递增 | 丢失更新 | 订单号 Date.now 毫秒级并发 |
| 状态机转换 | 非法中间态 | 优惠券 已核销→已核销 |

### 2.3 不需要加锁的场景

| 场景 | 原因 |
|------|------|
| INSERT 新行 | 新行无冲突 |
| 纯计算函数(无 DB 写入) | 无共享状态 |
| 单线程顺序执行的操作 | 无并发 |

## 3. 锁 key 命名规范

### 3.1 命名格式

```
{资源类型}:{资源标识符}
```

- 资源类型：小写英文，复数或单数均可，保持模块内一致
- 资源标识符：业务主键(id/code/level 等)

### 3.2 已落地的 key 清单

| 资源类型 | key 格式 | 示例 | 所在文件 |
|----------|----------|------|----------|
| 库存 | `stock:{productId}` | `stock:2` | inventory-service.js |
| 订单号 | `order:next` | `order:next` | checkout-service.js |
| 优惠券 | `coupon:{couponCode}` | `coupon:NEWYEAR2026` | checkout-service.js |
| 积分 | `points:{memberLevel}` | `points:L4` | checkout-service.js |
| 钱包额度 | `wallet:{agentId}` | `wallet:1` | main.js + agent-upgrade-service.js |
| 代理商事务 | `agent:{agentId}` | `agent:1` | agent-upgrade-service.js |

### 3.3 命名红线

- ❌ 禁止用 `lock1`/`mutex`/`global` 等无语义 key
- ❌ 禁止 deduct 用 `stock:{id}` 而 restock 用 `inventory:{id}`(不一致导致不互斥)
- ✅ 同一资源的所有操作必须用**完全相同**的 key

## 4. 三种加锁模式

### 4.1 模式 A：单锁（withLock）

适用：操作单一资源。

```js
await window.mutex.withLock('stock:' + productId, async () => {
    // 临界区：读+写同一资源
    const dbRef = { db: readDB() };  // dbRef 必须在锁内创建
    // ... 扣减/回补逻辑 ...
});
```

**实例**：inventory-service.js 的 deduct/restock

### 4.2 模式 B：多锁（withLocks）

适用：一个事务涉及多个资源，需同时持有多个锁。

```js
const lockKeys = ['order:next'];
if (couponCode) lockKeys.push('coupon:' + couponCode);
if (points && points > 0) lockKeys.push('points:' + (memberLevel || 'default'));

const result = await window.mutex.withLocks(lockKeys, async () => {
    const dbRef = { db: readDB() };  // 锁内创建
    const adapter = createAdapter(dbRef);
    const template = new Template({ name: 'checkout', adapter: adapter });
    return await template.run({ ... });
});
```

**要点**：
- `withLocks` 自动按 key **升序获取、反向释放**，避免死锁
- lockKeys 根据参数**动态生成**（无优惠券则不加 coupon 锁）

**实例**：checkout-service.js 的 submit

### 4.3 模式 C：事务入口锁（withLock 包裹整个事务）

适用：一个事务有多个阶段都更新同一主体的不同表，用主体级锁包裹整个事务。

```js
const result = await window.mutex.withLock('agent:' + agentId, async () => {
    const template = new TransactionTemplate({ name: 'agent_upgrade', adapter: dbAdapter });
    return await template.run({
        context: { agentId, ... },
        preflight: [...],
        stages: [
            // 阶段3: UPDATE agents
            // 阶段5: UPDATE orders
            // 阶段6: SELECT+UPDATE rebates
            // 阶段7: UPDATE credit_scores
            // 阶段9: UPDATE compliance_monitors
        ],
        asyncTasks: [...],
    });
});
// 结果形状转换在锁外(无需保护)
if (result.success) { ... }
```

**要点**：
- 事务入口加一个**主体级锁**，覆盖所有阶段的 UPDATE
- 结果形状转换（纯内存操作）在锁外，减少锁持有时间
- 与细粒度锁（如 `wallet:{agentId}`）互补：主体锁保护整体，细粒度锁保护子操作

**实例**：agent-upgrade-service.js 的 upgradeAgent / downgradeAgent

## 5. 实施检查清单

加锁时逐项确认：

- [ ] **key 语义化**：lock key 包含资源类型 + 标识符（如 `stock:2` 非 `lock1`）
- [ ] **key 一致性**：同一资源的所有操作用完全相同的 key（deduct/restock 一致）
- [ ] **dbRef 在锁内创建**：`const dbRef = { db: readDB() }` 在 withLock/withLocks 回调**内**，不在锁外
- [ ] **锁释放保证**：用 `withLock/withLocks`（自动释放）或 `try { ... } finally { release() }`
- [ ] **多锁升序**：用 `withLocks`（内置升序获取+反向释放），不要手动 acquire 多锁
- [ ] **async/await 正确**：`return await fn()` 不能漏 `await`（否则 finally 提前释放锁）
- [ ] **INSERT 不加锁**：新增行无需锁，只对 UPDATE/读后写加锁
- [ ] **结果转换在锁外**：事务入口锁只包裹 template.run，结果转换在锁外
- [ ] **无嵌套同 key 锁**：避免 `withLock('agent:1', () => withLock('agent:1', ...))` 死锁
- [ ] **锁契约命名**：跨服务被持锁调用方复用的方法须提供 `*_locked` 版本（详见 §11），临界区内禁止调用同一资源的自动加锁方法

## 6. 常见错误案例

### 6.1 ❌ dbRef 在锁外创建（lost-update）

```js
// 错误：dbRef 在锁外创建，所有并发事务读到同一陈旧快照
const dbRef = { db: readDB() };
const result = await _withMutex(lockKeys, () => template.run({ ... }));
```

**症状**：N 次并发操作只生效 1 次，tx_log 只剩 1 BEGIN+1 COMMIT。

**修复**：把 dbRef 创建移进锁回调内。

```js
// 正确：加锁后才 readDB
const result = await _withMutex(lockKeys, () => {
    const dbRef = { db: readDB() };
    const template = new Template({ ... });
    return template.run({ ... });
});
```

### 6.2 ❌ 漏 await（锁提前释放）

```js
// 错误：return fn() 漏 await，finally 立即执行释放锁
async _withMutex(keys, fn) {
    // ... acquire ...
    try { return fn(); }  // ← 漏 await
    finally { release(); }
}
```

**修复**：必须 `return await fn()`。

### 6.3 ❌ 锁 key 不一致（不互斥）

```js
// 错误：deduct 用 stock:{id}，restock 用 inventory:{id}
deduct:   await mutex.withLock('stock:' + pid, ...);
restock:  await mutex.withLock('inventory:' + pid, ...);
```

**症状**：扣减和回补不互斥，可能超卖。

**修复**：统一用 `stock:{pid}`。

### 6.4 ❌ rollback 丢 BEGIN（事务原子性破坏）

```js
// 错误：先取快照后 push BEGIN，快照不含 BEGIN
begin(ctx) {
    const snapshot = JSON.parse(JSON.stringify(dbRef.db));
    dbRef.db.tx_log.push({ type: 'BEGIN' });  // 快照不含此行
    return snapshot;
}
```

**症状**：rollback 恢复后 BEGIN 丢失，`begins !== commits + rollbacks`。

**修复**：先 push BEGIN 再取快照。

```js
begin(ctx) {
    dbRef.db.tx_log.push({ type: 'BEGIN', time: new Date().toISOString() });
    const snapshot = JSON.parse(JSON.stringify(dbRef.db));  // 含 BEGIN
    return snapshot;
}
```

### 6.5 ❌ 跨服务锁重入（asyncio.Lock 自死锁，2026-08-29 实录）

```python
# 错误：grab_ticket 已持有 ticket:transition:{ticket_no} 锁,
# 又调用 assign_ticket(内部经 _transition 再次 get_lock 同一 key)
async def grab_ticket(self, ticket_no, cs_user_id):
    async with get_lock(f"ticket:transition:{ticket_no}"):
        ...
        await self.ticket_service.assign_ticket(ticket_no, cs_user_id)  # ← 自死锁
```

**症状**：协程永久挂起（await 不返回），无报错、无超时，接口 100% 卡死。
**根因**：asyncio.Lock（及 Redis 分布式锁）**不可重入**，同一协程二次 acquire
同一 key 直接死锁。
**修复**：按 §11 锁契约，为被持锁调用的方法提供 `*_locked` 版本。

```python
# 正确：持锁后调用锁内直改版
async def grab_ticket(self, ticket_no, cs_user_id):
    async with get_lock(f"ticket:transition:{ticket_no}"):
        ...
        await self.ticket_service.assign_ticket_locked(ticket_no, cs_user_id, "抢单")
```

## 9. 与防重入/超时的关系

| 机制 | 层级 | 作用 | 文件 |
|------|------|------|------|
| Mutex 锁 | 资源级 | 防并发 lost-update/超卖 | mutex.js |
| _submitInFlight 防重入 | 全局 | 防连点重复提交 | checkout-service.js |
| request 超时竞争 | 请求级 | 防网络挂起导致重复点击 | env-adapter.js |

**协同链**：防重入拦截连点 → Mutex 锁串行化资源 → 超时竞争快速失败 → try/catch 兜底。

三者互补，**不可相互替代**：
- 防重入防"同一入口连点"，但防不了"跨入口并发"
- Mutex 防"资源并发竞争"，但防不了"网络挂起"
- 超时防"网络挂起"，但防不了"资源竞争"

## 10. 新模块加锁流程

为新模块/新操作加锁时，按以下流程：

1. **判定是否需要锁**：用 §2.1 决策树
2. **选择锁 key**：用 §3 命名规范，查 §8 确认无冲突
3. **选择加锁模式**：单资源用 A，多资源用 B，整个事务用 C
4. **实施**：参照 §4 代码模板，dbRef 在锁内创建
5. **自查**：用 §5 检查清单逐项确认
6. **验证**：用 §7 运行回归 + 并发测试
7. **更新文档**：在 §8 已落地清单追加一行

## 11. 锁契约显式化（2026-08-29 补充）

> 背景：AI 智能管理模块 P2 阶段实现抢单模式时，`role_service.grab_ticket` 已持有
> `ticket:transition:{ticket_no}` 锁后又调用 `ticket_service.assign_ticket`，
> 后者内部再次 `get_lock` 同一 key —— **asyncio.Lock 不可重入**，协程自死锁。
> 由此确立服务间锁契约命名规范，把"是否已持锁"从隐式约定升级为方法签名的一部分。

### 11.1 锁契约命名规范

为避免跨服务调用时的锁嵌套死锁（asyncio.Lock / Redis 分布式锁均**不可重入**），
所有涉及锁的方法必须按以下规则命名：

| 方法名后缀 | 含义 | 调用方责任 |
|---|---|---|
| `*_locked` | **锁内直改方法**：内部**不**获取锁，要求调用方已持有对应资源锁 | 必须在持锁状态下调用，且确保锁 key 与方法所需资源完全一致 |
| 无特殊后缀 | **自动加锁方法**：内部会自动获取资源锁 | 可直接调用；但**不得**在已持有该资源锁时调用（死锁） |

### 11.2 示例（backend/services/ticket_service.py）

```python
async def assign_ticket(self, ticket_no: str, handler_id: int,
                        handler_name: str = "") -> dict:
    """自动加锁版分配（内部经 _transition 获取 ticket:transition:{ticket_no} 锁）"""
    return await self._transition(
        ticket_no, TICKET_STATUS_PROCESSING,
        extra={"handlerId": handler_id, "handlerName": handler_name,
               "assignedAt": ts()},
        log_action="assign", log_detail=f"分配客服({handler_name or handler_id})")

async def assign_ticket_locked(self, ticket_no: str, handler_id: int,
                               handler_name: str = "") -> dict:
    """锁内直改版分配(调用方须已持有 ticket:transition:{ticket_no} 锁)

    供抢单等已持锁场景使用, 避免不可重入锁死锁。
    """
    ticket = await self._get_or_404(ticket_no)
    if TICKET_STATUS_PROCESSING not in STATUS_TRANSITIONS.get(
            ticket["status"], set()):
        raise ValueError(f"工单状态流转非法({ticket['status']} → "
                         f"{TICKET_STATUS_PROCESSING})")
    # 直接更新状态, 不获取锁(调用方已持有)
    updates = {"status": TICKET_STATUS_PROCESSING,
               "handlerId": handler_id, "handlerName": handler_name,
               "assignedAt": ts(), "updatedAt": ts()}
    await self.repo.update_ticket(ticket_no, updates)
    ticket.update(updates)
    return self._public(ticket)
```

### 11.3 调用方检查清单

| 调用场景 | 必须确认 |
|---|---|
| 调用 `*_locked` 方法 | 1. 已通过 `get_lock` 获取对应 key 的锁<br>2. 锁 key 与方法所需资源完全一致<br>3. 临界区内不再调用该资源的自动加锁方法 |
| 调用普通方法（自动加锁） | 1. 当前**未**持有该资源的锁（否则死锁）<br>2. 接受方法内部自动加锁的性能开销 |

### 11.4 已落地方法清单

| 服务 | 方法 | 类型 | 锁 key 格式 | 说明 |
|---|---|---|---|---|
| ticket_service | assign_ticket | 自动加锁 | `ticket:transition:{ticket_no}` | 经 `_transition` 统一加锁 |
| ticket_service | assign_ticket_locked | 锁内直改 | `ticket:transition:{ticket_no}` | 供已持锁场景调用 |
| role_service | grab_ticket | 外层自动加锁 + 锁内调 `*_locked` | `ticket:transition:{ticket_no}` | 持锁校验资格后调 `assign_ticket_locked` |
| role_service | settle_ticket / settle_worker_batch | 自动加锁 | `role:settle:{ticket_no}` / `role:worker-settle:{batch_no}` | 结算主体级锁 |
| role_service | claim_role / dispatch_session | 自动加锁 | `role:sign:{claim_id}` / `role:dispatch:{sessionId}` | 认领/派单防并发 |
| attract_service | 短码创建 / 注册归并 / ROI 再分配 | 自动加锁 | `attract:shortcode:{code}` / `attract:merge:{click_id}` / `attract:rebalance` | 引流模块三级锁 |

### 11.5 新增服务方法的锁契约决策树

```
方法是否会被"已持锁"的调用方调用?
├─ 否 → 只提供自动加锁版(无后缀), 内部 get_lock
└─ 是(如抢单/批处理等组合场景) → 提供两个版本:
    ├─ 无后缀版: 内部 get_lock, 供独立调用方使用
    └─ *_locked 版: 不加锁, 供持锁调用方在临界区内使用
    └─ 两版本必须共用同一内部实现逻辑, 避免规则漂移
```

**红线**：
- ❌ 禁止在持锁临界区内调用同一资源的自动加锁方法（asyncio.Lock 不可重入 → 自死锁）
- ❌ 禁止 `*_locked` 方法内部再 `get_lock`（契约破坏）
- ✅ `*_locked` 方法 docstring 必须注明所依赖的锁 key 格式

## 附录：Mutex API 速查

```js
// 单锁(自动释放)
await window.mutex.withLock(key, async () => { ... });

// 多锁(升序获取,反向释放,自动释放)
await window.mutex.withLocks([key1, key2], async () => { ... });

// 手动获取/释放(需 try/finally)
const release = await window.mutex.acquire(key);
```
