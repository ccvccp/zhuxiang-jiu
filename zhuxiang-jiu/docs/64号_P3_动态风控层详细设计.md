## 一、定位与目标

P3 是 64号的**经济免疫系统**——在 P0 刚性规则（宪法层）与 P1 结算引擎（流通层）之上，对"**规则合法但行为异常**"的模式做确定性识别：

| 层 | 回答的问题 | 手段 |
|----|-----------|------|
| P0 刚性规则 | 这笔交易**合法吗**（30/20/40/非负） | 单笔校验·拦截 |
| P1 结算引擎 | 这笔交易**账实相符吗**（原子转移/双花） | 事务·借贷对 |
| **P3 动态风控** | 这批交易**像不像在攻击经济系统**（四防） | **跨笔模式识别·分级处置** |

**QC 铁律（本层最高约束）**：预警仅建议、不自动处置——检测器可阻断**当前这一笔**交易（交易级、可申诉、与 P1 precheck 同性质），但**惩罚性处置**（tier 降档/商品下架/兑换冷却/账户冻结）**永远只输出建议**，执行必须经人工或 46号审批总线。

**三层输出语义（关键设计——调和"拦截"与"仅建议"）**：

| 输出 | 性质 | 触发时机 | 可逆性 |
|------|------|---------|--------|
| ① 决策面拦截 | 自动（交易级） | pay/exchange 同步前置 | 可申诉（P4 通道）秒级解冻 |
| ② 风险事件落库 | 自动（观测面） | 任意检测命中 | 人工复核可 dismissed |
| ③ 处置建议 | **永不自动执行** | 中/高风险命中 | 人工/46号审批后生效 |

## 三、五防检测器详细设计

全部检测器遵循统一契约：**纯函数式只读扫描 → 命中输出 finding（含全部命中指标，数字可溯源）**。同输入同输出（确定性），不引入 LLM/GNN/随机性。

### 3.1 ARB-HF 套利-高频小额检测器

| 项 | 内容 |
|----|------|
| 攻击模型 | RT-02 拆单绕限——多笔小额兑换压低基数绕过 R4/R5 |
| 数据源 | `xx64_orders`（buyerId 过滤，24h 窗口，态 ∈ paid/settled/completed）+ 当前余额（45号只读） |
| 判定（双条件同时满足） | ① 24h 兑换笔数 ≥ `ARB_HF_MIN_ORDERS`（默认 **10**）；② 24h 累计 trustValue > 单次限额 × `ARB_HF_MULTIPLE`（默认 **3**，即当前余额×20%×3） |
| severity | medium |
| 处置 | 标记 + 下笔增强验证（决策面对该买家下一笔 pay 前置增强校验） |
| 建议书 | 建议人工关注该买家窗口用量与 R5 基准快照序列（是否人为压基数） |

```python
# 算法骨架（确定性）
async def detect_arb_hf(buyer_id: int) -> finding | None:
    orders_24h = await repo.list_orders(
        buyer_id, since=now-24h,
        states=("paid", "settled", "completed"))
    count = len(orders_24h)
    total_tv = round(sum(o["trustValue"]
                         for o in orders_24h), 2)
    balance = await get_trust_balance(buyer_id)
    quota_x3 = round(single_quota(balance)
                     * ARB_HF_MULTIPLE, 2)
    if count >= ARB_HF_MIN_ORDERS \
            and total_tv > quota_x3:
        return {
            "detector": "ARB-HF",
            "severity": "medium",
            "detail": {
                "orderCount": count,
                "trustTotal": total_tv,
                "quotaX3": quota_x3,   # 可溯源
            },
            ...
    return None
```

**边界语义**：恰好 10 笔命中（≥10）、恰好 9 笔不命中；总额恰好等于 quota×3 不命中（严格大于）。

### 3.2 ARB-MA 套利-多账号集中检测器

| 项 | 内容 |
|----|------|
| 攻击模型 | 多账号矩阵对同一商品/卖方集中兑换（洗钱/刷量） |
| 数据源 | `xx64_orders`（按 productId 或 sellerId 过滤，1h 窗口） |
| 判定（双维度独立触发） | ① 同商品 1h 内 ≥ `ARB_MA_MIN_ACCOUNTS`（默认 **5**）个不同 buyerId；② 同卖方 1h 内 ≥ 5 个不同 buyerId 且非同商品（弱信号，severity 降半档） |
| severity | high（同商品）/ medium（同卖方） |
| 处置 | 阻断当前笔（决策面）+ 冻结待审（订单转 `disputed` 态进入人工队列） |
| 建议书 | 建议人工核查 5+ 账号关联性（同 IP/同设备属 47号职权——64号仅提供账号清单） |

**注意**：本检测器是唯一"自动阻断"级别为 high 的入口——因为其命中即意味着**正在进行中的攻击**（而非历史模式）；且阻断的是"当前这一笔"（可申诉解冻），矩阵处置仍属建议。

### 3.3 PTS-SHOCK 积分冲击检测器

| 项 | 内容 |
|----|------|
| 攻击模型 | RT-03 积分套利——大额/持续积分兑换冲击信值供给 |
| 数据源 | `xx64_points_exchange`（trustId 过滤，态 ∈ pending/credited） |
| 判定（三信号任一命中） | ① **量级**：24h 兑换信值等值 ≥ `PTS_SHOCK_MAX_TRUST`（默认 **1000** 信值 = 100000 积分）；② **持续高频**：连续 ≥3 日每日兑换次数 ≥ `POINTS_DAILY_LIMIT`（3 次）的 80%（即 ≥2.4→取整 3？——见下方边界说明）；③ **频率**：单日尝试次数（含被 P1 拒绝的）≥5 次即视为探测行为 |
| severity | ①量级=high ②持续=medium ③探测=medium |
| 处置 | ①量级命中：**拦截当笔兑换**（决策面）+ 建议冻结该账户积分入口待人工；②③：标记+增强验证 |
| 建议书 | 建议 47号 tier 降档联动（**经 46号 submit——不直改 47号**） |

**边界说明（信号②的确定性口径）**：连续 3 日每日满频（3/3/3）为命中；每日 2 次×3 日不命中（P1 限频是 3，80% 即 2.4，向下取整 2 不构成"持续高频"——避免误伤正常活跃用户）。信号③从 `xx64_events` 中统计当日 `points_exchange_rejected` 事件。

### 3.4 PRICE-MANIP 价格操纵检测器

| 项 | 内容 |
|----|------|
| 攻击模型 | RT-04 提价套信值——卖方提价 20%+ 后买家（同伙）信值支付，30% 信值抵扣放大提价收益 |
| 数据源 | `xx64_orders`（同 product 的价格快照轨迹，7 日窗口，态 ∈ paid/settled/completed） |
| 判定（双条件同时满足） | ① 商品现金价 7 日涨幅 > `PRICE_MANIP_MAX_DRIFT`（默认 **20%**）——口径：近 7 日均价 vs 前 7 日均价（避免单点噪声）；② 该商品存在叠加信值支付的订单（trustValue > 0） |
| severity | medium |
| 处置 | 标记（商品级风险画像） |
| 建议书 | **商品下架建议+告警**（仅建议——人工/46号决策；64号无下架权） |

**价格口径细节**：均价 = 窗口内该商品全部已支付订单 price 的算术平均；样本 <3 笔时降级为"样本不足"不判定（防冷启动误报——对齐 60号 anomaly 冷启动铁律）。

### 3.5 LIQ-CRUNCH 流动性推演检测器

| 项 | 内容 |
|----|------|
| 攻击模型 | 全站信值消耗速率失控（挤兑前兆） |
| 数据源 | `xx64_ledger`（全站 24h debit 总额）+ 45号全站信值总量（只读） |
| 判定 | 消耗速率 = 近 24h debit 总额 / 24（信值/小时）；线性推演 24h 消耗量 ≥ 全站总信值 × `LIQ_CRUNCH_RATIO`（默认 **40%**） |
| severity | high（但**处置仅建议**——全局性动作不可自动） |
| 处置 | 无自动动作（纯观测） |
| 建议书 | **兑换冷却建议**（如"建议 24h 冷却窗"）——**仅建议——人工/46号决策**（计划 §4.3 原文铁律） |

**唯一零拦截的 high 检测器**：流动性处置影响全体用户，属全局经济决策——权限在人工/46号，64号只提供推演数字（消耗速率/推演触线时间点/建议冷却时长）。

## 四、分级处置引擎

### 4.1 风险分（确定性加权）

```python
SEVERITY_WEIGHT = {
    "low": 20, "medium": 45, "high": 75,
}

def risk_score(findings: list[dict],
               tier: str) -> int:
    base = sum(
        SEVERITY_WEIGHT[f["severity"]]
        for f in findings)
    # 多检测器叠加：+10/额外命中
    base += 10 * max(0, len(findings) - 1)
    # tier 修正（摩擦与信任成反比铁律）
    base *= TIER_FRICTION[tier]  # 见下表
    return clamp(round(base), 0, 100)
```

### 4.2 tier 修正表（47号联动——纯读取）

| 47号 tier | 摩擦系数 | 语义 |
|-----------|---------|------|
| diamond/platinum | ×0.6 | 高信用户中风险降档处理（增强验证豁免） |
| gold | ×0.8 | 轻度豁免 |
| silver | ×1.0 | 基准 |
| bronze/watch | ×1.2 | 敏感人群加严 |

**铁律**：tier 只做**摩擦修正**（同 PAY60"支付摩擦与信任成反比"），**high 级检测器命中不可被 tier 豁免阻断**（如 ARB-MA 同商品 5 账号——tier 再高也阻断当前笔，仅豁免"增强验证"类摩擦）。

### 4.3 三档处置矩阵

| 档位 | 阈值 | 自动动作（交易级） | 建议书（仅建议） |
|------|------|-------------------|------------------|
| 低 | <40 | 无（直通） | 无 |
| 中 | 40-69 | 标记 + 下笔增强验证 | 人工关注建议 |
| 高 | ≥70 | 阻断当前笔 + 订单转 `disputed` 冻结待审 | tier 降档/下架/冷却/账户处置建议 → 人工/46号 |

处置结果全部落 `xx64_risk`（status=open）+ `xx64_events`（source=risk）留痕；人工复核后 status → confirmed/dismissed（复核人+时间+理由）。

## 六、API 设计（累计 16 端点）

| # | 端点 | 面 | 说明 |
|---|------|-----|------|
| 15 | `GET /risk/status` | 观测（member/admin） | 用户风险画像：当前风险分+tier 摩擦档+近 30 日命中事件+处置状态 |
| 16 | `POST /risk/scan` | 管理（admin，off 409） | 手动全量五防扫描：返回各检测器命中统计+新增 risk 事件数 |

**鉴权**：status 面向 member（自查）/admin（管理）；scan 仅 admin。
**异常映射**：KeyError→404 / ValueError→409（沿用统一口径）。
**观测面**：GET status 不受 XX64_MODE 影响；scan 为决策面（off 拒绝——与计划"决策面 off=409"口径一致）。

## 七、触发链路

| 链路 | 时机 | 范围 | 说明 |
|------|------|------|------|
| **同步前置** | `pay_order` / `points.exchange` 决策面入口（P1 服务内调用） | 单用户轻量三查：ARB-HF+PTS-SHOCK+ARB-MA（该用户维度） | 命中 high → 抛 ValueError（409 结构化原因含 riskId）；命中 medium → 响应附 `enhancedVerify` 标记（不阻断） |
| **异步扫描** | `POST /risk/scan`（手动） | 全量五防（全站维度） | 扫描只落事件+建议书，**不阻断任何已成立交易** |
| **回溯复核** | GET /risk/status（按需实时算） | 单用户五防（除 LIQ-CRUNCH） | 观测面实时计算当前画像 |

**性能约束**：同步三查均基于单用户键域索引查询（orders/points 按 buyerId/trustId 过滤），单次 <50ms；LIQ-CRUNCH 仅在手动 scan 中执行（全站聚合不进同步链路）。

**幂等**：scan 对同一 (detectorCode, entityType, entityId, 24h 窗口) 已有 open 事件不重复落库（dedupe by 窗口指纹）。

## 八、铁律与边界（零改动宪法）

| 铁律 | 本设计的落实 |
|------|-------------|
| 预警仅建议不自动处置（QC） | §二三层输出语义：惩罚性处置永不自动——tier 降档/下架/冷却/账户冻结全部走建议书→人工/46号 |
| 确定性检测（非 GNN/非 LLM） | 五检测器全为阈值+窗口聚合纯函数；同输入同输出；LLM 不进判定链 |
| 47号零改动 | tier 经 `trust_risk_profile_service.tier_of` 纯读取（与 PAY60 同范式） |
| 45号零改动 | 全站信值总量经既有 profile 接口只读 |
| 46号零改动 | 处置建议经 `ai_governance_service.submit_change` 提交审批（建议书的唯一执行轨） |
| 44号零改动 | risk 命中信号 → 第38档案 `arbitrage_blocked` 因子回流在 **P4**（本期仅落 xx64_events 留痕） |
| 两账分离 | 风控只读账本（xx64_ledger）+ 只读总账（45号）——不写任何余额 |
| 申诉通道 | 被阻断交易可经 P4 申诉通道秒级复核（本期 risk 事件 status 字段预留 dismissed 态） |
