## 二、逐一精审定性（证据驱动）

### 位置 1：drama84_routes.py:156 `_drama76_stats` —— **误报**

- 触发证据：块内 177 行 `for d in await svc._list_all():`（剧反查循环）+
  205 行 `logger.info("drama84_stats_skip: %s", exc)`
- 精审：logger 位于 **except 兜底路径**（fail-soft 设计，docstring 明示
  "无关联剧/无记录 → (0, 1.0) fail-soft 不阻断评分"），**非循环内**，
  单条异常日志恰是合规写法
- 定性：**误报**——块级正则不校验"日志在循环内"（粒度近似，已知局限）

### 位置 2：xiaozhu_routes.py:345 `_wake_hot` —— **误报（块边界过宽）**

- 触发证据：`_wake_hot` 本体（345-356 行）仅列表推导去重（行首非 for），
  无任何日志；命中源于 def 块按行扫描**无缩进感知**，块边界延伸至后续
  外层代码（371 行 `logger.info` 系诊断开关 `XIAOZHU_WS_DUMP=1` 内单次输出）
- 精审：被指控的函数本体既无 for 语句也无循环内日志；命中的日志在
  **另一个语义层**（ws_asr 端点处理逻辑），且常态关闭零开销
- 定性：**误报**——def 块边界近似（嵌套/闭包场景边界过宽），Fast Filter
  已知局限的典型样本

### 位置 3：locks.py:116 `_cleanup_async_locks` —— **误报**

- 触发证据：块内 123 行 `for k in to_remove: del _async_locks[k]`（真循环）+
  126 行 `logger.debug("清理 asyncio 锁缓存: 移除 %d 个未持有的锁", ...)`
- 精审：logger.debug 位于**循环结束后 if 守卫内单条聚合输出**——恰是
  AP-5 建议的"聚合一条"最佳实践形态；且该函数仅在锁缓存达上限时触发
  （低频清理路径），debug 级别
- 定性：**误报**——代码写法与 AP-5 整改建议完全一致

### 位置 4：module_guard.py:228 `full_guard` —— **语义豁免（人工裁量）**

- 触发证据：块内 236 行 `for mid in result["hits"]:` 循环内多处 print
  （238/243/247/252 行——回归套件结果/静态守卫/指纹漂移逐模块报告）
- 精审：这是**部署预检 CLI 主入口**（竹医部署门）——hits 为变更命中的
  模块清单（通常 1-3 个），print 系**控制台报告输出**（设计意图即逐模块
  打印判定明细），非运行时日志，无风暴风险
- 定性：**语义豁免**——管理面报告输出，非 AP-5 所指运行时高频日志；
  保留现状不改

## 四、规则改进建议（只出不施——供竹演后续迭代裁量）

1. **AP-5 块级正则收紧**：现口径"def 块内任意 for + 任意日志即报"，
   建议升级为"日志调用位于 for/while 块缩进区间内"（缩进感知），
   可消除位置 1/2/3 三类误报
2. **def 块边界缩进感知**：现 `_def_blocks` 按行扫描至下一 def 行，
   嵌套 def/闭包场景边界过宽（位置 2 样本），建议按 Python 缩进层级切割
3. **print 豁免通道**：CLI 管理面（部署预检/报告输出）可按文件级
   豁免标记（如模块 docstring 声明 `# zhuyan-exempt: cli-report`）

> 上述建议不改变 B4 基准结论（五类触发例拦截 5/5、干净样本零误报——
> B4 样本均为单函数粒度，块边界局限仅在真实多函数大文件暴露）。
