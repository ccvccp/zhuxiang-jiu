## 二、检查过程与取证误报四课（本报告自身的方法论沉淀）

本次检查连环踩了四个取证误报，全部当场纠正——**"取证的取证"也要复核**：

| # | 误报 | 真相 | 教训 |
|---|---|---|---|
| 1 | curl 首页 grep 'v72-variant' = 0 → 判"变体未注入" | gzip 压缩响应文本 grep 不中；文件层面已注入 | curl 取证必须 `--compressed` |
| 2 | （续上）--compressed 仍 0 → 仍疑 | nginx 根路径 **UA 分流**（10-02 加 map）：无 UA 的 curl 拿到 PC 站 index（15386B），Taro SPA 首页（1897B，含 v72 注入）才是移动端入口 | 分流场景取证必须带目标 UA |
| 3 | redis 扫 `attract72_{table}` 13 表全零 → 判"智能层零活动" | 键格式实为冒号式 `zhuxiang:attract72:{table}:{id}`；改扫后 personas 17/snapshots 35 等全部现形 | 扫描模式必须从 `_k()` 拼接规则推导，不能按表常量名想当然 |
| 4 | docker exec python heredoc 静默失败 → 数据"读不出" | heredoc 走 stdin 需 `-i` 参数 | docker exec 传脚本要么 `-i` 要么 `-c` 单行 |

## 三、真断点与修复（两项，均已部署生效）

### ① 健康度调度器"先 sleep 后执行"缺陷 → 启动即首轮

- **缺陷**：`_scheduler_loop` 原顺序 sleep(86400s)→执行——生产容器
  频繁重建（仅 10-03 即多次），计时器反复重置 → **健康检查永不执行**
  （HEALTH_AUTO=on 数日，health 台账仅历史 6 条、无调度产出佐证）
- **修复**：循环改为执行→sleep（[attract72_scheduler.py](file:///d:/网站架构设计/zhuxiang-jiu/backend/services/attract72_scheduler.py#L57-L72)），
  对齐五模型调度器"重建即即时轮"范式；空库 insufficient 不误冻
  （P6 既有语义，首轮安全）
- **测试**：test_12 新增"启动即首轮"断言（start 后 0.5s 内台账增长），
  专项 **12/12**
- **生产实证**：部署重建后日志 `21:41:54 attract72_scheduled_health
  checkId=6 verdict=healthy`——**首轮即时执行并落台账**
