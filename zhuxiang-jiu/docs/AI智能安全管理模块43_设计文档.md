# 43号·AI智能安全管理模块 设计文档 v1.0

> 定位：**每个请求进来，AI 都先看一眼**——威胁评分低放行、可疑挑战、高危封禁；每个角色的每个动作都建行为基线——偏离即预警；攻击确认与误报裁决自动回流学习，防线随攻防态势**自动升降级**。把安全从"出事后人工排查"变成"AI 常态化值守、越打越准的免疫系统"。
>
> 与既有 AI 风控的关系：**复用不合并**——现有 25 个档案（auth_risk/order_risk/traffic_antifraud 等）是"业务对象级"评分（订单/提现/登录场景内），43号补齐"**请求级**"防线（全局限流/IP 封禁/注入防护/WAF）与"**角色行为级**"基线（UEBA），并整合 ai_enforcement 阻断引擎灰度范式；既有档案一个不动。
>
> 方法论：对标成熟平台——**Cloudflare WAF**（边缘请求评分 + Under Attack Mode → 本模块态势三态）、**Stripe Radar**（每请求实时评分 + 人工裁决反馈学习 → 事件真值回流）、企业级 **UEBA**（用户实体行为分析 → 角色行为基线），叠加本项目既有 Hedge 学习引擎（第26档案）与三级灰度防误杀基建。

---

## 1. 设计目标与核心概念

### 1.1 一句话模型

**"请求到达 → 安全网关中间件（IP信誉 → 频次 → 注入特征 → 身份/时空异常 → ThreatGateScorer 第26档案威胁评分）→ allow / throttle / challenge / block 四档处置 → 攻击事件流水 → 管理员裁决（确认攻击=正反馈 / 误报=负反馈）→ Hedge 学习自动调权 → 防御态势（peace/alert/wartime）随攻击密度自动升降级。"**

- 安全三板斧：**全覆盖**（ASGI 中间件层，先于一切业务路由，无旁路）、**不误杀**（observe 灰度起步 + 误杀率守护 + 一键关闭）、**会进化**（裁决真值回流 Hedge 学习 + 态势自适应）

### 1.2 核心决策：每个请求怎么处置

| 威胁评分 | 处置动作 | 说明 |
|---------|---------|------|
| ≥70 | allow | 正常放行（无感） |
| 50-70 | throttle | 渐进延迟响应（1-3s，软性减速不拒绝） |
| 25-50 | challenge | 挑战验证（mock 验证码应答，一次通过放行并留痕） |
| <25 | block | 拒绝 403 + IP 进封禁表（TTL 自动解封 + 人工可解） |

### 1.3 与既有模块关系（复用不合并）

| 模块 | 关系 |
|------|------|
| `ai_learning` | 新增第 26 档案 `security_threat_gate`（batch 10），Hedge 学习闭环直接复用（submit_feedback/run_learning_cycle/get_weights_view） |
| `ai_enforcement` | **灰度范式底座**：observe/shadow/enforce 三级 + 误杀保护口径平移到安全网关（enforce 才真正 block，observe 仅留痕） |
| `auth`（core） | 中间件次序：CORS(最外) → **SecurityGateway(43号新增)** → JWTAuth → app；网关信任 JWT 注入的 X-Role/X-Member-Id（已删除客户端伪造头，不重复鉴权） |
| `auth_risk`（30号） | 登录场景的风控信号（block/challenge/step_up）作为 identity_risk 因子输入，不替代 |
| `compliance`（24号） | 攻击事件存证扩展（evidenceType=security_event，P2） |
| `order/member/ride 等` | 行为基线数据源：各模块操作流水 → 基线统计（只读，不侵入业务路由） |

## 2. 总体架构：五个子系统

### 2.1 安全网关中间件（SecurityGatewayMiddleware）

ASGI 层全局管线（先于 JWTAuthMiddleware，业务路由零侵入）：

```
请求 → CORS(放行 OPTIONS 预检)
  → SecurityGateway:
      ① 白名单快道(健康检查/静态资源 直接放行)
      ② IP信誉查询(ip_reputation, Redis/内存)
      ③ 频次计数(Redis 滑动窗口: IP+会员双维度, INCR+EXPIRE)
      ④ 特征扫描(path/query/body: SQLi/XSS/路径遍历/命令注入/probe 扫描器特征)
      ⑤ ThreatGateScorer 六因子评分(纯函数, 低延迟)
      ⑥ 处置: allow | throttle(渐进延迟) | challenge(401+挑战应答) | block(403+封禁)
      ⑦ 事件留痕(仅可疑档入流水, 正常放行不记——防流水爆炸)
```

关键设计：
- **快道优先**：白名单 + 纯静态请求直接放行；评分器为纯内存函数，单请求开销微秒级
- **封禁表自动 TTL**：Redis `security43:blocks:{ip}`（内存模式用 dict + 过期懒清理），到点自动解封，不产生"永久误封"
- **防锁死**：`SECURITY_GATEWAY_MODE=off` 一键回退现状；健康检查路径 `/api/decision/health` 永久白名单

### 2.2 威胁评分器（ThreatGateScorer，第 26 档案）

| 因子 | 权重 | 判据 |
|------|------|------|
| ip_reputation | 0.20 | IP 信誉分（历史攻击计数/封禁记录/冷却恢复） |
| request_rate | 0.20 | 滑动窗口频次（IP 与会员双维度，超基线 P95 递减） |
| payload_signature | 0.25 | 注入特征匹配（`' OR 1=1`/`<script>`/`../etc/passwd`/`; rm -rf`/扫描器 UA 特征库） |
| path_anomaly | 0.10 | 路径异常（`/.env`/`/wp-admin`/`/admin.php` 等探针路径、深度遍历） |
| identity_risk | 0.15 | 身份风险（未认证打敏感端点/越权尝试 403 堆积/登录场景 auth_risk 信号直通） |
| geo_time | 0.10 | 时空异常（凌晨 0-5 点集中高频/短时操作密度跳变） |

决策四档：**≥70 allow / 50-70 throttle / 25-50 challenge / <25 block**。

### 2.3 IP 信誉库与封禁（ip_reputation）

- **信誉分模型**：满分 100，攻击事件扣分（按档位 -10/-30/-60），正常请求缓慢恢复（冷却期 24h 每千次 +1）
- **三态**：normal（>60）/ suspicious（30-60，评分降档）/ blacklisted（≤30 或 wartime 直封）
- **自动进出**：攻击即扣分进表，冷却恢复自动出表；管理端可手动钉住（pinned，不受恢复影响）
- 首次访问冷启动给中性分 80（不因新 IP 误杀）

### 2.4 角色行为安全（UEBA·行为基线）

每角色（member/admin/driver/blogger/promoter/financer）行为画像，**只读各模块操作流水，不侵入业务路由**：

- **基线维度**：活跃时段直方图 / 操作频率（小时粒度）/ 功能分布 / 常用会话序列
- **偏离检测**：管理端凌晨批量导出、司机短时批量改单、会员高频秒杀击穿 P95、未授权功能试探
- **输出**：行为预警入事件流水（severity=behavior），高危偏离联动 threat_gate 的 identity_risk 因子加权
- **冷启动**：基线不足 30 天时用全局同角色基线兜底（避免新用户全报警）

### 2.5 自我学习与智能自主升级（learning & posture）

**学习闭环**（对齐 42号 P2 成熟范式）：

```
攻击事件 → 管理员裁决(确认攻击=AI拦对·正反馈 / 误报=AI拦错·负反馈)
  → collect 批量回流(幂等 eventFed 标记) → run Hedge 一轮学习
  → champion 权重晋升 → 六因子权重自动调优
```

**态势三态（autonomous posture，创新点）**：

| 态 | 触发 | 行为 |
|----|------|------|
| peace | 攻击密度 EMA 低于阈值 | 阈值宽松（频次上限×1.5），几乎不挑战 |
| alert | 攻击密度 EMA 超阈值 | 频次收紧（×1.0），挑战比例提高 |
| wartime | 密度跳变或单 IP 高危事件激增 | 频次×0.3、可疑即封、全站敏感操作强制挑战（对标 Cloudflare Under Attack Mode） |

- 升降级带**滞后防抖**（连续 2 个窗口超阈才升级，避免抖动）；管理端可**手动钉住**（pinned 优先于自动）
- **自适应阈值**：request_rate 因子的频次基线取近 7 天 P95 动态校准（而非死值）

**防误杀三保险**：observe 灰度起步（只留痕不处置）→ enforce 前误报率检查（>5% 拒绝晋升）→ 一键 off 总开关。

## 3. 数据模型（前缀 security43，双模式内存+Redis）

```
security_ip_reputation   IP信誉库(评分/状态/攻击计数/冷却时间/pinned)
security_events          攻击事件流水(请求快照/威胁分/因子明细/处置动作/裁决状态)
security_blocks          封禁表(IP/维度/时长/原因/自动解封时间)
security_behavior_baselines  行为基线(角色+会员维度 统计快照)
security_appeals         误报申诉(被挑战/封禁对象申诉→裁决→学习真值)
security_posture         防御态势(当前态/转换历史/钉住标记/密度EMA)
```

**Mock-first**：挑战验证为 mock（challenge_token 应答即通过，无真实验证码服务）；特征库为内置静态规则表 + Redis 热更新（ wartime 规则不重启生效）；真实验证码通道（极验/hCaptcha）与 GeoIP 库留 P3。

## 4. API 设计（约 13 端点，前缀 /api/security）

**会员端**：
- `GET  /api/security/status` 我的安全状态（当前 IP 信誉/是否被挑战中）
- `POST /api/security/challenge/verify` 挑战应答（mock 验证码，一次通过放行留痕）
- `POST /api/security/appeals` 误报申诉（对 challenge/block 事件）
- `GET  /api/security/appeals` 我的申诉列表

**管理端**：
- `GET  /api/security/admin/dashboard` 态势总览（事件统计/封禁数/当前态势/误报率）
- `GET  /api/security/admin/events` 攻击事件流水（按类型/档位/时间过滤）
- `POST /api/security/admin/events/{id}/decide` 事件裁决（确认攻击/误报 → 学习真值）
- `GET  /api/security/admin/ips` IP 信誉查询；`POST /api/security/admin/ips/{ip}/ban|unban|pin` 手动处置
- `GET  /api/security/admin/posture` 态势查看；`POST /api/security/admin/posture` 手动切换/钉住
- `POST /api/security/admin/learning/collect|run` + `GET /status` 学习回流三连（对齐 42号 P2 范式）

## 5. 环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `SECURITY_GATEWAY_MODE` | on | 安全网关总开关（off 一键回退现状，防锁死） |
| `SECURITY_ENFORCE_LEVEL` | observe | observe/shadow/enforce 三级灰度（对齐 ai_enforcement 范式；enforce 才真正处置） |
| `SECURITY_RATE_WINDOW` | 60 | 频次滑动窗口（秒） |
| `SECURITY_RATE_LIMIT` | 120 | 窗口内请求上限（peace 基准，态势自动缩放） |
| `SECURITY_BAN_TTL` | 900 | 自动封禁时长（秒） |
| `SECURITY_POSTURE_MODE` | auto | 态势 auto（自动升降级）/ manual（仅手动） |

## 6. 测试策略（Mock-first）

1. **专项**：六因子直测（构造 SQLi/扫描器/高频各场景）、四档处置口径、IP 信誉扣分/恢复/钉住、封禁 TTL 自动解封、误报申诉→裁决→学习回流幂等、态势升降级滞后防抖、总开关 off 回归现状、enforce 三级灰度
2. **全系回归**：`pytest -m "not redis"` 基线零新增（重点：网关不能拦正常测试流量——测试环境默认 observe）
3. **实机验收**：Docker 全链路（模拟攻击请求→事件流水→裁决→学习→态势联动→封禁/解封）
