## 1. 设计背景

### 1.1 问题来源

在对 `runShippingOpTest` 面板函数进行并发超时测试(PTC10-PTC12)时,发现两个潜在问题:

| 问题 | 触发场景 | 后果 |
|------|----------|------|
| 网络请求无超时 | `EnvAdapter.request` 调用 `fetch`/`wx.request` 后,服务端不响应 | Promise 永远不 settle,调用方长时间挂起,用户误以为卡顿而**重复点击**(不必要重试) |
| 连点提交无防护 | 用户连点"提交订单"按钮,发起多个并发 `submit` | 创建多个重复事务,浪费资源,可能产生重复订单 |

### 1.2 验证依据

PTC10-PTC12 并发超时测试证明:

- **try/catch 兜底在并发下对每个请求独立生效**(PTC11: 5 并发,PTC12: 20×2 轮)
- **极端并发无线程阻塞、无内存泄漏**(PTC12: 两轮 DOM 增长线性,JS 堆不持续暴涨)
- **快速失败 + 兜底处理**是安全的,可放心采用 fail-fast 策略

基于以上验证,设计了两项优化:
- **超时竞争**:让网络请求快速失败,避免长时间挂起
- **防重入**:在请求进行中直接拒绝重复调用,避免并发重复事务

## 2. 超时竞争机制

### 2.1 设计方案

采用 `Promise.race` 让实际请求与超时 Promise 竞争,先完成的胜出:

```
实际请求(realPromise) ──┐
                        ├── Promise.race → 调用方
超时 Promise(timer) ────┘
```

- 请求在 `timeout` 内完成 → 返回正常响应
- 超时先到 → reject 超时错误,调用方 try/catch 兜底

### 2.2 实现细节

文件: `js/env-adapter.js` · 函数: `request` · 版本: v1.2.0

```js
function request(opts) {
    const env = getEnv();
    const { url, method = 'GET', data = {}, header = {}, timeout = 10000 } = opts || {};

    let realPromise;

    // 各端请求分支(微信/支付宝/APP/H5),赋值给 realPromise
    if (env === 'wechat-mini')      { realPromise = miniRequest(wx, opts, {...}); }
    else if (env === 'alipay-mini') { realPromise = miniRequest(my, opts, {...}); }
    else if (env === 'app' && ...)  { realPromise = window.__nativeBridge.request(...).then(...); }
    else if (typeof fetch === 'function') {
        realPromise = fetch(url, {...}).then(function (r) { return {...}; });
    } else {
        return Promise.reject(new Error('无可用网络接口'));
    }

    // 超时竞争(fail-fast)
    return Promise.race([
        realPromise,
        new Promise(function (_, reject) {
            setTimeout(function () {
                reject(new Error('请求超时(' + timeout + 'ms · ' + method + ' ' + url + ')'));
            }, timeout);
        }),
    ]);
}
```

### 2.3 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `opts.timeout` | `10000`(10 秒) | 超时毫秒数,可通过 opts 传入自定义值 |

调用示例:
```js
// 默认 10 秒超时
EnvAdapter.request({ url: '/api/submit', method: 'POST', data: params });

// 自定义 30 秒超时(大订单/文件上传)
EnvAdapter.request({ url: '/api/submit', method: 'POST', data: params, timeout: 30000 });

// 快速探测(2 秒)
EnvAdapter.request({ url: '/api/health', method: 'GET', timeout: 2000 });
```

### 2.4 各端适配说明

| 端 | 请求方式 | 超时实现 | 备注 |
|----|----------|----------|------|
| H5 | `fetch` | `Promise.race` + `setTimeout` | fetch 无原生超时,需 race |
| 微信小程序 | `wx.request` | `Promise.race` + `setTimeout` | wx.request 有原生 timeout 字段,但 race 统一处理 |
| 支付宝小程序 | `my.request` | `Promise.race` + `setTimeout` | 同上 |
| APP | `__nativeBridge.request` | `Promise.race` + `setTimeout` | native 层可自行实现取消,race 作为兜底 |

> **注意**: `Promise.race` 超时后,底层请求(fetch/wx.request)仍在进行,无法取消(除非用 AbortController)。但调用方已收到失败信号,不会阻塞。这是 fail-fast 的权衡:优先保证调用方快速收到结果。

## 3. 防重入机制

### 3.1 设计方案

在 service 公共 API 层增加 `_submitInFlight` 标记:
- 进入 `submit` 时检查标记,若为 `true` 直接拒绝(返回"进行中"错误)
- 标记为 `false` 则设为 `true`,执行事务,`finally` 中释放

### 3.2 实现细节

文件: `js/checkout-service.js`

**模块作用域声明标记**(L64-L66):
```js
let mode = 'mock'; // 'mock' | 'live'
let apiBase = '/api/checkout';
// 防重入标记:避免连点提交按钮导致的并发重复下单
let _submitInFlight = false;
```

**公共 API submit 方法**(L554-L571):
```js
async submit(params) {
    // 防重入:连点提交时直接拒绝第二个,减少不必要的重复事务
    if (_submitInFlight) {
        return {
            success: false,
            error: '订单提交进行中,请勿重复点击',
            logs: [{ step: '防重入', level: 'WARN', msg: '提交被防重入拦截' }]
        };
    }
    _submitInFlight = true;
    try {
        if (mode === 'live') {
            try { return await liveSubmit(params); }
            catch (e) {
                return { success: false, error: e.message, logs: [...] };
            }
        }
        return await submit(params);  // mock 模式
    } finally {
        _submitInFlight = false;  // 无论成功/失败都释放
    }
}
```

### 3.3 释放保证

`try/finally` 结构确保标记在任何情况下都会释放:

| 执行路径 | _submitInFlight 释放 | 说明 |
|----------|----------------------|------|
| 正常完成(return) | ✅ finally 执行 | mock 模式事务成功 |
| 抛异常(throw) | ✅ finally 执行 | 事务失败,错误传播 |
| live 模式网络失败 | ✅ finally 执行 | catch 后 return,仍走 finally |

> **关键**: 必须用 `try/finally`,不能用 `try/catch`(会吞掉错误)或裸 `return`(异常时不释放)。

### 3.4 防重入 vs Mutex 锁的区别

| 维度 | 防重入(_submitInFlight) | Mutex 锁(stock:pid) |
|------|--------------------------|----------------------|
| 粒度 | 整个 submit 操作(粗粒度) | 单个商品库存(细粒度) |
| 行为 | 直接拒绝第二个(快速失败) | 排队等待(FIFO 公平) |
| 适用 | 用户连点提交(不应并发) | 库存扣减(需串行但可排队) |
| 实现 | 布尔标记 + try/finally | FIFO 队列 + acquire/release |

## 4. 协同工作流程

两项优化协同工作,形成"快速失败 → 兜底处理 → 减少重复"的闭环:

```
用户点击提交
      │
      ▼
┌─────────────────────┐
│ 防重入检查            │ _submitInFlight?
│                     │
│  true  → 拒绝(返回"进行中")──→ 用户看到提示,停止点击
│  false → 继续 ↓      │
└─────────────────────┘
      │
      ▼
┌─────────────────────┐
│ _submitInFlight = true │
│ 执行事务(9 阶段)      │
│                      │
│ live 模式: EnvAdapter.request
│   ┌─ 超时竞争 ─┐    │
│   │ Promise.race│    │
│   │  请求 vs 超时 │   │
│   └──────┬──────┘    │
│          │            │
│   完成 ← ┘ 超时 → reject
│          │            │
│   try/catch 兜底(验证已证明健壮)
└─────────────────────┘
      │
      ▼
┌─────────────────────┐
│ finally:             │
│ _submitInFlight = false │  ← 释放,允许下次提交
└─────────────────────┘
      │
      ▼
返回结果给用户
```

**逻辑链**:
1. 防重入拦截连点 → 减少并发重复请求
2. 超时竞争快速失败 → 避免长时间挂起
3. try/catch 兜底(PTC10-12 验证健壮) → 安全处理失败
4. 用户快速收到明确错误 → 不会盲目重试
5. _submitInFlight 释放 → 下次提交可正常进行

## 6. 与 Mutex FIFO 的关系

本机制与现有 [Mutex FIFO 并发控制](并发控制与事务一致性技术文档.md) 互补,作用于不同层次:

```
请求层(防重入 + 超时)          资源层(Mutex FIFO)
┌──────────────────┐         ┌──────────────────┐
│ submit 防重入      │         │ stock:pid 库存锁  │
│ request 超时竞争    │         │ 事务原子性(BEGIN/COMMIT/ROLLBACK)
│  → 减少不必要并发    │         │  → 串行化临界区    │
└──────────────────┘         └──────────────────┘
        │                            │
        └──────── 协同 ───────────────┘
```

| 层次 | 机制 | 作用 |
|------|------|------|
| 请求层(本文档) | 防重入 + 超时 | 减少不必要的并发请求进入系统 |
| 资源层(Mutex FIFO) | stock:pid 锁 + 事务 | 对已进入的并发请求串行化,防超卖 |

两者协同: 请求层减少并发量 → 资源层串行化处理剩余并发 → 整体并发安全且高效。

## 7. 扩展指南

### 7.1 为新 service 加超时

`EnvAdapter.request` 已内置超时,所有 service 的 live 请求自动受益,无需额外改动:

```js
// service 的 live 函数,自动获得 10s 超时
async function liveSubmit(params) {
    const r = await EnvAdapter.request({  // ← 自动有超时
        url: apiBase + '/submit',
        method: 'POST',
        data: params,
        timeout: 15000,  // 可选: 自定义超时
    });
    if (!r.ok) throw new Error('HTTP ' + r.status);
    return await r.json();
}
```

### 7.2 为新操作加防重入

适用于"用户主动触发、不应并发"的操作(提交/支付/核销等):

```js
// 1. 模块作用域声明标记
let _payInFlight = false;

// 2. 公共 API 方法包裹 try/finally
async pay(params) {
    if (_payInFlight) {
        return { success: false, error: '支付进行中,请勿重复点击' };
    }
    _payInFlight = true;
    try {
        return await doPay(params);
    } finally {
        _payInFlight = false;  // 必须释放
    }
}
```

### 7.3 不适用防重入的场景

- **库存扣减/回补**: 需要排队等待(Mutex FIFO),而非直接拒绝
- **查询类操作**: 幂等且无副作用,重复调用无害
- **后台异步任务**: 已由 TransactionTemplate 的 asyncTasks 管理
