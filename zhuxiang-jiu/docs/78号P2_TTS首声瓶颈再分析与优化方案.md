## 二、瓶颈实证：三视角网络分解（2026-09-23 16:20 实测）

| 视角 | TCP connect | TLS 增量 | TTFB | total |
|---|---|---|---|---|
| 国内客户端 → `POST /api/xiaozhu/sessions/*/voice` | **1258ms** | +515ms | **2027ms** | 2027ms |
| 国内客户端 → `GET /`（静态对照） | 253ms | +480ms | 967ms | 967ms |
| **服务器本机 → 同 API** | 0.2ms | — | **18ms** | 19ms |

**三条证据链定案**：
1. 服务器本机 TTFB 仅 **18ms**——FastAPI/鉴权/会话链/执行全无辜（与 voice48_timing 执行 58~85ms 相互印证）；
2. 国内单次 TCP 握手 253~1258ms——正常国内 RTT 应 <50ms，实证服务器（阿里云**新加坡**段位 47.236.x）跨境线路质量差且抖动大；
3. 浏览器热连接下 submit→resp 实测 2231~2837ms 与冷连接 TTFB 2027ms 同量级——连接复用救不了高 RTT，**2.3s ≈ 纯网络往返，非服务端问题**。

## 三、优化方案（按 ROI 排序）

### O1【治本·决策项】国内接入迁移——预期收益 1.7s+

- **方案**：迁移国内机房（阿里云深圳/杭州）或先以国内 CDN 动态加速接入（全站 API 反代）
- **收益测算**：submit→resp 2.3s → 200~400ms（国内 RTT），端到端首声 2.4s → **~0.7s**——超全部原《优化清单》P0+P1 理论收益之和的 3 倍
- **前置**：ICP 备案状态核查（境外机房大概率未备案）→ 迁移合规评估（周期 1~3 周含备案）→ 数据迁移方案
- **定位**：唯一治本项。其余皆为治标。

**评估纪要（2026-09-23 完成）**：
1. **备案判据**：主站与语音页页脚均无 ICP 备案号展示（境内合规强制项）——佐证**当前为未备案经营态**，与境外机房（阿里云新加坡）互为因果；工信部备案库需人工带验证码查询，建议以企业主体正式核验为准；
2. **关键路径锁定**：**ICP 备案是 O1 的唯一前置且无绕行**——国内机房接入与国内 CDN 动态加速均强制要求已备案域名；
3. **路径**：企业主体 ICP 备案（周期约 1~3 周）→ 备案通过后二选一：a) 整体迁移国内区域 ECS（数据/静态/后端一并迁）b) 先行国内 CDN 动态加速反代 API（迁移量最小，快速验证收益）；
4. **建议**：备案启动为纯行政流程（与开发并行不冲突），期间 O2/O3/O4 治标项已全部落地对冲；备案完成后按 b) 快速验证（预期 1 天内见效），再决策是否整体迁移。

**CDN 动态加速快验结果（2026-09-23 执行完毕——零成本拿走 85% 收益，GA 必要性重估）**：

1. **路径诊断定案**：国内（移动宽带）→ 源站（阿里云新加坡）RTT 平均 245ms + **丢包 20%**（移动→CMI 国际出口普通公网链路）——2.3s 的大头是"每次新连接在 20% 丢包下 TCP+TLS 握手 ~1.2s"被逐请求重复支付；
2. **快验动作（免备案合规路径）**：生产 nginx 站点原为 `listen 443 ssl`（**HTTP/2 从未开启**）——一行改 `http2 on`（nginx 1.30.4 自带 http_v2 模块，热加载零停机，配置备份 zxjiu.conf.bak-h2）——语音链多请求（提交 POST + TTS 多块并行 + 流式 fetch）单连接多路复用，免重复握手；
3. **实测对照（[LAT-embed] 生产真轮）**：**submit→resp 2231~2837ms → 274~393ms（降幅 ~85%）**，端到端 total 最优 **1030ms**（基线 2337ms）——端到端首声进入 1 秒时代；resp→play 82~179ms 持平（缓存路径不受影响，符合预期）；
4. **对 O1 的影响**：正式 CDN/GA（阿里云全球加速，IP 层免备案）的剩余收益空间收窄至 ~150-250ms（245ms 本征 RTT → GA 内网 ~70-80ms）——**备案+迁移的重决策必要性大幅下降**，建议 H2 观察一周（G1 完整版 09-30 同步统计 H2 后分布）后再定 GA 是否立项；
5. **遗留观察**：单轮 submit→resp 21.1s 异常一次（同轮 resp→play 82ms 正常——服务端/会话层波动，非网络因素），[LAT] 埋点持续采集中。

### O2【治标·立即小改】预合成 mood 键覆盖——慢档轮 950ms → ~90ms

- 现状：预合成只写 speed=1.0 键，care（0.92）/steady（0.95）轮永不命中 → 走流式，慢档时段首声 ~950ms
- 改法：`_preheat_tts_first_chunk` 按 turn 的 mood 系数算实际 speed 写键（turn 已带 mood 字段，前端请求口径 `moodSpeed` 对齐）——care/steady 轮亦 21ms 级命中
- 改动面：xiaozhu_service 一处；收益随慢档占比放大（G1 完整版定量后复核）

### O3【治标·微改】前端预取 decode 预热——挤 30~60ms

- preheatTTS/ttsPreheat 预取到 bytes 后立即 decode 存 AudioBuffer（播放时零 decode）；ctx 未建时 fail-soft 回退 bytes 存储
- 缓存命中路径 86~104ms → ~50~70ms

### O4【体感·慢档垫场】流式慢档过渡音接力——慢档体感 950ms → ~300ms

- 流式请求 300ms 未出首片 → 起播"好的"过渡音垫场，首片到达即让位（gap 机制扩展到流式等待期）
- 不改真实延迟，压感知延迟（原《清单》P2 思路在流式场景的延伸）

### O5【观察·零代码】G1 完整周样本（09-30）

- first_chunk 全周分时分布 → 定量慢档占比；若 <10%，O2/O4 降级为可选；若 >30%，O2 立即做 + B 路线（自建 TTS）触发器复核
