# 竹创多 Agent 创新规划与 Word 交付设计

- 日期：2026-11-27
- 目标仓库：`ccvccp/zhuxiang-jiu`
- 方案：仓库内轻量级多 Agent 文档流水线
- 输出：一份按创新规划、设计、部署、验收四章组织的完整 Word
- 状态：四部分设计已获用户逐项批准，等待书面规格复核

## 1. 背景与现状

竹香酒项目已有竹盾、竹医、竹园、竹演等 Agent 基础设施，以及模块、页面、端点、红线、业务链、案例和回放报告等项目资产。创新规划与验收文档已有实际样例，可以作为新能力的结构和证据口径参考。

项目已有 `backend/services/llm_client.py` 统一模型客户端，支持 OpenAI 兼容的聊天接口，并已有超时、节流、指标、日志及未配置时的规则回退机制。新能力应复用该客户端，不另建模型网关。

项目事实注册表位于 `docs/registry/`。其中 Markdown 是事实源，`registry.json` 由脚本生成，只用于机器检索，不能手工编辑。

当前项目没有发现既有 Word 生成实现，生产与开发依赖中也尚未声明 `python-docx`。因此，合并 Word 输出是新增能力，不能描述为已有功能。

## 2. 目标与成功闭环

用户输入一个创新主题及可选补充需求后，系统按需执行：

`真实项目证据 → 创新规划 → 设计 → 部署方案 → 验收计划／报告 → 独立审查 → 合并 Word`

首阶段成功标准：

1. 规划、设计和部署内容与目标项目的真实注册表、代码和历史案例对齐。
2. 四章通过稳定编号和结构化数据保持一致，而不是四段互不关联的模型文本。
3. 外部模型不可用时明确标记降级，不伪装成模型调用成功。
4. 生产部署不由文档命令自动执行。
5. 验收通过结论必须关联真实执行证据；未执行时只能生成待验证计划。
6. 最终真实生成一份可重新打开解析的 `.docx`，同时保留可审查、可重新渲染的源稿。

## 3. 约束与非目标

1. 采用轻量 CLI，按需运行，不引入常驻服务、任务数据库、分布式队列或管理后台。
2. 复用现有模型客户端、Agent 组织方式、项目注册表和测试纪律。
3. 不向外部模型上传整个仓库，只发送当前阶段所需的最小证据摘要。
4. 不提交或记录 API Key、请求头、支付配置、用户数据及其他敏感信息。
5. 不自动执行生产部署，不自动合并 PR，不伪造测试、部署或验收结果。
6. 首阶段只生成规划、设计、部署方案和验收计划／证据驱动报告，不承担真实生产部署执行。
7. 默认运行产物不直接进入 Git；经用户审定的正式文档可另行归档或按需提交。

## 4. 总体架构与角色

新增模块暂名“竹创”，位于 `agent-infra/zhuchuang/`。各 Agent 是职责独立、可单独测试的逻辑角色，由主控 Agent 顺序编排，不代表新增常驻进程。

| 角色 | 输入 | 主要输出 | 权限边界 |
| --- | --- | --- | --- |
| 主控 Agent | 创新主题、补充需求、运行参数 | 执行状态、阶段交接、恢复点、交付清单 | 不执行生产部署 |
| 证据 Agent | 注册表 Markdown、代码结构、历史方案与案例 | 带来源定位和仓库版本的项目事实包 | 不猜测缺失事实 |
| 规划 Agent | 创新主题、项目事实包 | 目标、范围、非目标、裁剪决策、复用关系、任务 | 不修改业务代码 |
| 设计 Agent | 规划结果、项目事实包 | 架构、组件、接口、数据、安全、错误处理与测试设计 | 重大变更仍按团队规程审查 |
| 部署 Agent | 设计结果、现有部署资产 | 前提、步骤、确认门、验证与回滚方案 | 只出方案，不实施生产部署 |
| 验收 Agent | 规划、设计、真实测试记录 | 验收用例、证据映射、实际结论或待验证状态 | 无证据不得判定通过 |
| 独立审查 Agent | 四章源稿及全部证据 | 事实、追踪、一致性、真实性和交付审查 | 硬门禁失败不能被模型覆盖 |
| Word 渲染器 | 审查通过的结构化源稿 | 一份四章合并 Word | 不直接渲染未经审查的模型原文 |

## 5. 数据流与阶段恢复

```text
创新主题与需求
      ↓
固定仓库版本并采集项目证据
      ↓
创新规划 → 设计 → 部署方案 → 验收计划／报告
      ↓
独立审查：事实、证据、跨章一致性、结论真实性
      ↓
结构化源稿、合并 Markdown 与审查记录
      ↓
一份完整 Word
```

关键规则：

- 注册表 Markdown 为事实源，JSON 只用于检索。
- 每项描述现有项目的关键事实保留相对路径和行号或符号定位。
- 证据不足时写“待确认”；面向未来的内容标为“建议／规划”。
- 后一阶段只消费前一阶段的结构化结果和证据包。
- 每个阶段完成后原子保存状态；失败重跑可从最后成功阶段恢复。
- Word 只从审查后的源稿生成。源稿变化会使原审查失效，必须重新审查。
- 渲染失败时保留源稿和审查记录，不宣称已交付 Word。

## 7. 命令入口

沿用项目现有脚本式 CLI：

```bash
python agent-infra/zhuchuang/cli.py run --topic "创新主题"
```

`run` 参数：

- `--request-file`：读取补充需求。
- `--repo-root`：目标项目，默认当前仓库。
- `--output-dir`：交付目录。
- `--generation auto|external|rule`：默认 `auto`。
- `--model`：可选模型名覆盖。密钥只从环境变量读取，不提供命令行密钥参数。

另设：

```bash
python agent-infra/zhuchuang/cli.py render --run-dir <运行目录>
python agent-infra/zhuchuang/cli.py accept --run-dir <运行目录> --evidence <真实验收证据>
```

- `render` 只对同一审查通过源稿重新排版；源稿摘要不一致时拒绝渲染。
- `accept` 导入真实测试／部署证据，更新验收章并重新审查，不提供手工把 `pending` 改成 `passed` 的捷径。
- 三个命令均不提供生产部署开关。

## 8. 数据契约

所有契约包含 `schema_version`。阶段间只传结构化对象，模型自由文本必须经过解析和校验后才能进入下一阶段。

| 契约 | 必要内容 |
| --- | --- |
| `RunManifest` | 运行编号、主题、仓库提交号、工作区是否干净、阶段状态、生成方式、模型名称、警告和交付路径 |
| `EvidenceItem` | 证据编号、类型、相对路径、行号或符号定位、摘要、来源版本 |
| `StageArtifact` | 阶段、状态、证据引用、结构化正文、待确认事项、实际生成方式 |
| `PlanningChapter` | 背景、目标、范围、非目标、裁剪决策、复用关系、优先级和任务 |
| `DesignChapter` | 架构、组件、接口、数据契约、安全边界、错误处理和测试策略 |
| `DeploymentChapter` | 前提、步骤、人工确认门、验证方法、回滚方案 |
| `AcceptanceChapter` | 计划／结果模式、验收用例、证据映射和 `pending|passed|failed` 结论 |
| `AcceptanceEvidence` | 执行命令或动作、环境、执行时间、退出状态或实际结果、输出摘要、产物定位 |
| `ReviewReport` | 无来源事实、跨章冲突、缺失章节、未验证声明、阻断项、源稿摘要和生成许可 |

生成方式逐章记录为 `external` 或 `rule`，整次运行为 `external`、`rule` 或 `mixed`。`external` 严格模式不允许混入规则章节。

`passed` 必须关联有效 `AcceptanceEvidence`。计划文本、模型陈述或只有截图而没有可核对结果的内容，不能单独构成通过证据。

## 9. 外部模型与降级

### 9.1 模型适配

`model_adapter.py` 只适配现有 `llm_client.py`，复用其配置、超时、日志和错误处理，不重新实现 HTTP 客户端。

默认沿用：

- `LLM_API_KEY`
- `LLM_BASE_URL`
- `LLM_MODEL`
- `LLM_TIMEOUT`
- `LLM_ENABLED`

每个 Agent 使用独立提示词和输出契约，共享同一运行的事实包和上游结构化结果。运行记录只保存模型名称和调用状态，不保存密钥或完整请求头。

### 9.2 内容边界

- 只发送当前阶段所需的最小证据摘要。
- 默认排除环境配置、密钥、令牌、支付配置、用户数据和疑似敏感文本。
- 证据采集使用明确的项目文件范围，不递归上传无关文件或二进制资产。
- 日志可以包含模型名、状态摘要和本地相对路径，但不包含秘密及敏感正文。

### 9.3 模式行为

| 情况 | `auto` | `external` | `rule` |
| --- | --- | --- | --- |
| 未配置密钥或模型关闭 | 降级并明确标记 | 停止正式文档生成 | 正常运行 |
| 超时、HTTP 错误、空响应 | 当前阶段降级并记录原因 | 停止正式文档生成 | 不调用模型 |
| 输出不符合契约 | 最多纠错一次，仍失败则降级 | 纠错后仍失败即停止 | 不调用模型 |
| 部分阶段降级 | 允许并标记 `mixed` | 不允许 | 全部为规则生成 |

规则降级仅使用真实证据和确定性模板，不宣称完成了外部模型推理。Word 封面、文档控制表和交付清单均标明实际生成方式。

## 10. 审查门禁与异常处理

### 10.1 独立审查

确定性硬门禁始终执行，模型辅助审查只能补充发现，不能覆盖硬门禁失败。

1. **事实门禁**：现状事实必须有证据，未来内容必须标为建议或规划。
2. **追踪门禁**：使用 `OBJ-*`、`CMP-*`、`DEP-*`、`AC-*` 连接目标、组件、部署步骤和验收用例。
3. **跨章一致性门禁**：核对范围、名称、接口、端口、环境开关和验收口径。
4. **真实性门禁**：没有真实证据时强制保持 `pending`，拒绝无证据的部署或通过声明。
5. **红线门禁**：涉及支付回调、鉴权、模型门控、Redis、语音或部署红线时，必须列出专项风险和人工确认点。
6. **交付门禁**：存在阻断项时保留源稿和报告，不生成正式 Word。

### 10.2 异常处理

| 场景 | 处理 |
| --- | --- |
| 主题为空、需求不可读、目录无效 | 调用模型前失败 |
| 注册表缺失或版本无法确定 | 记录阻断或待确认，不猜测补齐 |
| 单阶段失败 | 保留前序产物，从失败阶段恢复 |
| 模型失败 | 按生成模式处理，不紧密循环重试 |
| 审查阻断 | 不生成正式 Word，输出可定位的审查发现 |
| 渲染或重新打开失败 | 保留源稿，返回失败，不宣称交付 |
| 敏感信息或生产风险 | 停止相关处理，不记录秘密，不执行生产动作 |

## 11. Word 结构与排版

`python-docx` 只加入开发／测试依赖，不进入生产 Docker 镜像。

文档结构：

1. 封面：标题、创新主题、目标项目、日期、仓库提交号、文档状态、实际生成方式。
2. 文档控制表：版本、审查状态、证据截止时间、待确认事项。
3. 内容导航：四章及附录，使用 Word 标题级别支持导航窗格。
4. 第一章：创新规划。
5. 第二章：设计。
6. 第三章：部署方案。
7. 第四章：验收计划／报告。
8. 附录：证据索引、跨章追踪关系、独立审查摘要和运行记录摘要。

排版要求：

- A4 页面，统一页边距、中文字体、标题层级、正文行距和页码。
- 表格使用重复表头，长路径与长标识允许换行且不超出页面。
- `pending`、`passed`、`failed` 使用明确文字，不仅依赖颜色。
- 证据引用保留相对路径和行号／符号定位，不伪装成公开链接。
- 不残留模板变量、空章节或无证据通过结论。

## 12. 测试策略

| 测试层 | 覆盖内容 |
| --- | --- |
| 契约单元测试 | 必填字段、状态枚举、稳定编号、证据引用和跨章追踪 |
| 证据采集测试 | 注册表读取、代码定位、缺失文件、脏工作区标记、敏感内容排除 |
| 模型适配测试 | 模拟成功、空响应、超时、异常、非法结构和一次纠错；不访问真实网络 |
| 降级测试 | `auto` 明示降级、`external` 失败即停、`rule` 离线和 `mixed` 记录 |
| 审查测试 | 无来源现状、跨章冲突、缺失目标、伪造通过结论和红线变更被阻断 |
| 验收证据测试 | 无证据不能通过，失败证据产生 `failed`，有效证据才可形成 `passed` |
| Word 集成测试 | 生成真实 `.docx` 并重新打开，检查四章、表格、状态、附录和占位符 |
| 回归测试 | 新模块完整测试及相关现有 Agent、模型客户端测试 |

真实外部模型调用是独立可选冒烟测试，仅在已配置凭据时执行，并如实报告模型与结果。模拟测试成功、规则降级成功均不等于真实外部模型冒烟成功。

## 13. 首阶段验收标准

首阶段完成必须同时满足：

1. 一条命令读取当前真实项目，生成四章结构化源稿和一份合并 Word。
2. 源稿记录仓库提交号、工作区状态、证据来源和逐章生成方式。
3. 四章可通过稳定编号追踪，且不存在审查阻断项。
4. 三种生成模式均有自动化测试，模型失败不会被报告为成功。
5. 文档命令不自动执行生产部署。
6. 无真实证据时验收章保持待验证，有效证据才能形成实际结论。
7. 最终 `.docx` 真实存在、非空、可重新打开解析，四章及附录完整。
8. 使用当前仓库完成一次端到端示例；无真实模型凭据时明确标为规则降级。
9. 新模块测试及相关回归测试通过，敏感配置不进入产物、日志或 Git。

## 14. 后续扩展边界

后续如增加后端 API、任务队列、在线下载或管理界面，应另行设计持久化、权限、异步任务、配额和运维机制。首阶段不预先实现这些能力，也不把未来扩展描述为本次已交付功能。
