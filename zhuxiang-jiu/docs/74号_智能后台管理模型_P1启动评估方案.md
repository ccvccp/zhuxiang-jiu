## 一、四大真实缺口(= P1 边界)

### 缺口 1: 主机级监控——生产启用现成栈(零开发)

- `compose.monitoring.yml`(node-exporter/cAdvisor/Prometheus/Grafana)**已在仓库,
  仅本地验证过**——P1 第一步: 生产服务器拉起, Grafana 出主机/容器双视角
- 覆盖 docx"感知层-多维数据接入"的基础设施维度(单机 Docker 场景恰配轻量栈,
  无需 docx 的 Fluentd/Neo4j)
- 成本: 服务器加 2-3 个轻容器(~200MB 内存), 一次性配置

### 缺口 2: 告警发送闭环——最后一公里接线(小改动大回报)

- 摸底实锤: 26号 monitor_service 有告警状态机但 **notification 字段未接
  真实发送**; security_alert_service 已跑通"Redis 体检→管理员站内信+去重"
  同款通道
- P1: monitor 告警出口接入 message_service 六通道(站内信+短信双触达,
  P0/P1 级才短信), 复用防骚扰体系——**告警从"仪表盘里躺着"变"找到人"**
- 对应 docx"多模态告警聚合"务实版: 先触达, 聚合(P2)再上

### 缺口 3: IBMS 巡检总线——30 个脚本收敛为无人值守(核心增量)

现状: verify_wine_prod/verify_tts_fault/check_guard/window_rate/bom_trap_
watcher… 全是**人工手动跑**的散装验证。docx"无人值守/自愈剧本"落地为:

```
ibms_patrol_service(新, 74号):
  · 巡检清单注册表: {检查项, 脚本/方法, 频率, 风险级, 期望态}
  · 定时编排(挂 main.py startup 调度器, 同既有惯例)
  · 结果三态: PASS / WARN(LLM 诊断建议) / FAIL(告警+人工处置项)
  · 决策留痕: 每次巡检入 Redis, 44号归因口径同款
  · 低风险自愈试点(白名单): guard 自动恢复类(restore_guard_auto 已实证
    crontab 跑过)收编入总线; 高风险(重启服务/资金类)永不出白名单
    (对齐 docx 风险控制: 数据删除/核心配置/资金操作保留人工审批)
```

### 缺口 4: LLM 诊断助手——ChatOps 单入口(认知层变现)

- 现成件拼装: LLM 八方法 + 巡检总线数据 + 26号仪表盘 = docx"一键诊断助手"
- P1 形态: 管理接口 `POST /api/ibms/diagnose {target}` → 拉该模块
  巡检记录+监控快照+最近日志 → LLM 结构化输出
  {summary, rootCauseCandidates, suggestedActions[], riskLevel}
  (对齐 promo_agent JSON 结构输出+三级降级惯例, LLM 失败回退"原始数据摘要")
- 入口即 docx"自然语言控制台"的务实第一步——**只读诊断先行, 变更执行
  永远走既有 46号 approve 链**(不做 LLM 直接改配置, 铁律)

## 三、P1 实施路径(六步, 73号同款节奏)

1. **生产启用 monitoring 栈**(scp compose.monitoring.yml → 拉起 →
   Grafana 基线面板)——零代码
2. **告警闭环接线**(monitor_service 出口 → security_alert_service 同款
   通道 → message_service; P0/P1 短信阈值)——单测: 触发假告警验触达
3. **巡检清单 v1**(收编 6 个高频脚本: wine 四问链/guard/护栏/窗口率/
   bom 哨兵/Redis 体检——全部 PASS/WARN/FAIL 三态化)
4. **ibms_patrol_service 编排**(调度器挂载, IBMS_PATROL_MODE=off 默认
   铁律 → shadow 干跑一周 → on)
5. **diagnose 接口**(LLM 结构化诊断 + agentTrace 留痕 + 只读铁律)
6. **验收**: 触发三类真实场景(杀 Redis/磁盘写满/guard 掉线)全链
   巡检→告警→诊断→处置留痕实证; 单测全绿; 生产镜像更新走既有
   scp+compose rebuild 惯例

## 四、风险控制(全量继承项目铁律, docx 四机制一一对齐)

- **人机协同**: 资金/删除/核心配置永留人工(05号大额/36号三审现状即答案)
- **权限最小化**: 巡检自愈白名单逐项显式注册, 无通配符
- **审计追溯**: 巡检/诊断全量哈希链留痕(admin_log 同款 sha256 链)
- **熔断降级**: 自愈成功率 <90% 自动降 shadow 并 P0 告警(docx 原文采纳)
- **LLM 禁入判定链**: 诊断输出仅"建议", 执行一律走既有 approve 链

## 五、ROI 与触发器

- 值班成本: 当前 30 个验证脚本全人工——P1 后高频 6 项无人值守,
  日常巡检时间预计 -70%(docx 口径 70% 落到本项目)
- MTTR: 告警触达从"打开仪表盘才发现"变分钟级触达
- 74号 ROI 触发器(对齐 73号范式): P1 巡检稳定 4 周且 WARN 闭环率
  ≥80% → 启动 P2(变更建议书+调度器放量); 否则维持 shadow 观测
