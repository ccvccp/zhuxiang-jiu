## 五、音频缺陷根因修复(口播片, 用户实听反馈闭环)

**现象**: 口播片"嘴型在动但听到嘟嘟声, 嘟嘟后才出配音"。

**根因定位(频谱/分帧能量/对照实验三层实证)**:
- cogtts 整句接口(synthesize)返回 wav 前 1.78s 为固定 beep 脉冲
  序列(恒定振幅帧串 RMS≈1264+孤立静音, 频谱 200-400Hz 窄带)——
  与文本/语速/开头词无关(去开头词变体嘟嘟段逐帧一致; 短文本
  同样带); 三条新片+9-30 旧片+复现共 8 样本全部命中同指纹,
  silence 锚点 0.650167s 完全一致
- 即 9-30 起的口播片均带此缺陷(旧片用户未察觉, 今日细听发现),
  非今日服务端变化; SadTalker 全段 wav 驱动口型 → 嘟嘟段嘴照动
- 48号流式轨(synthesize_stream SSE 分块)不受影响(首块 32-83ms
  真分块)——仅 sv73 整句轨受累

**修法 ca78faf(sv73_render_service)**:
- _tts_audio 前置 _strip_beep_lead: 89 帧指纹模板精确匹配
  (mean_diff<120, 病样本实测 57)→ 剥除前 1.78s+重写 RIFF/data
  长度; 不匹配(智谱改前导/正常音频)零损伤跳过; 纯 stdlib 无新依赖
- 验证: 8 样本指纹全命中(剥离量精确 85440B=1.78s); 清洗后频谱
  实证开头即干净语音(无嘟嘟/无突兀截断); 短文本复现同样剥除;
  test_sv73_script 8/8 回归通过(mock TTS 不匹配指纹→零损伤)

## 六、小竹播报嘟嘟同源根治(用户二次反馈闭环, 2c3b422)

**现象(用户实测反馈)**: 小竹语音播报同样嘟嘟——"嘟嘟声响播报
中断, 嘟嘟响完再播报"。

**根因(推翻此前判断)**: 小竹播报主路径 GET /api/xiaozhu/tts
(微信 X5 无系统 TTS 引擎的服务端播报轨)→ synthesize_mp3
(to_thread 函数引用形式调用, 首次 grep 漏匹配)→ 整句
synthesize → cogtts 固定 1.78s 前导嘟嘟。此前"48号流式轨
不受影响"的判断仅对流式成立——生产 XIAOZHU_TTS_STREAM 默认
off(实证 printenv 未设置), 播报全走整句轨, 主路径一直带嘟嘟。

**修法(清洗下沉到源头, 一处覆盖全部调用方)**:
- llm_client.synthesize 返回口统一挂 _strip_beep_lead_wav
  (同款 89 帧指纹, 命中剥 1.78s+重写 RIFF/data; 不匹配零损伤)
  ——小竹 /tts、sv73 _tts_audio、未来调用方全量覆盖
- sv73_render_service._strip_beep_lead 保留为下游幂等防御副本
  (上游已剥后二次跑实测 stripped=0)
- Redis TTS 缓存 10 分钟 TTL 自然过期, 无需清存量

**流式轨留档(synthesize_stream docstring)**: 流式 PCM 同带前导
但形态不同(0-0.35s 宽带脉冲×4-5 + 2.2s 起语音, _tts_stream.wav
频谱实证)——生产关闭暂不透; 开启前须补首块缓冲清洗(能量检测
方案已注释留档)。

**生产部署与实证**: scp llm_client.py → docker compose up -d
--build backend → 生产 /api/xiaozhu/tts 实测合成下载, 首段静音
模式 0.838s(正常语音停顿)——嘟嘟锚点 0.650s 消失; **用户实测
确认"嘟嘟消除了"**。

**回归**: test_xiaozhu_joyvoice 81/81、test_sv73_script+sv73_dh
16/16 全绿(TTS 断言语义兼容清洗)。
