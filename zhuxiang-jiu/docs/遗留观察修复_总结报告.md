## 一、修复背景与目标

上一轮全站模块化检查（13 模块 221 端点收官）遗留两项观察：

1. **AUTH_MODE 未设置**（默认 compat）——X-Role 头兼容通道可伪造身份（本会话 13 轮 E2E 均靠此通道，它同时也是攻击面），建议切 strict
2. **评分器注册表增长至 64 项**——依赖注册表数量的断言须动态化，8 个 unknown 状态评分器语义待澄清

本轮从方案设计到落地实施，完成了评分器治理 + AUTH_MODE 切换全链路（阶段 A/C/D + 前端自愈修复）。

## 二、评分器注册表治理（提交 4e15f8e + a4e487b）

### 2.1 根因定位

`SCORER_REGISTRY`（ai_learning_service.py，64 项）混装两类评分器：

| 类型 | 数量 | 机制 |
|---|---|---|
| 可学习型 | 56 | 有 WEIGHTS 类映射 + DECISION_THRESHOLDS，走 Hedge 学习周期 |
| 治理档案型 | 8（batch 41-48） | 走 46 号治理审批总线（submit_change 建议书），权重机制在各模块自己的 registry（pay71 参数版本状态机等），**设计上不参与 Hedge 学习** |

`default_weights()` 的 `_SCORER_CLASSES` 无这 8 项映射 → `run_learning_cycle` 抛 KeyError → hub retrigger 捕获后标 `unknown`。**unknown 不是缺陷，是 retrigger 无差别遍历越过了类型边界**。

### 2.2 治理内容

- `GOVERNANCE_ONLY_SCORERS`（frozenset 8 项）+ `is_learnable()` 分型判定
- hub `retrigger_learning` 全量只遍历可学习档案（64→56），响应透出 `governanceOnly=8`；单指定治理型返回 `governance_only` 语义（取代 KeyError→unknown）
- `validate_registry()` 双不变量校验：治理型 ID 无悬挂 ⊆ SCORER_REGISTRY；DECISION_THRESHOLDS 键 ⊆ 可学习集
- `overview()` 透出 `registryCheck` + `learnable` 字段（口径归一）
- 三处过时 docstring 修正（"17/16 档案"→动态描述）

### 2.3 验证与顺带修复

- 本地：test_hub 132/132 + test_ai_learning 41/41 + ruff 零
- 生产部署重建后实测：retrigger `total=56, governanceOnly=8, statuses 全 skipped`（**8 个 unknown 归零**）、registryCheck `ok=true`
- 顺带修复 test_ai_learning 两处存量硬编码断言（`==56` 在注册表增长至 64 后注定失败——治理型入册即触发，与第 6 类陷阱"注册表动态增长"同源）

## 三、AUTH_MODE 切 strict 全链路

### 3.1 阶段 A：前端 Bearer 全量覆盖（提交 f48049e，compat 下零行为变化）

调研发现前端基建已就绪：`js/auth.js` 完整 JWT 工具链（登录/刷新/`apiHeaders()`），17 个文件已接入；**25 个文件仍靠裸头**。

改造 28 文件（+226/-32）：
- 14 个 js：9 个函数式 `headers()`/`adminHeaders()` 叠加 `Auth.apiHeaders()`、2 个 `ADMIN_HEADERS` 常量改函数（trust-risk/xiaozhu-dashboard）、3 个 widget 内联叠加（ai-hub-widget×3 处/chat-widget/xiaozhu-widget）
- 13 个 HTML 补引 `js/auth.js`（dashboard 配套页 + service.html + xiaozhu-fc-redteam 内嵌脚本）

双模式范式：**未登录保留 compat 裸头（行为零变化）+ 登录叠加 Bearer（strict 就绪）**；防御式 `typeof Auth` 兼容浮动组件宿主页未引 auth.js 场景。

冒烟 test_authmode_stage_a.py 12/12：裸头 200 零回归 / admin Bearer 叠加与单独均 200 / member Bearer + 伪造 X-Role → 403（中间件 JWT 声明覆盖伪造头，安全设计实证）。

### 3.2 阶段 C：生产切换（提交 8a333f2 + 085b397）

**切换前置补丁（硬阻断项）**：4 个第三方回调端点不在白名单（微信/支付宝支付回调、退款、付款、物流轨迹——服务器回调无本站 JWT），strict 下会 401 打断资金链路。入 `PUBLIC_EXACT`（安全性由自有验签保障：微信 APIv3 / 支付宝 RSA2 / 物流渠道签名）。test_auth_middleware 28→32 全绿（新增 test_25b 回调白名单断言）。

**切换**：`.env` 追加 `AUTH_MODE=strict`（原无该行，须 grep 追加而非 sed 替换）+ 重建容器。

**九项验证矩阵 9/9**（容器内 + HTTPS 入口双口径）：健康探针 200 / 游客公开 GET 200 / 登录 200 / Bearer 管理端点×2 200 / **裸头 X-Role 401（strict 生效，伪造头通道封死）** / 回调×2 业务层可达 / admin 会话通道正常。

### 3.3 阶段 D：E2E 裸头范式验证 + 回归发现（提交 89c2a1b）

**范式验证**：
- 旧裸头范式失效实证：管理面 X-Role / 用户面 X-Member-Id 四类代表请求全部中间件 401（compat 裸头 E2E 范式正式失效，留痕）
- JWT 化新范式（hub 试点）15 项全绿：`get_jwt()` 登录 → Bearer 全链（capabilities/ops 面/retrigger 零副作用 governanceOnly=8/member Bearer→403 权限边界/用户面 points 200）。**后续所有 E2E 须先 POST /api/auth/login 取 accessToken**（member1=13800000001 / member3=13800000002 站点管理员）

**strict 真实回归发现（nginx 401 日志实证法）**：切换后 500 条 401（477 浏览器流量）分布定位两类问题：

| 问题 | 实证 | 处置 |
|---|---|---|
| 换肤铁律被打断 | site-theme/active ×64 | ✅ PUBLIC_GET_PREFIXES 补录 `/api/site-theme/`（GET 公开不降级——管理子路径仍由路由层 `_require_admin` 把守） |
| 合作浏览面 | venue/partners ×33、venues | ✅ 同上补录 |
| token 过期用户 | member/profile ×65、wallet/info ×51 等"我的"面 | ⚠️ 前端自愈修复（见 3.4） |

另留档：dist 调用点全量盘点（496 静态路径 / 475 白名单缺口清单）——后续按"游客实际触达"（nginx 401 实证）增量补录，不全量公开。

### 3.4 方案 (a)：前端 401 自愈工程修复（提交 71e27f2）

**分析反转发现**：dist 的 app 包 `requestWithRetry` **已有** 401→refresh→重试链（全天 103 次 refresh 200 在工作），但 common chunk"我的"面调用（`f.WY` 直调 `Taro._request`）不走自愈——实锤：15:57 会话连发 6 个 401 无一触发 refresh。问题不是"没有自愈"，而是"自愈没覆盖全请求链"。

**双文件 minified 锚点补丁**（dist_auth401_patch.py）：

| 文件 | 改动 |
|---|---|
| app chunk | `refreshSession` 定义后挂 `window.__AUTH401__` 全局桥（复用既有刷新逻辑，刷新成功返回新 Bearer 头） |
| taro chunk `_request`（所有请求公共出口） | 响应分发处加 401 拦截：`/api` 前缀 + 非 auth/sms/entry + `__r401` 单次标记 → 桥刷新 → 带新 Bearer 重发；桥缺失/失败原样透传（增量兼容） |

防死循环三重保障：端点排除 + 单次重试标记 + 桥失败透传。

**部署（immutable 缓存绕过）**：nginx 对 `/js/` 有 30 天 immutable 强缓存——no-cache 头对已缓存旧版无效（immutable 不 revalidate），改用 **chunk 改名**：`app.a401fix.js` / `taro.a401fix.js` + index.html 引用更新（引用链分析确认仅 index.html 两处引用、零交叉引用）。老名文件保留兜底；index.html 本身 no-cache，用户下次访问必切新版。nginx no-cache 中间态配置已 revert。

**浏览器端到端验证（生产实站）**：篡改 `auth_session.accessToken` 为 `expired.token.test` → 刷新页面 → 网络序列"坏 token 请求 401 → POST /api/auth/refresh → 同批 API 重试成功" → localStorage 自动写回新 JWT（新 jti）→ 数据完整恢复，**未踢登录页** ✓；首页无白屏/JS 报错（补丁语法完好）✓。

## 七、陷阱与范式沉淀

1. **dist 反转陷阱**：修复前必须先实证"缺陷定位"——app 包已有自愈链（103 次 refresh 200）但覆盖不全，盲目重写会引入重复逻辑。nginx 日志时间线（401 后有无紧跟 refresh）是判定调用链是否走自愈的直接证据
2. **immutable 缓存部署陷阱**：原地修改 hash 名 chunk 对已有缓存用户无效（immutable 不 revalidate）——必须 chunk 改名 + 入口引用更新；改前必查引用链（本例仅 index.html 两处引用）
3. **nginx 401 日志实证法**：strict 类全局切换的真实受损面判定，比语义猜测/全量调用点清单可靠（475 条缺口清单里真实受损只有 site-theme/venue/token 过期三类）
4. **minified 修改安全范式**：python 锚点式替换（锚点唯一性断言 + 括号自配对校验 + 备份 + 幂等恢复）
5. **回调端点豁免铁律**：第三方服务器回调（支付/物流）无本站 JWT，切任何全局认证前必须先入白名单（安全性由自有验签承载）
6. **GET 前缀公开不降级**：`/api/site-theme/` 类前缀公开后，管理子路径（admin/*）仍由路由层 `_require_admin` 把守（无注入头 → 403）
7. **AUTH_MODE 切换命令细节**：`.env` 原无该行时须 `grep -q || echo 追加`（sed 替换不命中）
