# 42号·管理端拦截面板操作指南

> 配套：[42号设计文档](AI无感开票模块42_设计文档.md) §2.5
> 面板定位：AI 无感开票的**拦截观察与人工兜底**工作台——reject 档（金额异常/高频拆分/风控信号）的复核、误拦截恢复、申诉处理、裁决真值学习回流。
> 现状：P0/P1/P2 全部落地（面板页面 + 申诉通道 + 裁决恢复 + 误拦截率 + 学习回流），本文档为纯操作手册。

---

## 一、面板入口与权限

| 项 | 说明 |
|----|------|
| 访问角色 | `X-Role: admin`（财务/风控岗） |
| 面板地址 | [ai-invoice-dashboard.html](../ai-invoice-dashboard.html)（本地直开，30s 自动刷新） |
| 数据源 | `GET /api/invoice/admin/decisions?action=reject`（拦截流水）+ `GET /api/invoice/admin/stats`（四档分布 + 误拦截率）+ `GET /api/invoice/admin/appeals`（申诉队列） |
| 刷新建议 | 面板 30s 自动刷新；学习回流区块为周操作，走 §三 学习回流端点 |

## 二、面板信息结构（四区块）

**顶部统计卡**（数据源 `admin/stats`）：
- 决策总数 / 自动开具数 / 待确认数 / **拦截数** / 引导收集数 / 自动化率
- **误拦截率** `falsePositiveRate = approved申诉数 / reject决策总数`（P2 学习真值源，>10% 需关注阈值松紧）
- 阈值参考：自动 ≥70 / 待确认 50-70 / 拦截 <50

**拦截列表**（数据源 `admin/decisions?action=reject`）：

| 列 | 字段 | 判读要点 |
|----|------|---------|
| 订单号 | orderId | 与业务后台订单详情关联跳转 |
| 会员 | memberId | 高频拆分常集中同一会员 |
| 评分 | score + factors | 四因子明细展开看哪项拖分 |
| 拦截原因 | detail | "金额低于下限" / 因子降档 |
| 拦截时间 | decidedAt | 申诉时效参考 |
| 操作 | — | 见 §三 |

## 三、拦截处置五步法（核心操作流程）

### 第 1 步：复核拦截原因（判断误拦 vs 正确拦截）

展开决策流水的 `scoreSnapshot.factors`，按拖分因子分流：

| 拖分因子 | 判读 | 动作方向 |
|---------|------|---------|
| `order_risk` = block/review | **先查订单风控**（订单模块风控面板），风控误判则发票可恢复 | 转订单风控复核，确认后走第 3 步恢复 |
| `frequency` 低分 | 该会员 24h 开票 ≥5 张，查是否拆分开票（多笔小单同日报销） | 正确拦截（拆分开票违规）→ 保持拦截 |
| `amount_reasonable` 低分 | 金额相对该会员历史异常（首单巨额定酒类发票） | 联系会员核实 → 真实采购走第 3 步 |
| `title_confidence` 低分 | 新抬头首次使用 | 正常谨慎，非误拦 → 无需处理 |

### 第 2 步：查申诉队列

会员在"我的发票"页对拦截决策提交申诉（`POST /api/invoice/orders/{orderId}/appeal`，仅 reject 档、一单一申诉幂等）。申诉进入面板队列（`GET /api/invoice/admin/appeals?status=pending`），逐条处理：

**裁决操作**（`POST /api/invoice/admin/appeals/{appealId}/decide`，X-Role: admin）：
- 确认误拦 → `{"approve": true, "reviewer": "工号", "note": "核实依据"}` → 申诉置 approved，决策流水 detail 标注"申诉恢复"，通知会员走第 3 步补开
- 维持拦截 → `{"approve": false, ...}` → 申诉置 rejected 归档（该真值随后供学习回流判定 AI 拦对了）
- 重复裁决返回 409（仅待裁决可处理）

### 第 3 步：误拦恢复——人工补开

复核确认误拦后，两条路径（**均已可用**）：

**路径 A（推荐）**：通知会员在"我的发票"页手动触发
```
POST /api/invoice/orders/{orderId}/request   （会员端, X-Member-Id）
```
决策流水自动升级（reject → auto_issue，detail 记"用户手动补开"）。

**路径 B**：管理员直接开票（19号手动通道，需注意抬头信息由会员提供）
```
POST /api/finance/invoice/issue   （member 端点, 用会员 ID 与抬头）
```

### 第 4 步：正确拦截——归档观察

拆分开票等正确拦截**保持不动**（发票不开即无税影响）；面板按月导出 reject 流水给财务备查（用 `GET /api/invoice/admin/decisions?action=reject` 导出）。

### 第 5 步：周度学习回流（P2，让 AI 越用越准）

申诉裁决即人工真值：**approved = AI 拦错了（负反馈），rejected = AI 拦对了（正反馈）**。每周执行一轮三连操作（`X-Role: admin`，前端面板暂无此区块，走 API/运维脚本）：

```bash
# 1) 批量回流: 已裁决且未回流的申诉 → 第25档案反馈(幂等, 重复执行自动跳过)
POST /api/invoice/admin/learning/collect
#    → {"submitted": 2, "skipped": 1, "results": [...]}
#    每条反馈: correct=拦对(正反馈 reward +0.5) / 误拦(负反馈 -0.5)

# 2) 触发一轮 Hedge 学习(反馈不足 min_feedback 条会返回 409, 属正常保护)
POST /api/invoice/admin/learning/run
#    → 更新 invoice_decision_gate 因子权重

# 3) 查看学习状态(可选, 复核权重量变)
GET  /api/invoice/admin/learning/status
#    → appeals{total, decided, fed} + weights 视图
```

**运营口径**：
- 节奏：每周一次（攒够 `min_feedback` 条裁决再触发 run，避免频繁微调）
- 效果观察：对比 `admin/stats` 的 `falsePositiveRate` 周环比；持续 >10% 说明阈值过紧，学习回流会逐步纠偏
- 安全性：collect 幂等（appealFed 标记），单条失败不阻断批量；run 失败不影响线上决策（权重热更新，决策始终走最新权重）

## 四、判定口径速查（什么该拦、什么该放）

| 场景 | 判定 | 依据 |
|------|------|------|
| 同会员 24h 第 5 张票 | 拦 | 频次因子归零，疑似拆分开票规避发票限额 |
| 订单被风控 block | 拦 | 风控信号直通，先解风控再谈发票 |
| 首单 ¥5 万大额 | 拦后核实 | 金额合理性降档，防虚开 |
| 新抬头首次 | 不拦（分数够则自动开） | 置信度低但其余因子正常仍可过 70 线 |
| 零元/极小订单 | 拦（硬规则） | 低于 `INVOICE_MIN_AMOUNT`，无需人工 |
| 企业抬头无税号 | 不会到面板 | 抬头簿录入时已 409 拒绝 |
