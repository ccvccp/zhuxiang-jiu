# 05号收款 · 真实支付网关接入配置步骤

> 适用: 钱包充值 / SVIP 购买 / (后续)订单支付从 mock 渠道切换为真实收款。
> 铁律已就位: 业务端点只创建支付单, 权益/资金发放只发生在支付回调成功之后
> (payment_service._dispatch_business), 切换渠道模式不改变该语义。
> 生成日期: 2026-09-15 | 对应提交: fe6ddec(支付前置铁律)

---

## 一、渠道三态语义(先看懂再配置)

`PAY60_CHANNEL_MODE` 环境变量控制渠道行为(与 pay60 渠道适配层同源口径):

| 模式 | start_pay 行为(业务场景) | 说明 |
|---|---|---|
| `mock`(默认) | 确定性回执自动落账, 返回即 paid + dispatch | 当前生产状态, 全链留痕可审计 |
| `real` | 返回 paying + payParams, **等待真实渠道回调** | fail-hard: 凭证未注入直接拒绝, 绝不静默降级 |
| `mock_fallback` | 尝试 real, 失败回退 mock(留痕 fallback=true) | 灰度观察用 |

- 未接线场景(retail 订单等)不受自动落账影响, 始终等待显式回调。
- 回调幂等: 24h TTL 渠道交易号锁 + paid 状态机双保险, 网关重复通知不重复入账。
- 支付单超时: 30 分钟(`PAY_EXPIRE_SECONDS`), 超时可 `POST /api/payment/{pay_no}/close` 关闭。

## 三、代码任务清单(real 渠道执行器——当前为占位, 切 real 前必须完成)

> 诚实声明: `PAY60_CHANNEL_MODE=real` 的**开关与等待回调语义已上线**,
> 但以下三块真实执行代码尚未接入, 直接切换将导致支付单停在 paying 无法落账。

### P0-1 渠道执行器(统一下单)

- 位置: `pay60_service.execute_channel` real 分支(当前仅校验 `PAY60_CHANNEL_KEY` 存在即出占位回执 `REAL{flowId}`) + `payment_service.start_pay` real 分支(返回 payParams 元数据)
- 任务: 接入微信支付 V3(JSAPI/H5/Native)与支付宝(openapi-sdk)统一下单:
  1. 按 payChannel 分发到对应网关 SDK, 以支付单(payNo/amount/expireTime/回调地址)下单;
  2. 将真实预支付参数回填 `payParams`(微信 `prepay_id`+签名五元组 / 支付宝支付链接);
  3. 网关侧单号回写 `channelTradeNo` 预留位(下单即回填, 回调终态覆盖)。
- 建议 SDK: `wechatpayv3`(微信) / `alipay-sdk-python`(支付宝), 依赖加入 requirements.txt。

### P0-2 回调验签(安全关键——不实现等于开放免费入账)

- 位置: `routes/payment_routes.py` 的 `POST /api/payment/callback/pay`(当前无鉴权)
- 任务: 按渠道验签后再进入 `pay_callback`:
  - 微信: 校验 `Wechatpay-Signature`/`Wechatpay-Serial`/`Wechatpay-Timestamp`/`Wechatpay-Nonce` 头 + APIv3 解密 resource;
  - 支付宝: RSA2 公钥验签 `sign` 字段;
  - 验签失败返回 401 并留痕(疑似伪造回调计数告警)。
- ⚠️ 铁律: **该端点未验签前严禁切换 real 模式上线真实收款**——否则任何人可
  伪造 channelTradeNo 直接触发入账/SVIP 开通。

### P1-3 前端拉起支付

- 位置: `taro-app/src/api/payment.ts` 的 `completePay`(轮询已就绪: 2s×30 次, paid/failed/closed/timeout 终态判定)
- 任务: `startPay` 返回 real payParams 后:
  - 小程序: `Taro.requestPayment`(JSAPI 五元组);
  - H5: 微信 H5 支付跳转链接 / 支付宝重定向;
  - 用户取消 → 调 `POST /api/payment/{pay_no}/close`(reason=USER_CANCEL) → 提示「支付未完成」。

### P2-4 支付单超时自动关闭调度器(可选加固)

- 现状: expireTime 已落库, 手动 close 端点已备; 建议补 15 分钟周期扫描器
  (复用 order_timeout_scheduler 范式)自动关闭过期单, 防待支付单堆积。

## 四、配置步骤(代码就绪后按序执行)

### 4.1 服务器 .env 注入凭证(不落盘原则)

编辑 `/opt/zhuxiang/.env` 追加:

```bash
# --- 05号收款 · 渠道三态(PAY60) ---
# 灰度期建议先 mock_fallback; 稳定后切 real
PAY60_CHANNEL_MODE=mock_fallback

# 渠道主凭证(pay60 fail-hard 校验项; real 模式缺失即拒绝)
PAY60_CHANNEL_KEY=<微信APIv3密钥 或 支付宝应用私钥>

# 分渠道凭证(渠道执行器读取, 建议 JSON 单键或分键)
PAY60_WECHAT_MCHID=1900000000
PAY60_WECHAT_APPID=wxXXXXXXXXXXXXXXXX
PAY60_WECHAT_APIV3KEY=<32位APIv3密钥>
PAY60_WECHAT_SERIAL_NO=<证书序列号>
PAY60_WECHAT_PRIVATE_KEY=<商户证书私钥PEM 或 挂载路径>
PAY60_ALIPAY_APPID=2021000000000000
PAY60_ALIPAY_PRIVATE_KEY=<应用私钥PEM 或 挂载路径>
PAY60_ALIPAY_PUBLIC_KEY=<支付宝公钥 或 挂载路径>
```

权限收紧:

```bash
chmod 600 /opt/zhuxiang/.env
```

> 私钥建议以文件挂载注入(`docker-compose.yml` volumes 只读挂载
> `./data/keys:/app/data/keys:ro`), .env 中只存路径引用, 凭证永不落镜像。

### 4.2 重建容器生效

```bash
cd /opt/zhuxiang
docker compose up -d backend        # env 变更触发容器重建
docker exec zhuxiang-backend-1 printenv | grep PAY60   # 三层自验之一
```

### 4.3 渠道注册(管理端, AI 路由评分器数据源)

```bash
# 微信(third_party)
curl -X POST https://zxjiu.com/api/payment/channel \
  -H "X-Role: admin" -H "Content-Type: application/json" \
  -d '{
    "channelCode": "wechat", "channelName": "微信支付",
    "channelType": "third_party",
    "supportedMethods": ["jsapi", "h5", "native"],
    "supportedScenes": ["order_pay", "wallet_deposit", "member_svip"],
    "merchantId": "<mchid>", "feeRate": 0.006, "feeType": "percent",
    "settleCycle": "T+1", "minAmount": 0.01, "maxAmount": 20000
  }'

# 支付宝(third_party)同构; 银行直连(bank)按需
```

场景-渠道适配矩阵(路由评分)已含 `member_svip`(第三方扫码最优)。

### 4.4 网关侧回调地址配置

| 渠道 | 配置处 | 填写值 |
|---|---|---|
| 微信 | 商户平台「支付配置」 | `https://zxjiu.com/api/payment/callback/pay` |
| 支付宝 | 开放平台「应用网关」 | 同上(异步通知 notify_url 下单时传入同一地址) |

### 4.5 切换验证清单(逐层)

1. **容器 env**: `printenv | grep PAY60` 确认三态与凭证注入;
2. **mock 回执关闭**: 钱包充值创建支付单 → `POST /api/payment/{pay_no}/start`
   返回 **paying**(非 paid)——real/灰度回退前不再自动落账;
3. **小额真实支付**(¥100 充值): 真实付款 → 回调验签通过 →
   `pay_callback` paid + `dispatch.granted=true` → 余额入账,
   `channelTradeNo` 为真实渠道单号(非 `MOCK`/`REAL` 前缀);
4. **幂等复核**: 网关重推通知(微信会重试 15 次)→ 不重复入账;
5. **前端**: 支付宝 H5 跳转返回 / 微信支付完成 → 轮询 paid → 余额刷新;
6. **对账**: 次日 `POST /api/payment/reconciliation/start`(admin)核对渠道账单与平台流水。

### 4.6 灰度路径建议

```
mock(当前) → mock_fallback + 凭证注入
           → 观察渠道执行器成功率与 fallback 留痕
           → 稳定后 PAY60_CHANNEL_MODE=real 全量
```

`mock_fallback` 下 real 执行失败自动回退 mock(支付单留痕 `fallback=true`),
业务不中断, 是渠道执行器上线的标准灰度档。
