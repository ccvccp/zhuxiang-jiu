# 案例-20261021-599满减臆想断言

## 一、现象

2026-10-21 竹盾 T2.2 建"特性测试基线"（test_feature_baseline.py 16 条断言
锁定现行核心行为）时**首跑即红**：运费/优惠相关断言失败。测试此前一直是
绿的——但绿的原因是断言与实现**错着对**：断言描述的是一个臆想的业务规则，
代码实现的是另一个真实规则，两者各自"稳定"所以从不报错。

## 二、根因

AI 起草测试断言时**臆想了"满 599 减 30"的满减业务规则**写进断言，而真实
代码（811e45e7 统一后的 order/checkout 运费规则）是**满 ¥99 免运费、
否则 ¥10**——599 档只是免运费，根本没有满减 30。断言没对照业务事实与
实际代码，形成"假绿"：测试通过 ≠ 行为正确，只等于断言与实现自洽。
若基线照抄该断言，将来真实规则变化反而会误报，或臆想规则被"锁"进基线。

## 三、错误代码/配置

臆想断言语义（b0dbca95 基线建立前的旧测试形态）：

```python
def test_checkout_599():
    # 臆想业务规则: "满 599 减 30"
    assert calc_total(cart_of_599) == 599 - 30      # 实现无此规则 → 曾因实现同样臆想而绿
```

## 四、正确写法

特性基线的口径 = **锁现行为非臆想**（提交 b0dbca95）：16 条断言全部
从**当前真实实现**取证后回填（B1 运费 ¥99 免邮 6 条 / B2 评价双写链路
6 条 / B3 注册面 age_gate 4 条），pytest 16/16 + ruff 过。首跑红正是
基线的价值：把臆想断言与真实实现的分歧当场暴露，修断言而非改代码迁就。

## 五、预防规则

测试断言禁止臆想业务规则——断言必须"取证自现行为或用户业务确认"；
AI 起草的业务断言一律人工业务校对后才可入基线（79 号铁律"AI 起草、
用户校对"的同源教训）——挂 NEW-T3.4（consult 分级置信度：无出处断言
标低置信）。
