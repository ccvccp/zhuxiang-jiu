# 案例-20261021-qr白名单死条目

## 一、现象

2026-10-21 扫码登录全链断裂：scan/exchange/cancel 三步全部被 auth 中间件
401 拦截，手机端扫码后无法换取登录态（confirm 401 为设计内登录态，非事故面）。
竹盾红线标记 R2（鉴权体系）关联面。

## 二、根因

PUBLIC_EXACT 白名单新增的 3 条条目为**无参形态**（/qr/scan 等），而实际路由为
`/qr/{qr_id}` **带参形态**。EXACT 全等匹配永不命中带参路由 → 三条目成为
"死条目"（永不匹配的白名单项），扫码链三步永久被拦。条目登记时未对照
L0-端点清单的实际路由形态逐条核验。

## 三、错误代码/配置

backend/core/auth_middleware.py PUBLIC_EXACT（e73f6800 修复前）：

```python
PUBLIC_EXACT = {
    ...,
    "/qr/scan", "/qr/exchange", "/qr/cancel",  # 死条目: 实际路由为 /qr/{qr_id} 带参形态
}
```

## 四、正确写法

删 3 条死条目 + 新增 PUBLIC_POST_PATTERNS **正则档**放行带参 POST 路由
（提交 e73f6800）。exchange 公开性靠 loginTicket 60s 一次性防重放保证，
零身份依赖；confirm 保持登录态（设计内）。同提交扫描器（scan_endpoints.py）
同步 POST 正则档，dead_exact 清零防复发。

## 五、预防规则

白名单新增条目必须与 L0-端点清单实际路由逐条对照**（含参数形态）**——
挂 NEW-T1.2（audit 鉴权可达）与 NEW-T2.3（contract 死条目检测），
M1/M2 回放基准案例。
