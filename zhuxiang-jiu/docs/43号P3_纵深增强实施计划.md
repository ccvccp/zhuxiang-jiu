# 43号·AI智能安全管理模块 P3 可选方向实施计划 v1.0

> 配套：[43号交付总结](AI智能安全管理模块43_交付总结.md) §八
> 定位：P0-P2 已交付完整安全免疫系统（网关/评分/申诉/UEBA/态势/学习）；P3 为**纵深增强**——挑战验证真实化、时空因子精细化、行为序列建模、响应侧试探检测。
> 调研结论（2026-09-03）：39号已有设备指纹基建（`entry_service.hash_device_id/trust_device`）；41号有外部 API 三态通道范式（HMAC 签名+幂等+回调校验）；网关 send 当前未包装（响应侧观测需新增拦截层）；登录无结构化事件流（序列建模需自建留痕）。

---

## 一、四个方向总览（按价值/成本排序）

| 编号 | 方向 | 核心价值 | 依赖基建（已确认存在） | 建议优先级 |
|------|------|---------|----------------------|-----------|
| P3-1 | 网关响应钩子（D4 完整落地） | 填补当前唯一参数化口径的检测器，**纯内部改造零外部依赖** | security_gateway `__call__` send 包装 | ★★★ 高（先行） |
| P3-2 | 真实验证码通道 | mock 应答零防护 → 真人验证，enforce 前置条件 | 41号三态通道+HMAC 范式平移 | ★★★ 高 |
| P3-3 | GeoIP + 设备指纹 | geo_time 因子从"时段"升级为"地理+设备"多维 | 39号 fingerprint 基建直接复用 | ★★ 中 |
| P3-4 | 登录序列建模 | 跳步攻击检测（登录→直奔敏感端点） | 自建事件留痕（entry `_record_event` 范式） | ★ 中（观察期长） |

**实施顺序建议**：P3-1 → P3-2 → P3-3 → P3-4。理由：P3-1 零外部依赖且是 D4 完整性的收口；P3-2 是 enforce 上线的实质前提（mock 应答对自动化攻击无效）；P3-3/P3-4 为因子精细化，可并行或延后。

## 二、P3-1：网关响应钩子（D4 试探偏离完整落地）

### 现状与差距
- D4 检测器（403 堆积试探）当前为**参数化口径**（`forbidden_hits` 由调用方传入），网关自身不观测响应状态码——`SecurityGatewayMiddleware.__call__` 所有放行路径直接 `await self.app(scope, receive, send)` 原样透传。

### 实施方案

**① send 包装层**（core/security_gateway.py）：

```python
class _SendWrapper:
    """拦截 http.response.start 捕获状态码, 其余消息原样透传"""
    def __init__(self, send):
        self._send = send
        self.status_code = None

    async def __call__(self, message):
        if message["type"] == "http.response.start":
            self.status_code = message.get("status")
        await self._send(message)

# __call__ 放行路径改造:
wrapper = _SendWrapper(send)
await self.app(scope, downstream_receive, wrapper)
# 放行后(wrapper.status_code 可得):
await self._after_response(ip, member_id, wrapper.status_code)
```

**② 403 堆积统计**（security_repository）：
- Redis：`zhuxiang:security43:forbidden:{memberId}` INCR + EXPIRE 86400（24h 滚动）
- 内存：时间戳列表（与 rate 计数同范式）

**③ D4 完整接入**：
- `_do_process` 调用 `compute_deviation` 时实时查询 403 计数传入 `forbidden_hits`（替换参数化口径）
- 401 也计入（鉴权失败堆积同为试探信号，权重减半）

**④ 新端点**：无（复用既有 deviations 查询）

### 测试与验收
- 专项：send 包装不破坏响应（正常 200/业务 409/404 全透传）/ 403 计数累计 / 24h 滚动过期 / D4 触发（3 次 403 后偏离画像含 D4_probe）/ 越权试探 E2E（未认证连打管理端点 → identity_risk 降分）
- 实机：Docker 内连续 403 请求 → deviations 端点可见 D4 命中

### 关键风险
- send 包装对 SSE/流式响应的兼容（本项目无 SSE 端点，风险低；仍需回归全量）
- 性能：包装层每请求一次闭包，微秒级，可忽略

## 三、P3-2：真实验证码通道（极验/hCaptcha 替换 mock）

### 现状与差距
- 挑战应答为 mock（非空即过）——自动化脚本可直接伪造应答绕过挑战档，enforce 态下挑战档实际无防护。

### 实施方案（41号直发通道三态范式平移）

**① 三态开关**：`SECURITY_CAPTCHA_MODE = mock(默认) / real / mock_fallback`
- mock：现状（确定性应答，测试友好）
- real：fail-hard（真实服务商校验失败即挑战失败）
- mock_fallback：真实轨超时/故障回退 mock（回执标记来源，灰度观察）

**② 服务商客户端**（services/captcha_client.py，参照 `ride_dispatch_service._platform_real`）：
- 极验 v4（国内合规首选）：register 接口拿 challenge → 前端渲染 → validate 二次校验（server-side），HMAC 签名头（captcha_id/captcha_key）
- 备选 hCaptcha（海外）；两者均留 provider 抽象
- httpx timeout=10、传输错误重试 1 次、幂等（验证票据一次性消费）

**③ 挑战端点改造**（security_routes / security_service）：
- `challenge/verify` 请求体增加 `captcha_token`（前端组件回传）
- real 模式：调服务商 validate → 通过才发通行证；失败 409
- 回调/通行证发放逻辑不变（TTL 900s）

**④ 前端面板配套**：
- 管理面板无需改（挑战是会员侧）
- 会员侧挑战页（P3 新增轻量页 challenge.html）：嵌入极验组件 → 应答 → 调 verify 端点

**⑤ 凭证管理**：`CAPTCHA_PROVIDER`（geetest/hcaptcha）/ `CAPTCHA_ID` / `CAPTCHA_KEY` 环境变量 + docker-compose 暴露（.env 注入，对齐 DRIDE_PARTNER_* 模式）

### 测试与验收
- 专项：三态切换语义 / mock 确定性 / real 失败 409 / fallback 回退标记 / 票据一次性（重放拒绝）
- 实机：mock 轨全链路回归（既有 21 项不破坏）；real 轨待凭证后冒烟（同 41号"待外部凭证"口径）
- **凭证获取待办**：极验商户后台注册（企业资质）→ 拿 captcha_id/key → .env 配置 → real 冒烟

### 关键风险
- 极验审核周期（约 1-3 工作日）——与 41号滴滴凭证同口径，先 mock/mock_fallback 上线不阻塞
- 会员端无既有极验 JS SDK 依赖，需引入静态资源（本地托管，防 CDN 供应链风险）

## 四、P3-3：GeoIP 地理库 + 设备指纹（geo_time 因子精细化）

### 现状与差距
- geo_time 因子当前仅"凌晨 0-5 点降分"（时段单维）；39号已有完整设备指纹基建未被安全模块利用。

### 实施方案

**① 设备指纹接入**（复用 39号，零新建）：
- 网关从请求头读 `X-Device-Id`（39号登录时已由前端生成并 hash_device_id 登记）
- 身份风险增强：**陌生设备**（信任设备表 `entry` 的 trust_device 之外）打敏感端点 → identity_risk 降分
- 检测维度：同账号 24h 内设备数 ≥3（撞库信号）

**② GeoIP 离线库**（无外部 API 依赖）：
- 采用纯离线方案：`geoip2` 库 + MaxMind GeoLite2-City.mmdb（免费，需注册下载，季度更新）
- 落地动作：首次加载 mmdb 至内存；按需懒加载（文件不存在则 geo 功能静默关闭）
- 检测维度：**异地登录速度**（同账号两小时内跨省 IP 变更 → geo_velocity 信号，30号 auth_risk 已有同名因子概念，口径对齐）
- 因子改造：geo_time 更名 `geo_device`（保持向后兼容：旧名继续可读），维度扩为 时段/异地跳变/陌生设备 三合一

**③ 反代头处理**：网关 IP 提取支持 `X-Forwarded-For` 第一跳（当前直连 client.host；容器化直连场景不受影响，云部署时生效）

### 测试与验收
- 专项：陌生设备降分 / 设备数堆积 / geo 库缺失静默关闭（零影响）/ mmdb 加载与查询 / XFF 解析
- 实机：容器内无 mmdb → 功能关闭回归照常（默认零影响路径必须全绿）

### 关键风险
- GeoLite2 下载需 MaxMind 免费账号（许可证密钥），CI/容器构建需离线缓存 mmdb 文件（不入 git，>60MB）
- 设备指纹依赖前端配合（已有 X-Device-Id 头则增益，无则中性不惩罚）

## 五、P3-4：登录序列建模（跳步检测）

### 现状与差距
- 登录无结构化事件流（仅 logger + last_login_at 单值）；39号 entry 模块有 `_record_event`（eventId/success/riskScore/deviceId）但仅覆盖入口面，非全站。

### 实施方案

**① 统一安全事件留痕扩展**（复用 security_events 表，不建新表）：
- auth_service.login / login_by_sms 成功/失败钩子（best-effort 火后不管范式）→ security_events 增加 `action: "auth_event"` 档（含 memberId/deviceId/ip/success）
- 网关侧无需改（登录在业务层，钩子在 service）

**② 会话序列跟踪**：
- 登录成功时生成 `sessionSeq`（Redis：`security43:session:{memberId}`，TTL 与 JWT access 2h 对齐）
- 网关请求携带有效 member_id 时，若 session 缺失（未登录先访问）→ 记 `pre_auth_probe` 计数

**③ 跳步检测器（D5，新增第五检测器）**：
- 模式：登录成功后 N=3 个请求内直奔敏感端点（admin/finance/export）且无任何常规浏览行为 → 跳步信号（正常用户登录后先看首页/订单列表）
- 实现会话内请求序列环形缓冲（Redis List，最近 5 个 module），D5 在 UEBA compute_deviation 中合议

**④ 撞库联动**：登录失败堆积（同账号 24h ≥5 次失败）→ 直接生成 security_events 预警（不依赖序列）

### 测试与验收
- 专项：auth_event 留痕 / 会话序列缓冲 / 跳步命中（登录→连打 admin 3 次）/ 正常序列不误报（登录→首页→订单→admin）/ 撞库预警
- 实机：Docker 登录→敏感端点序列 → deviations 可见 D5

### 关键风险
- 误报：脚本化正常用户（API 直调不做浏览）会被命中——**D5 仅降分不处置 + 裁决通道兜底**（对齐 behavior_alert 口径）
- 观察期：建议 D5 上线后 observe 至少两周统计误报率再参与联动
