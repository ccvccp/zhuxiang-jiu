# 并发控制与事务一致性技术文档

> 适用范围：`zhuxiang-jiu` 前端库存/订单服务（H5 / 小程序 / APP 共享逻辑）
> 维护基线：2026-08 修复后的版本（Mutex FIFO + 事务快照两处关键修复）
> 关联代码：`js/mutex.js`、`js/inventory-service.js`、`js/main.js`

---

## 1. 背景与目标

库存扣减/回补、订单号生成、优惠券核销等场景存在异步竞争条件。若不加串行化，会出现：

- **超卖**：库存为 1 时多个并发请求同时读到"可扣"，各自扣减后写回，最终库存为负。
- **重复**：同一订单号被生成两次、同一张券被核销两次。
- **丢更新**：多个事务读到同一陈旧快照，各自覆盖写回，N 次操作只生效 1 次。

本系统的并发控制由两层组成：

| 层 | 职责 | 实现 |
|----|------|------|
| **悲观锁层（Mutex）** | 串行化同一商品的临界区，保证不超卖/不重复 | `mutex.js` 的 `Mutex` class（FIFO 队列） |
| **事务层（快照模式）** | 单次扣减/回补的原子性：要么全部提交、要么全部回滚 | `inventory-service.js` 的 `createAdapter` |

两层缺一不可：**锁保证串行，事务保证原子**。锁不替代事务（锁内仍可能因异常需要回滚），事务不替代锁（多个事务并发读同一快照会丢更新）。

## 2. Mutex FIFO 实现

### 2.1 为什么是 FIFO 队列（而非 while+await 自旋）

旧实现用 `while (_holders[key]) { await _holders[key]; }` —— 所有等待者 `await` **同一个** Promise。`release` 调用 `resolve()` 时，**全部 N-1 个等待者都被唤醒**，仅 1 个胜出重新获锁，其余 N-2 个再次 `await`（同一个新 Promise）—— 呈 **O(n²)** 唤醒代价（thundering herd）。n=1000 时尚可（<1s），更大并发会急剧退化。

FIFO 实现：每个等待者持有**独立 Promise**，`release` 只 `resolve` **队首唯一一个**等待者（直接交接锁）。唤醒代价 **O(n)**，且严格保证公平（入队顺序 == 执行顺序）。

### 2.2 核心 API（`js/mutex.js`）

```js
class Mutex {
    constructor() {
        this._locked = {};   // key → true（是否被持有）
        this._queues = {};   // key → resolve 函数数组（FIFO 等待队列）
    }

    // 获取锁（阻塞直到成功，FIFO 公平）。返回 release 函数
    async acquire(key) {
        // 空闲：同步检查+设置（JS 单线程内原子，无竞争）
        if (!this._locked[key]) {
            this._locked[key] = true;
            return () => this._release(key);
        }
        // 竞争：入队，每个 waiter 独立 Promise
        return new Promise(resolve => {
            (this._queues[key] || (this._queues[key] = [])).push(resolve);
        });
    }

    // 释放（内部）：交接给队首唯一一个 waiter；无 waiter 则真正释放
    _release(key) {
        const next = this._queues[key] && this._queues[key].length
            ? this._queues[key].shift() : null;
        if (next) {
            // 交接：_locked 保持 true 不留空窗，新到者仍入队
            next(() => this._release(key));
        } else {
            delete this._locked[key];
            delete this._queues[key];
        }
    }

    // 单锁包装（自动获取/释放）
    async withLock(key, fn) {
        const release = await this.acquire(key);
        try { return await fn(); }
        finally { release(); }
    }

    // 多锁包装（按 key 升序获取，反向释放，避免死锁）
    async withLocks(keys, fn) {
        const sorted = [...new Set(keys)].sort();
        const releases = [];
        for (const k of sorted) releases.push(await this.acquire(k));
        try { return await fn(); }                    // 必须 await（见 2.4）
        finally {
            for (let i = releases.length - 1; i >= 0; i--) {
                try { releases[i](); } catch (e) { /* ignore */ }
            }
        }
    }

    isLocked(key) { return !!this._locked[key]; }
    getLockedKeys() { return Object.keys(this._locked); }
    clear() { this._locked = {}; this._queues = {}; }   // 测试用
}
// 全局单例：window.mutex = new Mutex()
```

### 2.3 三条路径一致性

为兼容 `mutex.js` 未加载的场景，三个模块各自带兜底实现，**全部为 FIFO**，行为一致：

| 路径 | 文件 | 主路径 | 兜底 |
|------|------|--------|------|
| 工具类 | `js/mutex.js` | `Mutex` class（`window.mutex` 单例） | — |
| 库存服务 | `js/inventory-service.js` | `_mutex.withLocks(...)` | `_acquireMutex`/`_withMutex`（`_mutexLocked`/`_mutexQueues`） |
| 主入口 | `js/main.js` | `_mutex.withLocks(...)` | 同上结构 |

兜底判定：`const _mutex = (typeof Mutex !== 'undefined') ? new Mutex() : null;`，`_withMutex` 优先走 `_mutex.withLocks`，无则走兜底。

### 2.4 正确性要点

1. **JS 单线程下 `acquire` 的"检查 `_locked` + 设置 `_locked`"是同步原子的**，不会出现两个任务同时通过空闲检查。
2. **交接（hand-off）期间 `_locked[key]` 保持 true，不留空窗** —— 旧锁释放到新锁持有之间没有间隙，新到者仍会入队，不会插队。
3. **`withLock`/`withLocks` 内 `fn` 必须 `await`** —— 否则 `finally` 提前释放锁，临界区尚未完成，锁形同虚设。
4. **`release` 必须真正让出锁**（delete 占位或交接）—— 旧 `while+await` 实现 `release` 只 `resolve` 不 `delete`，导致 `_holders[key]` 仍是已 resolve 的 Promise（truthy），后续等待者 `while` 永真 → 死循环（见 §4.1）。

## 3. 事务一致性（快照模式）

### 3.1 事务适配器 `createAdapter`（`js/inventory-service.js`）

每次 `deduct`/`restock` 是一个独立事务：BEGIN（建快照）→ 阶段3（扣减/回补 + 写流水 + 预警）→ COMMIT 或 ROLLBACK。

```js
function createAdapter(dbRef) {
    return {
        begin(ctx) {
            // 【关键】先 push BEGIN 再取快照：确保快照包含本次 BEGIN，
            // 否则 rollback 用快照恢复时会丢失本次 BEGIN（只剩 ROLLBACK），
            // 导致事务原子性校验 begins !== commits + rollbacks
            dbRef.db.tx_log.push({ type: 'BEGIN', time: new Date().toISOString() });
            const snapshot = JSON.parse(JSON.stringify(dbRef.db));
            return snapshot;
        },
        commit(_snapshot, ctx) {
            dbRef.db.tx_log.push({ type: 'COMMIT', time: new Date().toISOString() });
            writeDB(dbRef.db);   // 持久化到 localStorage
        },
        rollback(snapshot, ctx) {
            if (snapshot) {
                snapshot.tx_log.push({ type: 'ROLLBACK', time: new Date().toISOString() });
                dbRef.db = snapshot;   // 快照恢复
                writeDB(snapshot);
            }
        },
    };
}
```

### 3.2 统一回滚持久化顺序

所有回滚逻辑（库存/订单/结账）必须遵循：

1. 在 `tx_log` 记录 `ROLLBACK`
2. 恢复内存引用（`dbRef.db = snapshot` 或 `db = snapshot`）
3. 经 `writeDB` 持久化到 localStorage
4. 记录错误日志

> 顺序不能颠倒：若先恢复内存再记 ROLLBACK，ROLLBACK 会写到已恢复的旧快照里被丢失；若不恢复内存引用只持久化，内存与存储不一致。

### 3.3 事务原子性校验

```js
function checkAtomicity() {
    const log = InventoryService.getMockDB().tx_log;
    const begins = log.filter(e => e.type === 'BEGIN').length;
    const commits = log.filter(e => e.type === 'COMMIT').length;
    const rollbacks = log.filter(e => e.type === 'ROLLBACK').length;
    return { atomicity: begins === commits + rollbacks, begins, commits, rollbacks };
}
```

正确的事务流应满足 `BEGIN 数 === COMMIT 数 + ROLLBACK 数`（每个 BEGIN 必然对应一个 COMMIT 或 ROLLBACK）。

## 4. 库存扣减/回补事务流（修复后）

### 4.1 `deduct` / `restock` 结构（`js/inventory-service.js`）

以 `deduct` 为例（`restock` 同构）：

```js
async function deduct(params) {
    const Logger = window.UpgradeLogger, Template = window.TransactionTemplate;
    if (!Logger || !Template) throw new Error('需要工具包');

    const { items, reason = '库存扣减', refNo = null } = params;

    // 锁 key：stock:{id}，按 id 升序避免死锁
    const lockKeys = items.map(i => 'stock:' + i.id);

    const result = await _withMutex(lockKeys, () => {
        // 【关键修复】dbRef 必须在锁内创建：加锁后才 readDB() 读最新已提交状态，
        // 避免并发下多个事务读到同一陈旧快照、各自覆盖写回导致 lost-update
        const dbRef = { db: readDB() };
        const adapter = createAdapter(dbRef);
        const template = new Template({ name: 'inventory_deduct', adapter });
        return template.run({
            context: { items, reason, refNo, deductedLines: [], totalQty: 0, alertsTriggered: 0 },
            preflight: async (ctx) => { /* 参数校验：id 存在、qty>0 */ },
            stages: [
                { name: '阶段2-开启事务', action: async (ctx) => { ctx.conn = await ctx.template.adapter.begin(ctx); } },
                { name: '阶段3-库存扣减', action: async (ctx) => { /* applyDeduct：校验库存+扣减+写流水+预警 */ } },
                { name: '阶段4-提交事务', action: async (ctx) => { await ctx.template.adapter.commit(ctx.conn, ctx); } },
            ],
            asyncTasks: [ /* 阶段5：库存变更通知 + 区块链存证 */ ],
        });
    });

    // 结果适配
    if (result.aborted) return { success: false, error: result.reason, logs };
    if (result.success) return { success: true, operation: 'deduct', details: {...}, logs, asyncOps };
    return { success: false, error: '未知', logs };
}
```

### 4.2 两条不可违背的约束

| 约束 | 错误做法 | 正确做法 | 违反后果 |
|------|---------|---------|---------|
| **dbRef 在锁内创建** | `const dbRef = {db:readDB()}; await _withMutex(keys, () => template.run({...}))` | `await _withMutex(keys, () => { const dbRef = {db:readDB()}; ... return template.run({...}); })` | 并发 lost-update：N 次操作只生效 1 次（见 §5.3） |
| **begin 先 push BEGIN 再取快照** | 先 `snapshot = clone(db)` 后 `db.tx_log.push(BEGIN)` | 先 `db.tx_log.push(BEGIN)` 后 `snapshot = clone(db)` | rollback 丢 BEGIN：`begins !== commits+rollbacks`，原子性失守（见 §5.4） |

### 4.3 锁 key 命名约定

- 库存操作：`stock:{productId}`（deduct 与 restock **必须一致**，否则扣减/回补不互斥）✅ inventory-service.js
- 订单号：`order:next` ✅ checkout-service.js（B1 推广）
- 优惠券：`coupon:{couponCode}` ✅ checkout-service.js（B1 推广）
- 积分：`points:{memberLevel}` ✅ checkout-service.js（B1 推广）
- 钱包额度：`wallet:{agentId}` ✅ main.js + agent-upgrade-service.js（C2 推广）
- 多商品订单：`items.map(i => 'stock:' + i.id)`，`withLocks` 自动按 key 升序获取、反向释放

```js
const lockKeys = ['order:next'];
```

```js
    await window.mutex.withLock('wallet:' + ctx.agentId, async () => {
        await ctx.conn.execute('UPDATE wallet_accounts SET credit_limit=? WHERE agent_id=?', [...]);

```

## 5. 历史 Bug 案例（反例与经验）

四个并发 Bug 均已修复，记录为反例供后续排查参照。

### 5.1 Mutex 死锁（while+await + release 不清占位）

- **现象**：同键并发 ≥2 时，500+500 混合测试挂死 30 分钟超时。
- **根因**：`release()` 只 `r()` resolve Promise，**未 `delete _holders[key]`**。释放后 `_holders[key]` 仍是已 resolve 的 Promise（truthy），后续等待者 `while (_holders[key])` 永真 → 反复 `await` 已 resolve 的 Promise → 死循环。
- **修复**：`release` 先 `delete _holders[key]` 再 resolve。
- **根除**：改 FIFO 队列实现，从结构上避免该模式。

### 5.2 thundering herd（O(n²) 唤醒）

- **现象**：吞吐随并发数急剧退化，n=1000 时延迟陡增。
- **根因**：`while+await` 共享 Promise，`release` 唤醒全部 N-1 个等待者，仅 1 个胜出。
- **修复**：FIFO 队列，每个等待者独立 Promise，`release` 只唤醒队首一个。
- **性能对比**：HP3 吞吐 5747–9804 → 43478–100000 req/s；p50 75–92ms → 2–15ms（约 10–30x）。

### 5.3 并发 lost-update（dbRef 锁外创建）

- **现象**：10 并发 deduct 全报 `success:true`，但库存只 10→9、`tx_log` 只剩 1 BEGIN+1 COMMIT。
- **根因**：`const dbRef = { db: readDB() }` 在 `_withMutex` 回调**之外**创建。所有并发事务在加锁**前**就各自 `readDB()` 读到同一陈旧快照（stock=10），加锁后各自扣到 9 再 `writeDB` 覆盖写回，last-write-wins，9 次扣减丢失。
- **沙箱测不出**：沙箱用简化 deduct 直接 mutate 同一 db 对象，无 `readDB` 快照语义。
- **修复**：把 `dbRef`/`adapter`/`template` 三行移进 `_withMutex` 回调内，加锁后才 `readDB()` 读最新已提交状态。`deduct` 与 `restock` 同病同修。

### 5.4 rollback 丢 BEGIN（begin 快照顺序）

- **现象**：HP4（库存0，1 个 deduct 因库存不足回滚）`atomicity=false (B=999 C=999 R=1)`，应为 B=1000。
- **根因**：`begin` 先取快照、后 push BEGIN，快照不含本次 BEGIN；`rollback` 用快照恢复 `dbRef.db = snapshot` 时，本次 BEGIN 被丢弃、只剩 ROLLBACK → `begins` 少 1。
- **修复**：`begin` 改为先 `push(BEGIN)` 再取快照。修复后 HP4 `atomicity=true (B=1000 C=999 R=1)`。

### 5.5 经验总结

> **沙箱复刻逻辑测不出真实事务适配器的快照语义与 begin/rollback 顺序问题。** 高压测试脚本（`runInventoryHighPressureTest`）只验证逻辑骨架，真实 `deduct`/`restock` 的事务适配器行为必须用 probe + 真实浏览器端到端验证。任何"锁已加、事务已有"的假设都应用并发测试证伪。

## 7. 新增并发场景的接入指南

为一个新的临界区（如订单号生成）加锁，遵循：

1. **确定锁 key**：用稳定标识，如 `order:seq`。多资源用数组，`withLocks` 自动升序获取防死锁。
2. **用 `withLock`/`withLocks` 包装整个临界区**，不要裸用 `acquire`（易漏 release）。
3. **临界区函数必须 `await`**（`withLock` 内 `return await fn()`，不能 `return fn()`）。
4. **读-改-写必须在锁内**：任何"先读再判断再写"的序列，`readDB()` 必须在 `withLock` 回调内调用，否则并发下读到陈旧快照。
5. **事务用 `createAdapter`**：BEGIN/COMMIT/ROLLBACK 走统一适配器，遵循 §3.2 回滚持久化顺序。
6. **写并发测试**：参考 `runInventoryHighPressureTest`，至少覆盖纯操作、混合、库存0 边界三类，验证不超卖/库存一致/事务原子三不变量。
7. **真实浏览器端到端验证**：沙箱复刻测不出快照语义，必须跑真实事务流。

### 7.1 代码模板

```js
async function myOperation(params) {
    const { items } = params;
    const lockKeys = items.map(i => 'stock:' + i.id);   // 1. 锁 key

    return await _withMutex(lockKeys, async () => {     // 2. withLocks 包装
        const dbRef = { db: readDB() };                  // 4. 读在锁内
        const adapter = createAdapter(dbRef);            // 5. 事务适配器
        const template = new Template({ name: 'my_op', adapter });
        const result = await template.run({ /* ... */ });
        // ...
    });
}
```
