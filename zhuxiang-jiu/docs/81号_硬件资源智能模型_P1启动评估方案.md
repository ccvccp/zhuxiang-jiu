# 81号·硬件资源智能模型（HRM）——P1 启动评估方案

> 2026-10-01 立项 | 惯例对齐: 73号/74号轨同范式(需求描述→现状映射→P1 边界→ROI 触发器)
> 姊妹模块: 74号 IBMS(感知→认知已闭环)——81号补"决策→执行"资源统筹层

## 〇、方案定位: 需求描述 × 项目现状

需求原文: "统筹网站各模型的进化维护等，将硬件资源根据需求进行分配，
确保网站运行顺畅，确保角色愉悦体验，自主决策自主进化，创新规划优化"。

**务实解读**(对齐 74号 docx 处理惯例——理想态映射到 1.6G 单机现实):

| 需求原词 | 本项目落地形态 |
|---|---|
| 统筹各模型的进化维护 | **模块资源台账**: 40+ 调度器/30 个 LLM 消耗点/护栏族的统一注册(吃资源/开关/时段/优先级) |
| 硬件资源按需求分配 | 单机 Docker 无虚拟化切分——真实杠杆是**批任务错峰 + 调度器闸门 + LLM 降频** |
| 确保网站运行顺畅 | **资源水位三档**(green/amber/red): 压力渐升时逐级让路, 交易主链路(下单/支付/登录)永不让路 |
| 确保角色愉悦体验 | **黄金时段保护窗**: C 端高峰批任务暂缓, 感知面体验指标(页面/接口延迟)联动 |
| 自主决策 | **白名单自主动作**(枚举注册无通配符): 延迟批任务/暂缓低优调度器/LLM 降频——资金/删除/重启/核心配置永不出白名单 |
| 自主进化 | **决策记账 + T+1 复盘回流**: 水位是否回落/是否误伤体验 → 阈值与动作 EMA 微调 |
| 创新规划优化 | **容量规划建议书**(40号建议书范式): 磁盘/内存水位趋势 → LLM 生成升配/清理建议, 人在环审批 |

**生产资源实证**(74号 §6.1 遗留事实): 内存 1674MB/available ~583MB,
磁盘 41% 可用——资源约束真实存在, 本模块有实际价值而非概念工程。

| 决策 | 决策门/三级灰度/各模块 *_MODE 分段(全项目惯例) | **资源统筹决策引擎**(错峰/降级/限流策略与白名单) |

**杠杆面盘点**(摸底实证, "可分配资源"的真实清单):

1. **调度器族 40+**(main.py L467-665): 学习回流族(50-63号, 默认 off)
   /质量进化/雷达类/结算类(低频) vs guard 族 12 个(默认 on, 保护机制
   **永不让路**)——错峰对象天然分层
2. **LLM 消耗点 30 文件**(ibms_patrol/growth80/sv73/xiaozhu/trust/
   knowledge/pdm/promo_agent/attract...): glm-4-flash 同端点, 高峰
   期可降频(fail-soft 惯例天然支持降级回静态/rule)
3. **磁盘**(57% 已用): 日志/视频物料(sv73_videos/promo_videos)是大头,
   容量建议书主对象
4. **GPU(73号)**: AutoDL 云端渲染, 生产小机无 GPU——**P1 不涉**,
   留云端额度预算记账(P2)

## 二、四大真实缺口(= P1 边界)

### 缺口 1: 模块资源台账——"统筹各模型"的数据底座(核心增量)

现状: 40+ 调度器/30 LLM 点散落各处, 无统一视图回答"现在哪些模型
在吃资源/什么时段吃/业务优先级谁高"。

```
module_registry(新, 81号):
  · 静态注册表: {模块号, 资源画像(LLM/IO/CPU/内存), 调度器与开关,
    业务优先级(critical/normal/batch), 时段特征}
  · 优先级铁律: 交易主链路(下单/支付/登录/验证码) = critical 永不让路;
    guard 族 = 保护机制永不暂停; 学习回流/质量进化/雷达 = batch 可错峰
  · 台账喂给决策引擎与容量建议书
```

### 缺口 2: 资源水位三档——把 74号 原始指标变成决策语义

- 复用 check_host_health 同源采集(node-exporter 直采, **零新增采集器**),
  判定升级为持续水位: green(正常)/amber(渐紧, 启动错峰)/red(告急,
  激进让路+告警)
- 阈值 v1 静态(内存 available<450MB→amber/<250MB→red; load1>核数×2
  →amber; 磁盘<20%→amber), P2 用 30 天水位曲线 EMA 动态化(黄金时段
  EMA 同款范式)

### 缺口 3: 运行时批任务闸门——不重启的资源分配执行器

现状痛点: *_AUTO 环境开关要重启容器生效, 无法按实时水位动态分配。

```
acquire_slot(module_id)(新惯例, 81号):
  · 可错峰调度器跑批前调用: green→放行; amber→batch 类延迟到闲窗;
    red→暂缓+留痕(下轮重试, 幂等惯例保证安全)
  · P1 试点接入 3 个低风险调度器(知识库质量/AI 自学习/escrow 结算——
    均低频无资金风险), 验证零破坏后再扩容接入面
  · 调度器不接入也能跑(默认放行)——渐进式, 不强制改造存量
```

### 缺口 4: 决策记账 + 容量规划建议书——"自主进化"的务实形态

- 每次水位判定/自主动作全量留痕(Redis, 74号巡检史同款) + T+1 复盘
  回流(水位是否回落/批任务是否积压)——决策成功率 <90% 自动降 shadow
  并 P0 告警(74号熔断惯例)
- 容量建议书: 水位趋势 + 台账 → LLM 生成{升配 ROI/磁盘清理清单/
  调度错峰优化}结构化建议, **只读输出, 执行走 46号 approve 链**

## 四、P1 实施路径(六步, 73/74号同款节奏)

1. **模块资源台账 v1**(静态注册 + 手动盘点落表, 含优先级分层)
2. **水位评估器**(复用 host_health 采集, 三档判定 + 留痕)
3. **批任务闸门 acquire_slot**(3 试点调度器接入, 单测覆盖三档放行/暂缓)
4. **决策引擎 v1**(amber 延迟批任务 / red 暂缓+LLM 降频标记+告警,
   白名单枚举注册; HRM81_MODE=off 默认铁律)
5. **容量建议书**(LLM 结构化输出 + approve 链挂接)
6. **验收**: 人工制造内存压力(tmpfs 消耗)→shadow 留痕三档决策实证;
   on 模式批任务延迟实证; 交易主链路 red 档不受影响实证; 熔断演练;
   单测全绿 + 生产部署走既有 scp+compose rebuild 惯例

## 五、风险控制(全量继承项目铁律)

- **人机协同**: 资金/删除/重启服务/核心配置永不出白名单(05号大额/
  36号三审现状即答案); 建议书只读, 执行走 46号 approve
- **保护机制豁免**: guard 族 12 个与交易主链路在任何水位下不暂停——
  "让路"只针对可延迟的批任务
- **权限最小化**: 自主动作白名单逐项显式注册, 无通配符
- **审计追溯**: 决策全量留痕(模块/水位/动作/结果), admin_log 同款
- **熔断降级**: 自主动作后水位未回落或误伤体验 → 连续 2 轮自动回
  shadow + P0 告警
- **分段铁律**: HRM81_MODE=off(默认)/shadow(干跑留痕)/on(全链),
  生产先 shadow 观察一周

## 六、ROI 与触发器

- **稳定性**: 内存渐紧场景从"被动 OOM/重启"变"错峰让路主动化解"——
  1.6G 小机最大运行风险直接收敛
- **体验保障**: 批任务不再与 C 端高峰抢资源(黄金时段保护窗)
- **维护成本**: 模块资源台账使"哪个模型吃资源/何时维护"从考古变查询
- **81号 ROI 触发器**: P1 shadow 稳定 4 周且三档决策零误伤 →
  转 on 全链 + 启动 P2(阈值 EMA 化/接入面扩容); 否则维持 shadow

## 六、P1 上线实录(2026-10-01 生产部署+验收, 四缺口全做完成)

### 6.1 形态定版(四组件落位)

- **hrm81_service.py**(核心): MODULE_REGISTRY 台账 17 模块三分层
  (critical 4/normal 6/batch 7, 试点 3 调度器 gated=True) +
  assess_water_level 水位三档(node-exporter 直采复用 74号
  _parse_metric, 60s 缓存; 采集失败 fail-open 回 unknown 不误伤) +
  acquire_slot 闸门(off/shadow 恒放行, on+amber/red 拦 batch,
  critical/未注册豁免) + run_hrm_decision 决策引擎(amber→
  batch_defer; red→batch_defer+llm_throttle 60s+告警; 熔断:
  red 连续 2 轮动作无效自动回 shadow) + decision_history 留痕
  (Redis list 保 50 轮) + capacity_proposal 建议书(LLM 只读,
  readOnly=True 显式标注)
- **llm_client.py 挂接**: set_llm_throttle(秒) 进程内降频窗口,
  chat 入口短路返回 None——调用方按既有 fail-soft 惯例回退
  rule/静态(growth80 文案降级静态、74号诊断降级摘要已先实证)
- **3 试点调度器接入**(ai_learning/knowledge_quality/growth80_
  escrow 循环跑批前 acquire_slot, 暂缓=下轮重试幂等安全);
  未注册调度器不查闸门照常跑(渐进式零强制)
- **hrm81_routes.py**: 观测面 status/registry/decisions 无模式
  门槛, 决策面 run/proposal off 409 铁律(X-Role admin, 74号同款)
- **hrm81_scheduler.py**: HRM81_AUTO(默认 off)/HRM81_INTERVAL
  (默认 300s 下限 60)双闸

### 6.4 部署坑回填(两处, 后续部署必读)

1. **compose/.env 位置**: compose 文件在 `/opt/zhuxiang/docker-compose.yml`
   (非 zhuxiang-jiu 子目录), env 经 `env_file: .env` **直传**全部
   变量——81号 环境变量加在 `/opt/zhuxiang/.env` 即可, 无需改
   compose(误建 zhuxiang-jiu/.env 无效, 已清理)
2. **tmpfs 压不住水位**: tmpfs 干净页内核视为可回收, MemAvailable
   不降——压力演练须用**匿名内存**(bytearray 逐页 touch)
3. **P2 遗留 flaky 顺手修复**: test_growth_p2 T5 的 datetime.now
   微秒竞态(escrow createdAt 与 last_login 同刻生成概率性走"注册
   后回访"分支)——改 escrow 创建于注册一天后, 五连跑稳定
