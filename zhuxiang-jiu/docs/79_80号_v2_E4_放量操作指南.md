# v2-E4 放量操作指南(阶梯奖励 + IBMS 速率检查项)

> 适用: 管理员/运营 | 2026-10-01(v2 收官版) | 前置: E4 已于当日上线
> 与 E2/E3 指南的差异: **E4 两组件开箱即生效**(默认参数已启用), 本指南是"调参与告警开通"指南
> 命令中 `<TOKEN>` 为管理员凭证; 生产基址 zxjiu.com

---

## 〇、总览与当前状态

| 组件 | 作用 | 当前状态 | "放量"含义 |
|---|---|---|---|
| **阶梯奖励** | 月引进达档升每客分值 | **已生效**(默认档 50/200 → 400/500 分) | 调整档位参数 / 试点新档位 / 关闭阶梯 |
| **IBMS 速率检查项** | 24h 绑定速率异常监测 | **已运行**(随巡检留痕) 但告警不触达 | 开通告警触达(随 74号 IBMS 整体转 on) |

**当前生效规则(默认参数)**:

| 档位 | 当月引进数(含当笔) | 每客积分 |
|---|---|---|
| 基础 | < 50 | 300 |
| 精英 | ≥ 50 | 400 |
| 王者 | ≥ 200 | 500 |

> 档位语义: 按自然月累计(跨月自动清零), **含当笔**——当月第 50 位好友注册时, 该笔即按 400 计。
> 与 E3 escrow 兼容: escrow 记录建立时按当月档位定格分值, 观察期后按定格值发放。

## 一、阶梯奖励调参指南

### 1.1 何时调参

| 场景 | 建议动作 |
|---|---|
| 头部推荐人月量接近 50, 想强化冲量 | 维持默认(档位即激励梯度) |
| 大促月想拉高动力 | 临时调低门槛(如 Elite=30)或调高分值(ElitePts=500) |
| 常态月控制积分支出 | 调高门槛(Elite=80/King=300)或调低分值 |
| 积分成本压力/规则试验 | `referralTierElite=0` **关阶梯**(恒基础分 300) |

### 1.2 调参操作(即时生效, 只影响之后新绑定)

```
curl -X PUT -H "Authorization: Bearer <TOKEN>" -H "X-Role: admin" \
     -H "Content-Type: application/json" \
     -d '{"referralTierElite": 30, "referralTierElitePts": 500,
          "referralTierKing": 100, "referralTierKingPts": 600}' \
     https://zxjiu.com/api/promotion/admin/settings
```

四参数可任意组合(只传要改的):

| 参数 | 默认 | 约束 | 说明 |
|---|---|---|---|
| referralTierElite | 50 | ≥0, **0=关阶梯** | 精英档月引进阈值 |
| referralTierKing | 200 | ≥0 | 王者档阈值(须 > Elite 才有意义) |
| referralTierElitePts | 400 | ≥0 | 精英档每客分 |
| referralTierKingPts | 500 | ≥0 | 王者档每客分 |

### 1.3 验证

```
# 参数确认
GET /api/promotion/admin/settings → 四字段
# 实测(测试号连绑): 第 N 笔分值随档位跳变
# 单测参考序列(阈值2/4): [300, 400, 400, 500, 500]——含当笔累计定档
```

### 1.4 观测与预算口径

- 某会员当月档位: `GET /api/promotion/admin/relations?inviterMemberId=<UID>` 数当月 createdAt 条数
- 月积分支出预估: Σ(各档人数 × 档位分)——档位调整后新笔按新值, 已发不追
- 与 E3 组合时: escrow `GET /api/promotion/admin/escrows` 的 points 字段即定格档位值

### 1.5 回退

- 回默认: `{"referralTierElite": 50, "referralTierKing": 200, "referralTierElitePts": 400, "referralTierKingPts": 500}`
- 关阶梯: `{"referralTierElite": 0}`——恒基础分(pointsPerReferral)

## 二、IBMS 速率检查项(growth_anomalies)观察与告警开通

### 2.1 当前运行形态

- 检查项已注册为 IBMS 巡检第 8 项, 随**小时级自动巡检**运行(74号 `IBMS_PATROL_AUTO=on`)
- 但 74号 巡检整体处于 **shadow 观察期**(`IBMS_PATROL_MODE=shadow`)——**留痕不告警触达**
- 即: 异常数据已在积累, 管理员还不会收到站内信

### 2.2 观察现状(无需任何操作)

```
# 巡检历史(含第 8 项三态)
curl -H "Authorization: Bearer <TOKEN>" -H "X-Role: admin" \
     "https://zxjiu.com/api/ibms/patrol/history?limit=24"

# 单项直查(不经巡检)
docker exec zhuxiang-backend-1 python -c "..."  # check_growth_anomalies 直调
```

三态语义: **PASS** 正常 / **WARN**(某推荐人 24h 新增 >50, 疑似) / **FAIL**(>100, 团伙嫌疑)。

### 2.3 告警触达开通(= 74号 IBMS 整体转 on)

> 注意: MODE 是 **74号 全局开关**(8 项检查共用), 开通后主机/Redis 等其他项的 FAIL 也会触达——这是 74号 观察期满后的整体决策, 不只是 E4。

前置条件(74号方案既定): 巡检稳定 4 周 + WARN 闭环率 ≥80%。

```
ssh root@47.236.61.117
sed -i 's/^IBMS_PATROL_MODE=shadow/IBMS_PATROL_MODE=on/' /opt/zhuxiang/.env
cd /opt/zhuxiang/zhuxiang-jiu && docker compose up -d backend
```

开通后: `growth_anomalies` 出现 WARN/FAIL → 管理员站内信(74号 告警闭环, 规则级 24h 去重)。

### 2.4 回退

```
sed -i 's/^IBMS_PATROL_MODE=on/IBMS_PATROL_MODE=shadow/' /opt/zhuxiang/.env
# + 重启 backend(同上)——回留痕不触达
```

## 三、组合场景与节奏

| 阶段 | E4 阶梯 | E4 检查项 | E2/E3 | 说明 |
|---|---|---|---|---|
| 现在(默认) | 50/200 档生效 | shadow 留痕 | 关 | 已是可运营状态 |
| 观察期(2-4 周) | 可按 §1.1 调参 | 只看 history 数据 | 视触发放量 | 数据积累 |
| 常态化 | 大促调参/常态回默认 | IBMS 整体转 on | 按需 | 告警触达全自动 |

**推荐顺序**: E4 检查项的告警开通**晚于** E2 放量(E2 闸门先拦, 告警后置——拦截比告警优先)。

## 四、应急速查

| 症状 | 判定 | 动作 |
|---|---|---|
| 会员问"为什么他 400 我 300" | 当月档位差异 | 查双方当月引进数(§1.4); 属正常规则 |
| 积分支出超预算 | 档位+引进量双高 | 调高门槛/调低分值(§1.2); 紧急 `referralTierElite=0` 回恒 300 |
| 想临时停档位做 A/B | — | 记录当前参数 → 关阶梯(=0) → 试验后恢复 |
| 巡检 history 有 growth FAIL 但没收到信 | shadow 模式正常 | 按 §2.3 决策是否转 on; 紧急处置走关系审计+追回(E1) |
| 转告警后收到误报频繁 | 阈值过敏感 | 反馈技术调整 >50/>100 阈值(代码常量, 需发版) |
