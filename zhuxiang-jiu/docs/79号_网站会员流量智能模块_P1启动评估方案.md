## 〇、方案定位: docx 理想 × 项目现状

docx 核心需求一句话: **会员在各平台的流量 → 引流短码 → 观看者点击
入站 → 注册 → 引荐人得 300 积分, 全自动**。

摸底实证(2026-10-01): 这条链路的**基础设施已经 90% 存在**——
72号 attract 体系 + 推广码矩阵模块 + auth 注册自动归并(2026-09-26
P0 修复)已把"短码点击→注册→自动绑定"跑通, **勿重复造轮子**。
真实缺口只有一个: **奖励规则轨**(现行是"满 10 人发 20 元钱包"
阶梯制, 需求是"每引进 1 注册会员即时 300 积分")。

## 一、三大真实缺口(= P1 边界)

### 缺口 1: 积分奖励轨——"每引进 1 注册会员 300 积分"(核心增量)

- 现行 promotion 奖励是**钱包阶梯制**(满 10 人发一轮 20 元, 有提现/
  领酒链路), 与需求的"按人即时积分"是两种规则
- P1: `_check_rewards` 新增**积分分支**——绑定计业绩(counted=True)时
  即向引荐人发 300 积分(PointsService.earn_points 复用, 幂等由
  bind_relation 一人一绑锁 + ref_id=traffic79:{inviteeId} 双保险)
- `DEFAULT_SETTINGS` 加 `pointsPerReferral: 300`(admin 可调, 0=关)
- **与钱包轨并行不替换**(钱包体系有完整提现/领酒/审计链路, 不动)

### 缺口 2: 注册成功通知引荐人(触达闭环, 小改动)

- 积分发放成功 → message_service.send_message 站内信:
  "您推荐的会员已成功注册, +300 积分已到账"(docx"消息推送"务实版)
- 同步 promotion 既有 reward 流水(会员 my/rewards 可查)

### 缺口 3: 会员个人引流漏斗(进化层数据面)

- 现有 report_* 是全站维度; 会员需要看**自己的码**:
  点击数(attract clicks 按码计) / 注册数(attribution) / 累计积分
- P1: `GET /api/promotion/my/funnel`——my codes → clicks →
  attribution → points 汇总(get_my_stats 扩展或独立端点)

## 四、风险控制(全量继承项目铁律)

- **规则开关**: pointsPerReferral 默认 300, admin 可调 0=关(出问题
  一键停新发, 已发流水可 admin 追回)
- **刷单防御(P1 现有资产够用)**: 24h 新人原则(老会员绑定不计业绩)
  + 一人一绑 + 防环 + 自绑拦截 + 43号网关 IP 评分 + 注册手机号门槛
- **幂等三保险**: bind_relation 一人一绑锁(一人只触发一次) +
  earn_points ref_id 流水标记 + relation 锁内调用
- **不动的链路**: 钱包两级奖励/提现/领酒/矩阵关系结构——积分轨纯增量

## 五、ROI 与触发器

- 会员激励即时化: 从"满 10 人等一轮"变"每 1 人即时到账"——
  裂变动能显著放大(每注册 300 分, 站内积分抵现体系内流通)
- 全自动闭环: 短码点击→注册→绑定→300 分→站内信, **全程无人值守**
  (复用 2026-09-26 P0 修复的自动归并, 前端零改造)
- 79号 ROI 触发器: 积分轨稳定运行 2 周 + 无刷单告警 → 启动 P2
  (延迟结算/阶梯奖励/LLM 文案按需排期); 异常则 pointsPerReferral
  调 0 止损复盘
