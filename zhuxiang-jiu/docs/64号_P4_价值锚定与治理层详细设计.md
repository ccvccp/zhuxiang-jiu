## 一、定位与目标

P4 是 64号的**经济仪表盘与纠错通道**——前三期解决了"花得合法（P0）/花得可靠（P1）/花得舒服（P2）/花得安全（P3）"，P4 回答两个终极问题：

| 问题 | 子系统 | 输出 |
|------|--------|------|
| **信值还值钱吗？** | 购买力指数锚定 | 日快照+通胀/通缩预警 |
| **系统错了怎么办？** | 申诉通道 | 重算展示+翻转补偿+留痕 |

外加治理闭环：**兑换率校准建议**（46号审批轨）与**第38档案回流**（44号信任分——价值经济健康度进入 AI 学习闭环）。

**QC 铁律（本期最高约束）**：回流幂等（orderId 1:1）；校准/预警**仅建议**——一切参数变更必须经 46号 submit→人工审批双模；申诉终审**人工铁律**（AI 仅重算展示，不自动翻转）。

## 三、购买力指数锚定（xx64_anchor_service ①）

### 3.1 指数定义（确定性）

```
avgPrice        = 近 7 日已支付订单(paid/settled/completed) price 算术均值
purchasingPower = 基准均价 / 当前均价 (基准=首期快照 avgPrice, 后续快照锚定首期)
```

- **语义**：`purchasingPower > 1` → 信值升值（可兑更多商品）；`< 1` → 通胀（单位信值可兑商品变贵）
- **冷启动**：样本 <3 笔不落快照（对齐 60号冷启动铁律——防止小样本噪声进入指数序列）
- **日快照**：每日一 条 `xx64_anchors`（同日重算覆盖更新——`anchorDate` 幂等键）

### 3.2 通胀/通缩预警（观测+建议）

| 信号 | 判定（确定性） | 输出 |
|------|---------------|------|
| 通胀预警 | 指数连续 3 日下行且累计跌幅 >10% | 告警+建议（消耗场景扩充/兑换率下调——经 46号） |
| 通缩预警 | 指数连续 3 日上行且累计涨幅 >10% | 告警+建议（消耗激励——经 46号） |

预警仅落事件+建议书（`autoExecute: false`——P3 同铁律）。

### 3.3 供需预警（品类维度）

| 信号 | 判定 | 说明 |
|------|------|------|
| 需求激增 | 同商品 24h 兑换笔数 > 前 7 日日均 ×3 且 ≥5 笔 | 运营建议（补货/限购） |
| 供给不足 | 同商品近 7 日兑换总量 > 供给参考值（运营录入，缺省不判定） | 运营建议 |

需求激增与 P3 ARB-MA 的边界：ARB-MA 看**账号集中度**（洗钱特征），供需预警看**总量趋势**（运营特征）——同一数据源不同视角，互不替代。

## 四、兑换率校准建议（46号双模）

### 4.1 触发判定（确定性）

```
pointsEarned24h  = 24h 积分获取总量(points 流水 source≠xx64_exchange 求和)
trustConsumed24h = 24h xx64_ledger debit 总额
imbalanceRatio    = pointsEarned24h / 100 / max(trustConsumed24h, ε)
```

| 判定 | 阈值 | 动作 |
|------|------|------|
| 获取过快 | imbalanceRatio > 2.0（持续 3 日） | 提交 46号 config 变更建议（调低兑换率/增加消耗场景） |
| 消耗过快 | imbalanceRatio < 0.5（持续 3 日） | 提交 46号 config 变更建议（调高兑换率/缩减消耗） |
| 均衡 | 0.5 ≤ ratio ≤ 2.0 | 无动作 |

### 4.2 46号提交轨（不直改参数）

```python
await AIGovernanceService().submit_change(
    scorer_id="value_exchange",
    kind="config",
    payload={"suggestion": {...},   # 建议参数+依据数字
             "before": 当前值快照,
             "after": 建议值},
    reason=f"兑换率失衡 ratio={ratio}(依据...)")
```

- **同档案 pending 冲突**：46号已有 pending 变更时不重复提交（ValueError 捕获 fail-soft——跳过本轮）
- 参数真值仍在 registry（R6 100:1 属宪法域）——**本期校准建议仅覆盖非宪法参数**（如日限频/窗口天数经 46号 审批后由 threshold 表落地，宪法七条 R1-R7 占比结构永不可变）

## 五、申诉通道（xx64_appeal_service）

### 5.1 流程（人工铁律）

```
① 提交: POST /appeals {orderId, reason}
   (不受 XX64_MODE 影响——宪法口径)
② 重算: 确定性复跑 precheck四查+explain步骤+P3五防检测
   (AI 展示"为什么这样算"——数字可溯源, 不做翻转决定)
③ 终审: POST /appeals/{id}/review {decision: approve|reject, note}
   (admin 人工——approve 才翻转)
④ 翻转: approve 且核实系统错误 → 订单转 adjusted 态
   + 补偿动作(解锁信值/返还积分) + 全链留痕
   + appeal_overturn 因子数据(第38档案)
```

### 5.2 翻转语义（关联 P1/P3 资产）

| 申诉对象 | approve 翻转动作 |
|---------|-----------------|
| 预校验误拦（blocked/reserved 前拒） | 无资产变动——记录翻转率供 rule_compliance 因子 |
| 支付后被风控冻结（P3 disputed） | 订单恢复 paid 态（冻结解除） |
| 积分兑换被拦截 | 重新走 exchange（积分未扣——拦截时点在扣减前） |
| 结算金额争议 | 订单转 adjusted+差额补偿建议（人工执行） |

### 5.3 状态机

```
submitted → recalculated(重算完成) → approved(翻转生效)/rejected(维持)
           ↘ expired(48h 未终审——自动关闭仅留痕, 不翻转)
```

重复申诉拒绝（同 orderId 已有非 closed 申诉）；申诉不改变订单现状（终审前冻结观察）。

## 六、第38档案回流（xx64_learn_service）

### 6.1 信号判定（终态扫描→八因子输入）

| 信号 | 订单终态 | 44号反馈 |
|------|---------|---------|
| exchange_ok | completed/settled | correct=true（兑换健康+） |
| exchange_refunded | refunded | correct=false（结算偏差——供 appeal_overturn 归因） |
| exchange_cancelled | cancelled | 中性跳过（不计入反馈） |
| exchange_disputed | disputed | correct=false（风控冻结——供 arbitrage_blocked 归因） |

因子聚合口径（观测面实时算，回流仅送单笔信号）：
- `exchange_health` = (completed+settled)/总数
- `appeal_overturn` = approved 申诉/申诉总数（反向）
- `arbitrage_blocked` = P3 risk confirmed/总命中
- `anchor_stability` = 指数波动率（§三快照序列）
- `latency_budget` = 结算链路 P95（事件时差统计）

### 6.2 幂等（orderId 1:1——QC 铁律）

- 订单回写 `pooledFeedbackId`（>0 即已入池——跳过）
- 双轮 collect 断言：第二轮 labeled=0（全部 skipped already_pooled）
- 44号 submit_feedback fail-soft（44号异常不阻塞订单——仅 poolFailed 计数）

## 七、T+1 调度（xx64_scheduler）

对齐 PAY60 调度范式（XX64_LEARN_MODE=on 总开关，默认 off）：

```
run_scheduled_tasks() 一轮 = ① 指数快照(anchor_snapshot)
                           + ② 回流(collect_feedback)
                           + ③ 供需扫描(supply_demand_scan)
                           + ④ 校准检查(rate_check→46号)
                           + 调度留痕(eventType=scheduler_run)
start_scheduler()/stop_scheduler() 后台 asyncio 循环(默认 86400s 可配)
```

- `run_scheduled_tasks` 可独立调用（测试/手动触发——与 XX64_MODE 解耦，仅看 LEARN_MODE）
- 三任务 fail-soft 互不阻塞（单任务异常进 errors 列表）

## 八、API 设计（+8 端点，累计 24——全期收官）

| # | 端点 | 面 | 说明 |
|---|------|-----|------|
| 17 | `GET /anchors` | 观测（member/admin） | 指数序列+最新快照+趋势预警 |
| 18 | `POST /anchors/audit` | 管理（admin，off 409） | 手动触发指数计算（非调度场景） |
| 19 | `POST /threshold/calibrate` | 管理+终审双模（admin） | 提交校准建议→46号（off 409） |
| 20 | `GET /thresholds` | 观测（admin） | 当前阈值域+46号 pending 变更视图 |
| 21 | `POST /appeals` | **不受开关**（member/admin） | 提交申诉（重算展示） |
| 22 | `POST /appeals/{id}/review` | 终审（admin 人工铁律） | 人工终审+翻转执行 |
| 23 | `POST /feedback/collect` | **不受开关**（admin） | 手动触发一轮回流 |
| 24 | `GET /learn/status` | 观测（admin） | 回流状态+因子聚合+调度状态 |

**异常映射**：KeyError→404 / ValueError→409（统一口径）；appeals/feedback 不受 XX64_MODE 影响（宪法口径——观测与纠错永不关停）。

| 表/字段 | 类型 | 说明 |
|---------|------|------|
| xx64_anchors（P0 预留，本期启用） | anchorId 主键 | anchorDate(幂等键)/avgPrice/purchasingPower/samples/trend/alarms(json) |

仓储增量：`pooledFeedbackId` 补入 _INT_FIELDS；anchors/appeals 存取方法已预留。

## 十、铁律与边界（零改动宪法）

| 铁律 | 本设计的落实 |
|------|-------------|
| 回流幂等（orderId 1:1，QC） | §六.2 pooledFeedbackId 回写+双轮断言 |
| 校准仅建议（46号双模） | §四 submit_change 提交——参数变更必经人工审批 |
| 申诉终审人工铁律 | §五 AI 仅重算展示，approve 决定权在 admin |
| 宪法参数不可校准 | §四.2 R1-R7 占比/结构永不变——校准域仅限日限频/窗口等可调参数 |
| 观测/纠错永不关停 | appeals/feedback/learn-status 不受 XX64_MODE 影响 |
| 44号零改动 | submit_feedback 既有接口调用（第38档案 P0 已入册） |
| 45/47号零改动 | 指数/预警只读余额与档案；翻转动作只动 64号自有账本 |
| 46号零改动 | submit_change 既有审批总线调用 |
| 调度默认 off | XX64_LEARN_MODE=off——三开关铁律收官 |
