# 43号·AI智能安全管理模块 P6 聚合规模化与就绪度 实施计划 v1.0

> 配套：[P5 全景收官总结报告](43号P5_全景收官总结报告.md) §八
> 定位：P5 后模块进入**默认零影响的待启用态**——六项能力齐备但均等外部条件（数据达标/凭证/资产）。P6 做三件事：把情报覆盖面从单源 2k 段扩到**多源聚合 ~180k 段**（冷启动防护面扩大约 90×）、把运维告警从 Redis 单信号扩到**三信号全覆盖**、把 enforce 上线检查单从操作指南文字变成**一键就绪度评估端点**（数据说话，不拍脑袋）。
> 调研结论（2026-09-03）：
> 1. **全量替换语义是聚合的第一道墙**：`import_netset(replace=True)` 清空**全部**段再导入——多源并存必须改为**按源替换**（导入 level2 只清 level2 旧段，level1 保留）；
> 2. **逐键 IO 是规模化的第二道墙**：导入逐键 `hset`、读取逐键 `hgetall`（`_list` 实现）——容器内 Redis 180k 次 round-trip 估算 15~20s+ 级；导入与构建均需 **pipeline 批量化**；
> 3. **stats() 全量 list 是第三道墙**：180k 段时管理端 stats 单次调用将卡顿 18s 级——需**计数器化**（导入时增量维护 source→count，查询零 list）；
> 4. `MAX_IMPORT_CIDRS=20000` 硬编码——需**环境变量化**提额（聚合全量 ~180k 段）；
> 5. `SecurityAlertService` 仅采集 Redis 体检信号——P5-3 的 `stats().auto.degraded` 与调度器 `lastErrors`（baseline_anomaly）**已有留痕字段但未接入告警通道**；
> 6. enforce 检查单为操作指南 §六纯文字口径（5 条人工核对）——日报/观测端点数据已齐备，可自动化为就绪度端点。

## 一、三个方向总览（按成本/收益排序）

| 编号 | 方向 | 核心价值 | 依赖 | 成本 | 建议顺序 |
|------|------|---------|------|------|---------|
| P6-2 | 告警通道多信号化 | 运维风险感知：Redis 体检 + 情报订阅降级 + 调度器基线异常三信号全覆盖 | P5-2 通道（已交付） | 低 | ★★★ 先行（纯集成，半天级） |
| P6-3 | enforce 就绪度自动化 | 人工检查单 → 一键评估端点 + 面板卡（切换 enforce 的"数据绿灯"） | P4-1 日报（已交付） | 低 | ★★★ 次之 |

## 二、P6-1：情报源聚合与规模扩展

### 现状与差距

| 维度 | 现状 | 差距 |
|------|------|------|
| 替换语义 | `replace=True` 清空全部段 | 多源并存需**按源替换** |
| 导入写入 | 逐键 `hset`（180k 段 ≈ 20s+） | pipeline 批量（目标秒级） |
| 段表读取 | `_list` 逐键 `hgetall`（区间构建/stats 均走此路径） | pipeline 批量读（目标 < 5s） |
| 上限 | `MAX_IMPORT_CIDRS=20000` 硬编码 | 环境变量化（默认 20000 兼容，聚合时调 200000） |
| stats | 全量 list 统计 | 计数器增量维护（查询零 list） |
| 自动订阅 | 单源单状态（`threatintel:auto` 单例） | 多源各自状态（`threatintel:auto:{source}`） |
| 情报源 | firehol_level1 单 URL | 多源列表（level1+level2+cross 起步，可扩） |


**④ stats 计数器化**（查询零 list）：

```python

#   zhuxiang:security43:threatintel:stats {source: count}
# stats() 读计数器(毫秒级) + auto 状态聚合
# 兜底: 计数器缺失(旧数据) → 回退全量 list 一次并重建计数器
```

**⑤ 多源自动订阅**（feed 层）：

```
SECURITY_THREATINTEL_URLS=level1=https://raw.githubusercontent.com/firehol/blocklist/master/firehol_level1.netset,level2=https://.../firehol_level2.netset,cross=https://.../cross.netset
```
- `source` 从 URL 文件名推导（`firehol_level2.netset` → `firehol_level2`），单 URL 变量 `SECURITY_THREATINTEL_URL` 保留兼容（推导为 `firehol_level1`）
- 每源独立 auto 状态（`threatintel:auto:{source}`：lastAutoImportAt/status/consecutiveFailures/lastError）
- 调度器⑤遍历源列表逐源 `maybe_refresh`（每源独立周期判断/失败计数，单源失败不阻断其余）
- `stats().auto` 聚合输出：`degradedSources: [...]`（任一源连续失败 ≥3 即列入，整体 `degraded` 为任一源降级）

**⑥ 实机规模验证（验收门槛）**：

- 生成 ~180k 段多源数据（10.a.b.0/24 全空间 + v6 少量）分 3 源导入
- 断言：导入耗时 < 60s（pipeline 生效）/ 区间构建 < 5s / 10k 次匹配查询 < 3s / 容器内存增量 < 50MB / stats 调用 < 500ms
- P4-4 Redis 体检回归（键族计数 18 万段正常输出）

### 测试与验收

| 层级 | 覆盖 |
|------|------|
| 专项（预计 26 项） | 按源替换（A 源刷新不清 B 源/单源全清兼容）/ pipeline 批量读写正确性 / 上限环境变量（默认 20000 兼容+提额生效）/ stats 计数器（增量维护/兜底重建/毫秒级）/ 多源 URL 解析（source 推导/单 URL 兼容）/ 每源独立 auto 状态 / 多源 degraded 聚合 / 调度器多源遍历（单源失败不阻断） |
| 实机（预计 12 项） | 180k 段三源聚合导入全链路 + 性能门槛断言（导入/构建/查询/stats 四项耗时）+ 命中正确性抽样 + bisect 模式生效 + Redis 体检回归 |
| 回归 | security 18 套（重点 P4-3/P5-3/P5-6 三套情报链路） |

### 关键风险

| 风险 | 对策 |
|------|------|
| 180k 段导入卡顿调度循环 | pipeline 分批（5000/批）+ 每批 `await asyncio.sleep(0)` 让出事件循环（P4-2 分批节流范式） |
| 计数器与实际漂移（手动删键等旁路操作） | stats 兜底：计数器 total 与区间缓存 segments 交叉校验，不一致触发一次全量重建 |
| 多源单源毒源（错误内容反复失败） | 每源独立失败计数/degraded——毒源降级不拖垮其余源；P6-2 告警按源触达 |
| 外网多源可达性 | P5-3 既有 fail-soft 语义按源继承（旧段宁旧勿空）+ URL 可配镜像 |
| 上限误配过大（内存） | 默认 20000 不变；提额属显式运维决策；实机验收含内存增量断言 |

## 三、P6-2：告警通道多信号化

### 现状与差距

- P5-2 `SecurityAlertService.notify_redis_alerts` 仅采集 Redis 体检告警（大 key/rate 泄漏/内存水位/碎片率）
- P5-3 `stats().auto.degraded`（订阅降级）与调度器 `lastErrors` 含 `baseline_anomaly`（基线重建异常）**已有字段但无人消费**——降级/异常静默发生，运维不可知

### 实施方案

**① 多信号采集**（`security_alert_service.py` 扩展，Redis 体检逻辑零改动）：

```python
async def notify_security_alerts(self, force=False) -> dict:
    """三信号统一采集 → 过滤 → 去重 → 管理员触达

    信号源:
        S1 Redis 体检告警(既有, P5-2 原样)
        S2 情报订阅降级: stats().auto.degradedSources 逐源
           → warn 级 [源 X 连续失败 N 次: lastError]
        S3 调度器异常: get_scheduler_stats().lastErrors 含
           baseline_anomaly → warn 级 [基线重建异常:
           N actor 有行为但 0 基线]
    """
```

- 去重规则延续 P5-2 口径（rule 级 24h SETNX）——新增 rule：`threatintel_degraded:{source}` / `baseline_anomaly`
- 仍仅 warn+critical 触达；S2/S3 构造为 warn 级

**② 端点**（第 33 个）：`POST /admin/alerts/collect`（全信号采集+触达，`force` 跳过去重）；既有 `/admin/redis/alert/test` 保留（仅 Redis 信号，向后兼容）
- 面板⑦区"发送告警站内信"改调新端点（返回结构含 `signals` 分组计数，info 文案展示三类信号数）

**③ 调度轨**：调度器④步骤改调 `notify_security_alerts`（内部自动含三信号；S3 读的是上一轮调度留痕——自检口径：本轮基线异常下轮告警，滞后一轮可接受）

### 测试与验收

| 层级 | 覆盖 |
|------|------|
| 专项（预计 18 项） | S2 降级触达（mock degraded→发送）/ S3 基线异常触达 / 三信号聚合单封 / 各自独立去重 / 单信号无告警零发送 / 旧端点兼容（仅 Redis）/ force 跳过 / 管理员触达回归 |
| 实机（预计 8 项） | 制造订阅降级（坏 URL 3 次）→ collect 端点 → 管理员站内信含降级消息 → 24h 去重 → 恢复后不再触达 |
| 回归 | security 18 套（重点 P5-2 告警专项） |

### 关键风险

| 风险 | 对策 |
|------|------|
| 三信号单封过长 | 分组渲染（每信号一行摘要）；超 10 条截断+计数 |
| S3 滞后一轮 | 口径明示（上轮留痕本轮触达）；可在计划评审时改为实时读 `lastErrors`（实现等价） |
| 信号风暴（多源同时降级） | 每源独立 rule 去重（24h 内每源一条）+ 聚合单封 |

## 四、P6-3：enforce 就绪度自动化

### 现状与差距

- enforce 检查单为操作指南 §六纯文字（5 条人工核对：observe ≥1 周/误报率 <10%/积压清零/申诉畅通/白名单确认）
- D5/情报/geo 三类信号的达标数据分散在各端点（`/admin/reports/d5`、`stats().auto`、geo 可用性）——切换 enforce 前需人工逐项翻查

### 实施方案

**① 就绪度端点**（第 34 个）：`GET /admin/enforce/readiness`

```python
async def enforce_readiness() -> dict:
    """enforce 上线就绪度评估(检查单五条 + 三信号达标)

    Returns:
        {overall: "ready"|"holding",
         checks: [
           {id: "observe_days", name: "灰度观察期≥7天",
            passed: bool, actual: "12天", required: "≥7天"},
           {id: "false_positive_rate", ...},   # 误报率<10%
           {id: "pending_backlog", ...},       # 待裁决积压=0
           {id: "appeal_channel", ...},        # 申诉端点可用
           {id: "health_whitelist", ...},      # 健康检查白名单
         ],
         signals: {d5Enforce: {...观测三条件...},
                   threatintel: {mode, degraded},
                   geo: {available}},
         blockers: ["误报率 12.4% 未达标", ...]}   # 未过项列表
    """
```

- 数据源全部复用既有端点/服务（日报序列算 observe 天数与误报率；dashboard 算积压）——纯聚合层零新检测
- `overall: ready` 仅当五检查全过（三信号达标是加分项不是门槛——与检查单口径一致）

**② 面板⑦区"enforce 就绪度"卡**：ready（绿灯）/holding（黄灯+blockers 摘要）；按钮按需加载（与 D5 状态卡同区）

**③ 操作指南 §六联动**：检查单文字补充"一键评估：面板⑦区就绪度卡 / GET /admin/enforce/readiness"（人工核对为兜底）

### 测试与验收

| 层级 | 覆盖 |
|------|------|
| 专项（预计 16 项） | 五检查各自过/不过两态 / actual 口径正确（造数据验证天数/误报率/积压计算）/ 三信号汇总结构 / blockers 列表 / overall 判定 / HTTP 鉴权 |
| 实机（预计 6 项） | 真实容器数据就绪度输出 / 制造积压 → holding / 面板卡渲染 |
| 回归 | security 18 套 |

### 关键风险

| 风险 | 对策 |
|------|------|
| 就绪度被误用为自动切换依据 | 端点只评估**不切换**（切换仍人工改环境变量——检查单第 6 条人工操作不可自动化，防误切换铁律） |
| 误报率计算口径分歧（全事件 vs 已裁决） | 沿用 dashboard 既有口径（已裁决分母），actual 明示分母 |

## 七、P6 与既有架构的一致性声明

- **零不可逆变更**：上限提额/多源/三信号均为增量扩展，默认值保持 P5 末行为（单源/单信号/20000 上限）
- **fail-soft 全继承**：多源单源失败不阻断其余源；告警采集异常不阻断调度；就绪度端点只读不切换
- **纯集成优先**：P6-2/P6-3 零新检测能力（消费既有留痕字段）；P6-1 为性能与规模工程（无新业务语义）
- **性能门槛即验收**：P6-1 四项耗时门槛写入实机断言（P5-6 经验——无断言的性能优化等于没做）
