# 78号·竹盾 — 网站开发增量管理 Agent 创新规划方案

> v1.1 · 2026-10-20 · 状态: 设计定稿, 待启动 P0
> 形态: **开发期工具链**（非常驻大模型服务）—— Python CLI（agent-infra 家族同构）+ pre-commit 钩子 + 巡检接入
> 使命: 让每一次改动"先理解存量、再做保护性增量"，护航全站模块持续演进与 11 月单端化改造
> v1.1 修订: 首实战场景由"Express→Koa 迁移"修正为本项目真实变更（后端为 FastAPI/Python，Koa 为跨项目背景不适用）；实现载体定为 Python CLI
> 编号: 承接全站大模型序列（73-77 全量终态之后为 78），但竹盾不占用决策端点、不新增常驻 LLM 调用

## 一、设计理念

借鉴外部方案的四大原则：**资产优先 / 防御性开发 / 增量上下文 / 可验证交付**。在此基础上按本项目实情做四项创新：

| # | 创新 | 相对外部方案的改造 |
| --- | --- | --- |
| 1 | 去基建化 | 向量库(Qdrant/Milvus)→ **git 内分层 MD 索引**；LangGraph 多 Agent 编排→**单 CLI 三子命令**；IDE 插件→**既有 pre-commit 钩子（F3 全检）+ CLI 调用** |
| 2 | 与家族范式同构 | 沿用全站既有模板：编号/四档灰度/护栏三指标/guard_pause/回滚命令/Redis stats，学习成本≈0 |
| 3 | 确定性优先 | 引用追踪用 grep 硬扫描（结果可复核、带文件行号），LLM 仅做风险解释层——呼应百炼链路"确定性压倒微优化"的定版哲学 |
| 4 | 报告即交接文档 | 影响报告 = PR 附件 = junior 培训教材，直接服务团队交接需求 |

**明确不做**（防止过度设计）: 不自动重构（只建议）、不接管部署（走既有 deploy 脚本族）、不重建巡检（接入既有 patrol 而非替代）、不引入企业级基建（ELK/ArgoCD/A-B 测试/视觉回归 Percy——单 lead + 2 junior 规模撑不起，也不需要）。

## 三、架构设计

单 CLI（`zhudun`），三个模块，全部只读分析、不写业务代码。**实现载体：`agent-infra/zhudun/`（Python 包，与图形分析 Agent 同构——cli.py + 模块拆分 + pytest + ruff）**，入口 `python agent-infra/zhudun/cli.py <子命令>`。

```
┌──────────────────────────────────────────────────┐
│  M1 资产图谱 registry    M2 影响评估 impact    M3 增量门禁 gate │
│  扫描→分层MD索引+红线    git diff→反向引用     三道门对接既有节奏 │
│  (zhudun index)          (zhudun impact)      (ZHUDUN_MODE)    │
└──────────────────────────────────────────────────┘
   产出物: docs/registry/{L0清单, L1资产卡片, reports/影响报告}
   状态位: Redis zhudun:stats / zhudun:index:last_run
```

**M1 资产图谱（对应外部方案"考古分析师"）**
- 扫描面：backend（路由表/models/services/env 开关清单）+ dist（18 页面清单）+ nginx conf
- 产出：L0-总清单（端点/模块/页面三张表，常驻速查）→ L1-资产卡片（按需生成：引用方、被引用、行为契约要点、关联测试、红线标记）→ L2 源码（按需 Read）
- 更新：手动 `zhudun index`；红线标记初版一次性人工录入后由 diff 钩子增量维护
- 对应外部方案"分层索引+按需召回"，但用 grep-able 的 git 内文件实现，零外部依赖

**M2 影响评估器（对应"影响评估师"+"增量架构师"）**
- 输入：`git diff --name-only`（对照基线分支）
- 三步分析：①符号/路由反查引用方（grep 带行号）②红线区命中判定 ③检查清单映射（改 js→B1 v= 升位提醒；改 Redis 读写→C3 备份；改支付/鉴权→红线告警）
- 产出：`docs/registry/reports/影响报告-YYYYMMDD-HHmm.md`（涉及文件/引用方/风险分级 红-高-中-低/建议回归项/复用建议）
- LLM 可选解释层：走现有 GLM key 生成风险叙述，失败降级纯文本（对齐 38 号审图降级惯例）

**M3 增量门禁（对应"守门员"）**
- 门 1（PR 前）：特性测试锁定现行为 + 单测全绿——既有铁律，竹盾只做登记
- 门 2（PR 时）：PR 必附影响报告（junior 的 PR 由 lead 对照报告 review——对接现流程）
- 门 3（部署后）：patrol 快照对比 + 核心链路探活（接入既有每日巡检，11 月随海外退役改单端）

## 四、核心工作流——五步增量 SOP

1. **登记**：一行写改动意图 → 跑 `zhudun impact`
2. **读报告**：确认引用方、红线命中、检查清单映射项
3. **锁定**：高风险改动先补特性测试锁住现行为（Characterization Tests）
4. **实施**：单模块小步提交；commit 中文一行式（历史风格）；单测绿才提 PR
5. **验证**：PR 附报告 → 部署走既有通道 → patrol 对比 → 报告归档 registry

## 五、灰度与护栏（对齐家族模板）

- **ZHUDUN_MODE 四档**：off（不干预）/ shadow（只出报告不拦截，P0-P1 默认）/ assist（缺报告提示、人工确认放行，P2）/ full（pre-commit+PR 阻断，P3；Override 逃生通道=tech lead 审批标记）
- **护栏三指标**（恶化>3% 自动 guard_pause 降档）：
  - 影响报告误报率 ≤30%（shadow 期人工抽检）
  - 漏报率 =0 红线（上线后回归事故归因到报告未列引用方即降档）
  - 复用采纳率 ≥30%（报告中"建议复用"实际采纳比例）
- **回滚**：`ZHUDUN_MODE=off` 一行关闭；竹盾不写业务代码，无代码回滚负担

## 六、首个实战：两项真实变更护航

竹盾不空转、不用假想需求演练——P2 起拿排期中的真实变更跑通全流程：

| 试点 | 内容 | 风险级 | 竹盾动作 |
| --- | --- | --- | --- |
| 巡检单端化改造 | 每日巡检任务 fa991160 双端探测（海外+ECS）改单端，2026-11-11 海外退役前完成 | 中 | 影响报告列引用方（巡检脚本/检查清单 A 节）→ 锁定现有巡检断言 → 单端改造 → patrol 验证 |
| 首个模块升级试点 | 选一个排期中的中等风险模块升级，用五步 SOP 全流程护航 | 中 | 报告 + 特性测试锁现行为 + PR 附报告 + 部署后对比 |

原则：**试点即生产**——全部为真实变更；SOP 验证通过后，后续所有模块升级默认走竹盾流程。

## 八、避坑（外部方案精华的本地化）

- **不过度索引**：L0 常驻速查、L2 按需读，禁止全量塞上下文
- **警惕幻觉复用**：引用建议必附文件行号，采纳前人工 Read 复核——不凭相似度盲推
- **尊重遗留代码**：红线区= Frozen Zone，非专项指令不"美化"
- **副驾驶定位**：分析、建议、验证归竹盾；决策权在人（即便 full 档也有 Override）
- **从痛点最痛处切入**：本项目最痛=迁移不敢动、双端曾不同步——先建"不破坏"底线，再谈智能复用
