# 42号·AI无感开票模块 设计文档 v1.0

> 定位：**买完酒，发票已经开好了**——订单完成（评价/超时）后 AI 全自动完成"抬头决策 → 风险审评 → 自动开具电子发票 → 区块链存证"，用户零操作；退款时自动红冲。把发票从"用户手动申请的财务动作"变成"完成即达的服务体验"。
>
> 与财务模块（19号 P0-7）的关系：**复用不合并**——19号已有手动开票（issue/red/红冲负数票范式/FP序列号/锁/仓储双模式），42号只做"无感"层：抬头簿记忆、AI 决策、自动触发、自动红冲、发票存证；手动开票端点保持不变作为兜底。
>
> 方法论：对标成熟玩法（京东/天猫"闪电开票"——订单完成即推送电子票；企业微信电子发票卡包），叠加本项目既有 AI 基建（评分器档案体系/订单风控信号/37号式留痕口径）。

---

## 1. 设计目标与核心概念

### 1.1 一句话模型

**"订单 COMPLETED → AI 查抬头簿决策（有默认抬头+低风险 → 自动开）→ 电子发票 mock 通道开具 → 区块链存证 → 推送会员；无抬头 → 偏好收集不阻断；REFUNDED → 自动红冲。"**

- 无感三板斧：**零操作**（有默认抬头即自动开）、**零等待**（完成即开，不等用户申请）、**零差错**（AI 风险审评拦截异常开票，误开自动红冲兜底）

### 1.2 核心决策：什么时候开、给谁开

| 场景 | AI 决策 | 动作 |
|------|---------|------|
| 有默认抬头 + 低风险 | auto_issue | 自动开具 + 存证 + 推送 |
| 有抬头但中风险 | manual_queue | 待确认队列（用户可一键开） |
| 高风险（金额异常/高频） | reject | 拦截留痕，转人工 |
| 无抬头簿 | collect | 首次引导收集偏好（不阻断订单流） |
| 订单退款（已开票） | auto_red | 自动红冲原票 + 负数票留痕 |

### 1.3 与既有模块关系（复用不合并）

| 模块 | 关系 |
|------|------|
| `finance`（19号） | **底座**：issue_invoice/red_invoice 服务、FP 序列号、`finance:invoice:*` 锁与仓储、红冲负数票范式、`priceDetail.actualAmount` 金额口径——42号自动开票直接调 `issue_invoice`（同一防重锁同一发票池，手动/自动共用不冲突） |
| `order` | 触发点：review→COMPLETED 钩子（现有 L216 `on_order_outcome` 旁挂 best-effort）+ refund→REFUNDED 钩子；超时完成 timeout/complete 补挂 |
| `ai_learning` | 新增第 25 档案 `invoice_decision_gate`（batch 9） |
| `compliance`（24号） | 发票存证：`EVIDENCE_TYPE_INVOICE = "invoice"` 扩类型白名单 |
| `risk_control` | 复用订单风控信号（order_risk 决策快照）作为开票风险因子输入 |

## 2. 总体架构：五个子系统

### 2.1 会员抬头簿（title_book）

会员维度常用抬头记忆（当前 member 模块零发票画像，全新建）：

- **抬头记录**：titleType（personal/company）/ title（抬头）/ taxNo（税号）/ isDefault（默认标记，一人一默认）
- **入口**：①手动维护（增删改查端点）②首次自动开票时用户提交 ③历史开票自动回填（迁移：扫描已有发票提炼每个会员最近抬头入簿）
- **置信度**：使用次数计数——用得越多 AI 对自动开票越有信心（决策因子）

### 2.2 开票决策评分器（InvoiceDecisionScorer，第 25 档案）

| 因子 | 权重 | 判据 |
|------|------|------|
| 抬头置信度 | 0.30 | 默认抬头存在+使用次数（≥3 次满分） |
| 金额合理性 | 0.25 | 实付金额相对会员历史区间（异常大额降分） |
| 开票频次 | 0.20 | 同会员 24h 开票数（≥5 次疑似拆分开票） |
| 订单风险 | 0.25 | order_risk 决策快照（block/review 信号直通降档） |

决策三档：**≥70 auto_issue / 50-70 manual_queue / <50 reject**（阈值范式）。

### 2.3 自动开票流水线（auto_pipeline）

```
订单 COMPLETED 钩子(best-effort 火后不管)
  → 幂等检查(该订单是否已决策过)
  → 抬头簿取默认抬头; 无 → collect 留痕返回
  → InvoiceDecisionScorer 评分
  → auto_issue: 调 finance.issue_invoice(同一锁同一防重)
      → 电子发票开具(FP 序列号沿用)
      → compliance 存证(evidenceType=invoice)
      → invoiceAutomationRate 留痕(AI 自动化率)
  → manual_queue: 入待确认队列(用户端一键开票)
  → reject: 留痕(可申诉)
```

### 2.4 自动红冲（auto_red）

退款 REFUNDED 钩子 → 查该订单已开发票 → 未红冲则自动调 `finance.red_invoice`（负数票 + 原票置 red），红冲原因自动填"订单退款联动"。手动红冲端点不变（管理员兜底）。

### 2.5 待确认队列与偏好收集（user_funnel）

- manual_queue：用户端"我的发票"页一键确认开票（用队列里的抬头快照）
- collect：首次购完成的会员在下单完成页收到抬头引导（非阻断）
- 管理端：拦截记录观察（reject 留痕面板）

## 3. 数据模型（前缀 invoice42，双模式内存+Redis）

```
invoice_title_books     抬头簿(会员维度, 抬头列表/默认标记/使用计数)
invoice_decisions       决策流水(订单维度, 评分快照/档位/幂等标记)
invoice_auto_queue      待确认队列(manual_queue 档, 抬头快照)
```

发票本体不入新表——**直接落 finance 发票池**（复用 19号），decisions 流水通过 `invoiceNo` 关联。

**Mock-first**：电子发票开具为 mock（生成 FP 号即视为开票成功 + 存证哈希），真实税务通道（百望/航信/税务 UKey）留 `INVOICE_CHANNEL_MODE` 三态开关（对齐 36/41号通道惯例）。

## 4. API 设计（约 10 端点，前缀 /api/invoice）

**会员端**：
- `GET  /api/invoice/titles` 我的抬头簿 / `POST`/`PUT`/`DELETE /api/invoice/titles/{id}` 维护
- `GET  /api/invoice/mine` 我的发票列表（自动+手动开的都在 finance 池，按 memberId 过滤）
- `POST /api/invoice/queue/{decisionId}/confirm` 待确认一键开票
- `POST /api/invoice/orders/{orderId}/request` 手动触发（无感漏网兜底）

**管理端**：
- `GET  /api/invoice/admin/decisions` 决策流水（可按档位过滤）
- `GET  /api/invoice/admin/rejects` 拦截面板
- `GET  /api/invoice/admin/stats` 自动化率统计（auto/manual/reject/collect 分布）

## 5. 环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `INVOICE_AUTO_MODE` | on | 无感开票总开关（off 则纯手动回到现状） |
| `INVOICE_CHANNEL_MODE` | mock | 电子发票通道 mock/real/mock_fallback |
| `INVOICE_FREQ_WINDOW_HOURS` | 24 | 频次因子窗口 |
| `INVOICE_FREQ_THRESHOLD` | 5 | 高频阈值 |
| `INVOICE_MIN_AMOUNT` | 0.01 | 开票最低金额（低于不开） |

3. **实机验收**：Docker 全链路（订单完成→自动开票→存证→退款→红冲）
