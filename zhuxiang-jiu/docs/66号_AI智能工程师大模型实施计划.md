> 定位：网站生命体征的守护者 + 角色数字体验的护航员——将 26/27号运维底座、07号工单、35号中枢、57号知识库、45/62/47号信值体系编排为"预测性自愈 + 有温服务 + 可信支撑"的智能免疫系统。
> 依据：全站 54-65号新范式（评分器×决策门×回流闭环×三模式开关）+ 批次七融合收官产物（47号 hub 统一调度/44号 panorama/跨模块红队范式）。
> 状态：**设计完成，待实施**——P0~P4 五期交付，每期专项 ≥40 断言 + 全模块回归 + Docker 实机 ×2 轮幂等 + lint 全绿。

## 一、模块定位与设计哲学

### 1.1 核心定位：从"故障响应工具"到"信值生态的智能免疫系统"

| 维度 | 传统运维/客服 | 本站现状（勘察实证） | 66号目标 | 核心差异 |
|------|--------------|----------------------|----------|----------|
| 触发机制 | 用户报错/告警后响应 | 26/27号被动记录（指标靠上报、自愈停在 detected 态） | 预测性维护 + 情绪感知 + 主动关怀 | "救火" → "防火+暖心" |
| 问题解决 | 查文档/提工单/等人工 | 工单五态流转完整但根因靠人工 | 规则+案例根因分析 → 自愈编排（经审批）→ 信值联动补偿 | "流程等待" → "秒级闭环（观测面）" |
| 交互体验 | 机械问答/冰冷术语 | 小竹语音指令轨（无工程师人格） | 三模式自适应沟通 + 信值透明化解释 | "技术对接" → "伙伴陪伴" |
| 知识沉淀 | 静态 FAQ | 57号知识库有 RAG 无案例库 | 案例四要素自动沉淀 + 缺口回写 | "死知识" → "活智慧" |
| 价值锚点 | 保障系统可用 | 各自为战的记录型状态机 | 系统可用 + 信值事务完整性 + 信任指标 | "技术指标" → "信任指标" |

### 1.2 设计哲学（三条转化）

1. **技术的温度**：最好的 AI 工程师让人忘记技术的存在，只记住被善待的感觉——设计自检问题永远是"这个设计是让角色更安心，还是让机器显得比人更冷漠？"；
2. **确定性为骨、共情为皮**：情绪判定/补偿计算/故障预测全部确定性代码（LLM 不产数字、不进判定链——全站铁律），LLM 仅生成共情话术与归因描述；
3. **信任即资产**：服务过程本身是"增强角色对平台信任"的正向循环——留痕上链、解释可展开、补偿透明化，把每次故障处理转化为信值体系的信任积累。

### 1.3 铁律总纲（继承全站宪法 + 本模块新增）

**继承**：
- XX66_MODE 三态开关默认 off（观测面永不关停——宪法口径）；决策面 off → 409；
- 惩罚性处置（账户冻结/信值扣减）与补偿执行**永不自动**，统一走 46号审批总线；
- 观测面/回流通道不受 MODE 影响；AI 合规建议仅为辅助，最终责任归属操作者与审批人；
- fail-soft：工程师设施故障不阻断业务主流程（fail-open 兜底）；
- 留痕采用哈希指纹链（62号 S8 范式），不直接上链；
- 多进程并发用 Redis 分布式锁（redis.asyncio.Lock / core.locks）；
- 新评分器入册 44号学习域（第56档案，batch40，55→56 全站同步）。

**新增（本模块红线）**：
- **自愈白名单制**：可执行动作封闭集合（restart_task/scale_task/cache_purge/readonly_switch/notify——经 27号任务轨），集合外动作一律生成建议书转人工；
- **manual 级故障强制人工**：不可被任何模式豁免（对齐 64号"high 阻断不可被 tier 豁免"范式）；
- **补偿双闸**：反欺诈门（确定性）+ 46号审批缺一不可；LLM 永不参与补偿额度计算；
- **情绪数据最小化**：情绪判定即用即弃，仅落匿名统计（烈度分档+模式选择），原文不落库——对齐 48号"音频即转即删"隐私红线。

## 四、核心机制设计

### 4.1 智能运维中枢（P0 生命体征 + P2 预测/自愈）

#### 4.1.1 全链路生命体征图谱（P0）

单端点 `GET /api/xx66/vitals` 聚合四源（全部只读，fail-soft 分区）：

| 区块 | 数据源 | 输出 |
|------|--------|------|
| system | 26号 metrics（system/performance/error 三类近 1h/24h 窗口聚合） | 各指标当前值/EWMA/异常分/环比 |
| business | 26号 business 类指标 + 45号信值流水速率（issue/burn 频次） | 信值结算引擎健康度 |
| ai_services | 35号 get_health + 44号 panorama（模式分布/漂移告警/调度器） | AI 生成服务健康度 |
| trust | 47号 hub overview（tier 分布/三联动子系统）+ 对账最新一轮结果 | 信值资产安全面 |

**生命体征总评（vitals_score）**：四区各算绿灯（0）/黄灯（1）/红灯（2）——阈值确定性（指标异常分均值 >0.5 → 黄；fatal 告警>0 或 26号 health_check=critical 或对账 danger 差异 → 红），总分映射 healthy/degraded/critical。快照落 `xx66_vitals_snapshots`（5 分钟粒度，供预测特征消费）。

> 巡检硬编码缺口（G3）对策：`POST /api/xx66/vitals/scan` 主动巡检 = 真实聚合四源生成快照 + 对 unhealthy 区块自动以对应级别调 27号 detect_fault 起链（替代 inspect_all 硬编码清单）。

#### 4.1.2 故障预测（P2，确定性——零 ML 模型）

**铁律**：禁止 GNN/神经网络/LLM 进预测判定链（对齐 64号 P3 确定性范式）；全部特征为阈值+窗口聚合，离线可复现。

特征工程与预测规则详见**附录B**。核心口径：
- 对每个 (source, metric) 滚动维护 7 日基线（μ/σ/p95/p99/EWMA(α=0.3)）；
- 触发预警条件（三条件与）：z-score>3 **且** 连续同向异常计数≥3 **且** 突破 p99；
- 预警级别：warning（单指标）/ critical（核心源 database/payment/redis 或多指标并发）；
- 预警产出"影响范围 + 建议预案 + 信值影响预估"建议书（shadow 留痕；assist 也不自动执行——预测只预警）。

#### 4.1.3 自愈编排（P2——27号状态机补链）

66号成为 `diagnose_fault` / `attempt_recovery` 的**首个真实调用方**（补 G2 断链）：

```
26/27号 detect_fault(detected 态)
  → 66号 diagnose: 根因分析(规则知识库 + 案例库检索 top-3 + LLM 归因描述[不产数字])
     → 27号 diagnose_fault(diagnoseResult.rootCause + recoveryStrategy.actions)
  → 66号 recovery_plan: 动作白名单校验
     ├─ 白名单内 + XX66_MODE=assist + auto/assisted 级
     │    → 变更预演(§4.1.4) → 27号 create_task(执行轨) → attempt_recovery
     ├─ 白名单外 或 manual 级 或 MODE=shadow
     │    → 建议书(46号 submit_change) + 07号工单转派(AI 附根因/方案上下文)
     └─ 终态 → engineer_log 留痕 + on_recovery_completed 回流(既有钩子复用)
```

**动作白名单（封闭集合，代码常量）**：`restart_task` / `scale_task` / `cache_purge` / `readonly_switch` / `notify_only`——每项映射 27号 task_type 与参数模板；白名单外动作（数据修复/配置变更/信值操作）一律建议书转人工（**红线：集合永不因 tier/模式豁免扩大**）。

**manual 级强制人工**：detect_fault 落 manual_required（27号既有语义）时 66号只做工单转派+上下文附注，任何模式不可自动执行（对齐"惩罚性处置永不自动"精神）。

#### 4.1.4 变更风险预演（P2）

所有自愈执行/系统变更建议前，沙箱预演三步（纯内存/只读，不触生产状态）：
1. **影响面推演**：按动作模板静态列出受影响模块/端点/数据表清单；
2. **信值安全预检**：预演动作涉及 45/62号数据域时，跑对账不变式 dry-run（§5.3 只读校验）；
3. **回滚可行性**：校验动作是否可逆（readonly_switch 可逆/restart_task 幂等可重试），不可逆动作降级为建议书。
预演结果附于建议书（供 46号审批人参考），预演失败阻断 assist 执行（fail-safe）。

### 4.2 角色支持引擎（P1）

#### 4.2.1 多模态入口

- **文本**：`POST /api/xx66/support/chat`（主入口，无状态；可选 body.sessionId 挂接 48号小竹会话上下文）；
- **语音**：复用 35号 `POST /api/hub/asr` 转写文本后进 chat（不重复建设）；
- **截图**：`POST /api/xx66/support/vision`——llm_client.vision 识别错误码/UI 元素 → 关联订单（错误码→order/payment 键域规则映射）→ 查 45号信值余额 → 输出精准方案。PII 脱敏复用 48号 mask_pii。

#### 4.2.2 情绪感知轨（规则主轨 + LLM 辅助轨——详见附录A）

```
输入文本 → 规则词典轨(确定性, <5ms):
    负面词表命中数 + 感叹号密度 + 重复标点 + 全大写比 + 字长异常
    → emotion_intensity 0-100 → 分档: calm / confused / frustrated / angry
  → LLM 辅助轨(XX66_LLM_MODE=on 时, 仅返回分档标签 JSON, 不产数字;
    返回 None/超时 → 回退规则轨——双轨范式)
  → 模式选择: calm+熟练 → 高效模式 | confused/新手 → 教学模式
             | frustrated/angry → 安抚模式(共情+优先处理+补偿选项主动展示)
```

- 情绪原文即用即弃，仅落 `xx66_emotions` 匿名统计（烈度分档/模式选择/满意度关联——供 44号学习域关联分析，无个人标识）；
- 新手/熟练判定：47号画像 tier + 会员注册时长（>90 天且历史工单≤2 → 熟练）。

#### 4.2.3 信值规则透明化解释（P1）

`GET /api/xx66/explain/{subject}`——复用三件套：
- 信值扣减/兑换质疑 → **64号 P2 explain 确定性重算**（展示计算过程/规则依据/历史记录三栏）；
- 画像 tier 质疑 → 47号 get_profile（riskEMA/命中明细/历史）+ 复核通道指引；
- 平台规则质疑 → 57号知识库 RAG 检索（信值规则域过滤）。
LLM 仅生成"通俗总结"一段并标注置信度；数字全部来自重算层（**LLM 不产数字**铁律）。

#### 4.2.4 愉悦体验设计（P1，确定性优先）

| 组件 | 实现 | 信值联动 |
|------|------|----------|
| 等待彩蛋 | 确定性文案库轮换（趣闻/平台彩蛋/轻音乐链接——零 LLM 依赖，零成本降焦虑） | 无 |
| 虚拟勋章 | 服务终态满意度≥4 → 勋章记录（纯展示） | 可选小额信值奖励走 46号审批（永不自动） |
| 工程师手记 | 重大故障修复后 LLM 生成故事稿 → 57号合规审查（违禁词+医药断言禁用）→ 人工发布 | 无 |
| 个性化感谢 | 按角色偏好（tier/会员等级）文案模板三档 | 无 |

### 4.3 知识进化层（P4）

#### 4.3.1 案例库（四要素——构建/更新 SOP 详见附录D）

- **结构**：`{problem, root_cause, solution, outcome}` 四要素 + 信值关联度标注（涉信值操作 case 标 value_linked=true）+ 匿名化脱敏；
- **自动沉淀**：自愈终态（recovered/failed）/工单 resolved 且满意度≥4 / 补偿执行完成 → 触发 case 入库管道（质量门校验后）；
- **检索**：复用 57号双路向量检索（n-gram 余弦基线 + KNOWLEDGE_EMBEDDING=on 语义路径 + rerank）供根因分析 top-3 匹配；
- **淘汰**：半衰期机制（90 日未被命中且无关联复发 → 归档）+ 失效标记（底层规则变更后批量复核）。

#### 4.3.2 知识联动与自助赋能

## 五、信值事务完整性保障技术方案（专项一：网站各功能映射）

### 5.1 全站信值触点风险表（各功能三重保护现状 × 66号覆盖）

| 兑换销毁（45 redeem/confirm） | burn 四联动 | ✅ 五重校验链（余额/冻结/日上限/月上限/保证金） | ⚠️ frozen 字段锁+状态机防重，**无 get_lock** | ❌ 无（pending 无超时对账） | 锁补强（§5.4）+ 不变式 I2/I4 + pending 超时对账 |

### 5.2 三重保护架构

```
事前(既有为主, 66号只读复用): 校验链(余额/冻结/上限/方向/熔断) + 47号三查前置
事中(补强):  core.locks.get_lock("trust45:txn:{trustId}") 包裹 RMW 关键段
            (锁补强调轨, §5.4——经46号审批+全回归后合入, 66号仅提案)
事后(66号新建——对账引擎):
  T+1 定时(XX66_RECON_MODE=on, 复用 PAY60 调度范式)
    + 手动触发 POST /api/xx66/reconcile/run
    + 事前预演 dry-run(变更预演调用)
```

### 5.3 对账引擎（核心新建）

**四条不变式**（全量只读校验，确定性）：
- **I1 总量守恒**：`Σledger(issue) − Σledger(burn) == Σbalance(全档案)`；
- **I2 冻结一致**：`Σbalance.frozen == Σpending redeem 申请额`；
- **I3 准备金锚定**：`reservePool == Σ(issue_net/2) − Σ(burn_amount)`（62号锚定语义）；
- **I4 流水完整**：每笔 issue/burn/transfer 在 62号事件域可追溯（depositId/reserve_ref 双向核对）。

**差异分级**：
- `info`（±0.01 容差浮点/时间窗错位）→ 留痕观测；
- `danger`（不变式破坏/单档案余额错位）→ 生成"冻结建议书"（**46号 submit_change——永不自动冻结账户**，对齐惩罚性处置铁律）+ 冲正建议（补发/回滚方案）。

**冲正执行**：经 46号审批后走 45号 issue 轨（`reserve_ref="reconcile:{run_id}"` 锚定）——冲正本身也是一笔可对账的信值事务，形成自洽闭环。

**产物**：`xx66_recon_runs`（每轮 run 快照+差异清单+处置状态）+ `GET /api/xx66/reconcile/report` 观测面。

### 5.4 锁补强调轨（可选加固项，独立审批）

勘察实证：45号 redeem/issue"读余额→校验→写回"为非原子无锁读改写（并发超兑/lost-update 风险，现有上限校验仅部分兜底）。
**调轨方案**：在 trust_asset_service 的 redeem/redeem_confirm/issue 三函数 RMW 段加 `get_lock(f"trust45:txn:{trust_id}")`（async with，10s TTL——core.locks 既有设施零新建）。
**约束**：此为 45号核心改动——独立提交、经 46号审批、跑全量信值回归（45号 P0-P7 + 62号 + 64号 + 批次一~七回归）后方可合入；66号 P3 仅交付提案+对账（观察验证锁缺失期差异基线）。

## 六、服务补偿信值计算规则（专项二——DSL 全文见附录C）

**原则**：
- 补偿 = 因平台原因（宕机/误扣/对账差异确认）导致的角色损失，**确定性 DSL 计算，LLM 永不参与额度**；
- 额度与 tier 挂钩（trusted×1.2 … restricted×0.6——对齐 60号"高信任少摩擦"精神：高 tier 上浮是信任回报，restricted 减半但仍可补偿+可申诉，绝不拒之门外）；
- 情绪烈度附加系数（angry 档 +10%——"被善待的感觉"量化为确定性规则，非 LLM 判断）。

**反欺诈门（确定性，借鉴 64号 P3 五防范式）**：
- 同窗同实体去重：incidentId/ticketNo 1:1 幂等（重放拒绝）；
- 连环申请检测：同实体 7 日 ≥3 次补偿 → 建议书标记人工终审；
- 多账号关联：同设备指纹/IP 段 7 日 ≥5 账号申请 → 标记（对齐 ARB-MA 口径）；
- 额度封顶：单案 ≤50 TV / 日全站 ≤500 TV / 月每实体 ≤200 TV。

**执行轨**：DSL 计算建议书 → 反欺诈门 → **46号 submit_change → approve 后 45号 deposit 轨入账**（reserve_ref=`comp:{case_id}` 锚定）→ 透明化推送（补偿原因/计算过程/到账通知）→ engineer_log 留痕。补偿记录公开可查（`GET /api/xx66/compensation/{id}`——含计算依据展开）。

```
沟通准则：
1. 分步引导：每次只讲一步，确认完成再进下一步（"做完了告诉我，我们进行第 2 步"）；
2. 零术语：用生活类比解释技术概念（如"清缓存=把小黑板擦干净重写"）；
3. 可视化：能配图/截图指引的优先给操作路径（页面名→按钮名→预期结果三段式）；
4. 结尾自检："刚才这几步里，哪一步和预期不一样？"——主动暴露理解偏差。
数字铁律同上。
```

**高效模式（calm+熟练）**：

```
你是智能工程师小匠，当前用户为熟练用户（判定依据：规则轨 calm 档且注册>90天且历史工单>2）。
沟通准则：
1. 直达结果：结论先行（"已定位：{根因一句话}，方案：{动作}"），背景其次；
2. 提供高级选项：除标准方案外附"高级路径"（日志自查入口/API 端点/配置项名）；
3. 尊重时间：单轮不超过 5 行；用户追问再展开。
数字铁律同上。
```

### A.3 共情话术库（确定性种子——LLM 仅润色，禁止生成新承诺）

| 场景 | 话术（种子） |
|------|--------------|
| 支付失败 | "这次支付没成功，钱不会无缘无故消失——我们先一起确认卡在哪一步，我全程都在。" |
| 信值质疑 | "您的每一分信值都有完整账本记录，我马上调出这笔的计算过程给您看——规则透明是我们的底线。" |
| 等待超时 | "让您久等了。等待期间给您准备了一个小彩蛋：{彩蛋文案库轮换项}——问题一有进展我立刻同步。" |
| 故障修复后 | "问题已修复（{时长}）。我们写了这次故障的工程师手记，记录了发生原因和防再发措施——您的耐心值得一份交代。" |

### A.4 禁用词/红线清单

- 敷衍模板词（亲/呢化语气滥用）、技术甩锅（"这是正常的"）、绝对化承诺（"肯定""100%"）、恐吓性表述、数字自行估算；
- PII 红线：情绪判定输入必须先过 mask_pii（48号复用）；情绪原文不落库、不进 LLM 上下文二次使用。

## 附录B：故障预测特征工程文档（确定性——零 ML）

### B.1 特征表（每 (source, metric) 维度滚动计算）

| 特征 | 公式 | 窗口 | 用途 |
|------|------|------|------|
| feat_zscore | (当前值 − μ_7d) / σ_7d | 7 日基线 | 突破幅度 |
| feat_ewma_dev | 当前值 − EWMA_α0.3 | 连续 | 短期漂移 |
| feat_streak | 连续同向异常计数（超 threshold.warning） | 连续样本 | 趋势确认 |
| feat_slope | (v_now − v_1h前) / 60s | 1 小时 | 速率 |
| feat_pctile | 当前值在 7 日分布的分位 | 7 日 | 稀有度（p95/p99 突破） |
| feat_burst | 5 分钟计数 / μ_5m_7d | 5 分钟 | 突增（复用 60号 ×3 口径） |
| feat_recur | 同 (source,metric) 7 日预警复发次数 | 7 日 | 慢性病识别 |
| feat_linked | 并发关联告警/故障数 | 当前 | 雪崩前兆 |

### B.2 预测规则（三条件与，确定性）

```
触发预警: feat_zscore > 3 AND feat_streak >= 3 AND feat_pctile > 0.99
级别:     warning（单指标命中）
          critical（source ∈ {database, payment, redis} 或 feat_linked ≥ 3 或
                   26号 health_check=degraded 叠加）
提前量:  5 分钟粒度窗口外推（feat_streak × feat_slope 达到 critical 阈值 ETA），
          目标提前 ≥30 分钟预警
```

### B.3 数据源与落库

- 输入：26号 metrics（collect_metric 上报流）+ xx66_vitals_snapshots（5 分钟快照）；
- 基线：每 (source,metric) 滚动 7 日窗——冷启动 <3 样本不落预警（对齐"冷启动 <3 样本不落快照"既有惯例）；
- 产物：xx66_predictions（features 全量留痕——可复现性铁律）+ 建议书（影响范围/预案/信值影响预估=该源近 24h 信值流水频次×预估中断时长，确定性乘法）。

## 附录C：服务补偿信值计算规则 DSL

### C.1 语法（声明式规则，确定性求值引擎）

```dsl
rule 信值误扣补偿 {
  trigger: reconcile_diff_confirmed | ticket_compensation(severe) | incident_postmortem;
  when: { cause: "platform_error", loss_amount > 0 };
  base: loss_amount;                       // 损失锚定——补偿永不超损失
  tier_multiplier: { trusted: 1.2, standard: 1.0,
                     watched: 0.8, restricted: 0.6 };   // 47号 tier 联动
  emotion_bonus: { angry: 0.10, frustrated: 0.05, default: 0.0 }; // 有温但封顶
  history_factor: { member_loyalty_years >= 2: 0.05 };  // 历史贡献（可选）
  caps: { per_case: 50, daily_site: 500, monthly_per_entity: 200 };  // TV 单位
  fraud_gates: {
    idempotent_key: "incident_id | ticket_no 1:1";      // 同窗同实体去重
    serial_detector: "7d >= 3 次申请 → 标记人工终审";
    multi_account: "同设备指纹/IP段 7d >= 5 账号 → 标记(ARB-MA 口径)";
    tier_watch: "restricted/watched → 强制人工终审(不拒之门外)";
  };
  execution: propose → fraud_gates → 46号 submit_change
             → approve → 45号 deposit(reserve_ref="comp:{case_id}");
  transparency: 计算过程四栏展示(基数/系数/封顶/依据) 推送角色;
}
```

### C.2 规则清单（首版三条）

| 规则 | trigger | base | 说明 |
|------|---------|------|------|
| 信值误扣补偿 | reconcile_diff_confirmed | 差异额 | 对账 danger 确认后自动生成建议书 |
| 宕机损失补偿 | incident_postmortem | 受影响角色数 × 1 TV | 上限内按档补偿 |
| 工单严重补偿 | ticket_compensation(severe) | 复用 07号三级补偿基额 | 07号 propose 的信值化延伸 |

### C.3 求值引擎约束

- DSL 规则版本化（规则变更留痕 + 全站宪法域不可校准精神：cap/tier 系数属宪法治安域，调整须 46号审批）；
- 求值结果 = `min(base × Σ系数, caps.per_case)`（先乘后截断，封顶永不破）；
- 引擎为纯确定性代码（解析→求值→留痕三段），**LLM 禁止进入任何环节**；
- 每次求值落 xx66_compensations（规则版本/因子快照——可复现审计）。

## 附录D：AI工程师知识库构建与更新 SOP

### D.1 案例生命周期管道

```
触发源: 自愈终态(recovered/failed) | 工单 resolved+满意度≥4 | 补偿执行完成
  → ① 抽取: 四要素结构化(problem/root_cause/solution/outcome)——规则模板优先,
       LLM 仅做摘要润色(禁止产数字/承诺)
  → ② 质量门: 四要素完整(缺一不入) + PII 脱敏(48号 mask) + 置信度来源标注
       (根因来自诊断引擎 confidence, 方案来自白名单/人工审批记录)
  → ③ 去重: 与既有案例余弦 ≥0.85 合并(复用 57号相似去重口径), 复发计数+1
  → ④ 入库: embedding 生成(KNOWLEDGE_EMBEDDING=on 时, 失败回退 2-gram)
       + valueLinked 标注(涉信值操作 case)
  → ⑤ 检索消费: 根因分析 top-3 / 自助向导 / proactive 建议
  → ⑥ 淘汰: 90 日未命中且无关联复发 → 归档; 底层规则变更 → 批量失效复核
```

### D.2 知识联动更新（三通道）

1. **缺口回写**：支持对话未命中（案例+知识库双未命中）→ 57号 record_gap（既有缺口管道）→ 缺口月报驱动知识补充；
2. **规则变更同步**：信值规则/阈值调整（46号审批通过的 change）→ 自动标记受影响案例批量复核（失效或更新）；
3. **学习域关联**：`xx66_emotions` 匿名统计 × 案例命中率 → 月度分析"高 tier 与低 tier 角色问题类型差异"（信值行为关联学习）→ 服务策略校准建议书（46号审批——AI 仅建议）。

### D.3 SOP 红线

- 案例入库永不绕过质量门（含 LLM 生成内容——LLM 产物须人工抽检 10% 才可转正为"已验证"档）；
- value_linked=true 案例的 solution 字段禁止含具体数字（只有动作序列+审批引用）；
- 案例库只读于根因检索，永不作为自动执行依据（执行仍走白名单+审批）。
